# 让没有电脑的 iPhone 用户用上 RunnerCoach

> 承接《交付形态调研》§9、《iOS迁移评估》§7、《小程序可行性评估》。
> 评估基准：`main` @ 1.1.1，2026-11-12。**本文只写入工作区，未提交 git。**

---

## 一、先分清「苹果用户」是谁

这两个场景的答案完全不同，混在一起会选错方案：

| | 数据是谁的 | 隐含要求 |
|---|---|---|
| **A 自己用** | 你自己的佳明账号 | 只要求「在 iPhone 上看得到、像 App」 |
| **B 别人用** | 对方自己的佳明账号 | 要求「每人一份数据、互不串号」，且对方没有电脑 |

**本项目现有的一切线上产物（relay 看板、`site/index.html`）都只含数据主人自己的健康数据。**
把它直接发给 B 类用户，等于让他看你的病历，不是「他用上了软件」。

---

## 二、结论先行

| 场景 | 推荐 | 工作量 | 用户侧 |
|---|---|---|---|
| **A 自己用** | **现成 relay HTTPS 看板 + 添加到主屏幕** | **0 人日，今天就能用** | 零安装、零硬件 |
| **B 别人用（最轻）** | 投递一图流 PNG / 纯文本简报 | 0–2 人日 | 零安装、零硬件 |
| **B 别人用（体验最好）** | **代管一台中枢 + PWA + 每人独立访问码** | **2–8 人日** | 零安装、零硬件 |
| B 别人用（完全自助） | 纯前端 PWA + 自导数据 | 40–60 人日 | 零安装，但导出很别扭 |

**都不需要**：Mac、小程序、企业主体、备案、App Store、用户装任何 App、用户买电脑。

## 三、实测：项目里那条公网看板链路是活的

2026-11-12 对本机 `llm.py:114-115` 内置的公网域名做了带分享码的 HEAD 请求：

| 项 | 结果 |
|---|---|
| 不带 sharecode | `403 Forbidden`（平台层分享门禁） |
| 带 sharecode | **`200 OK`**，`Content-Type: text/html`，`Content-Length: 46796` |
| 传输 | **HTTPS**，`Server: CloudStudio Gateway` |
| 记忆 | `Set-Cookie: __wb_rsc=…; Max-Age=2592000; HttpOnly; Secure`（**30 天免重输**） |
| 内容时间 | `Last-Modified: Tue, 10 Nov 2026 01:15:29 GMT` → **是 11-10 的旧快照** |

链路本来就是完整的：`daily.bat` → `cli.py:456-460` 写 `site/index.html` →
`server/app.py:1130-1141` 服务 `site/` → `tools/relay_client.py` 穿隧道 →
`server/relay/app.py:74-76` 的 `STATIC_MAP`（`/`、`/index.html`、`/card.png`）+ 快照回落。

**这条链路一直被当成「AI 网关的测试通道 / 看板兼任」，没人把它当 iPhone 入口。**
`server/deploy.md:217-222` 原文：「兼任每日看板…约 5 秒拿不到就回落云端内置快照」。

## 四、iOS 26 让这一步几乎零开发

WebKit 官方 [Safari 26.0 发布说明](https://webkit.org/blog/17333/webkit-features-in-safari-26-0)：

> *"By default, every website added to the Home Screen opens as a web app … Simply put, there are now **zero requirements for installability** in Safari."*

也就是说 **iOS 26 / iPadOS 26 起，「添加到主屏幕」默认就是全屏 Web App，
不再要求 manifest、图标或 service worker。** 用户操作只有三步：

1. Safari 打开那条 HTTPS 链接（带 sharecode，Cookie 记 30 天）
2. 分享 → 添加到主屏幕 → 保持「Open as Web App」开启
3. 主屏出现图标，点开是无地址栏的独立窗口

`site/index.html` 本身已有 `width=device-width` + `@media(max-width:960px/560px)`
（`:3,141,147`），iPhone 上是自适应的，不是一图流那种 `width=1080` 整张缩放。

> 注意：service worker / 离线缓存仍只在 **HTTPS 安全上下文**注册。
> 现有 relay 域名天然满足；局域网 `http://IP:8765` 不满足（这也是别走纯局域网 PWA 的原因）。
> Safari 还会在 7 天无交互后清除脚本数据，别把唯一副本放手机里。

## 五、四条路径逐条看

### 路径 0：自己用 —— 今天就能用（0 人日）

打开现成链接 → 添加到主屏幕。**但上线前必须先补三件事**：

| # | 缺口 | 位置 / 证据 |
|---|---|---|
| 1 | **看板是 11-10 旧快照**，云端 `server/relay/index.html` 甚至是 11-06 | 实测 `Last-Modified`；`.gitignore:60-61`；`deploy.md:220-221` 现在纯手动 `cp` + 重新发布 |
| 2 | **看板路径零鉴权**：relay 自身对 `/`、`/card.png` 直接进 `_dashboard()`，只有平台层 sharecode 门禁 | `server/relay/app.py:202-204`；对照 `serve.py:913-944` 有 `?k=` + `gc` cookie 的 `_gate` |
| 3 | 只有 3 个路径有快照回落，`/event`、`/history`、`/ai` 没有；`/ai` 本来就 loopback-only | `STATIC_MAP`；`serve.py:109-115` |

最小改法：`daily.bat` 尾部加两行同步 `site/` → `server/relay/`；把 `serve.py` 的 `_gate`
搬到 `_dashboard()` 前，或让看板路径也校验分享码；`FRESH_WAIT=5`（`relay/app.py:73`）调小。
补一个 `manifest.json` + `apple-touch-icon` 只是让图标和名字好看，iOS 26 下**不是必需**。

### 路径 1：别人用 —— 投递（0–2 人日，零硬件）

把 `output/card.png`（1080×1920 一图流）或 `brief.one()` 纯文本发微信，iPhone 直接看。
`daily.bat` 已串好 `sync → report → card`。

**两个必须记住的坑**：

- **只发 PNG，别发 `.html`**：iOS 微信内置浏览器不直接渲染 `.html` 附件，
  《交付形态调研》§9 D 写的「双击打开」在 iPhone 上要「用其他应用打开 → Safari」，普通用户会卡住。
  `exportspec.py:5-8` 已把画幅归一到 9:16，微信预览不裁切。
- `latest.html` 里 `report.py:224` 的 `fetch('/ai/note')` 离线必然失败并显示「还没有教练点评」占位，
  离线投递版应去掉 `NOTE_POLL_JS` 或换静态文案。

**数据入口**：让对方在 iPhone 的 Garmin Connect App 里用官方
[「授权查看者」](https://support.garmin.com/zh-CN?faq=oFgzQxgDmq01HUOtmRrltA)功能，
把「活动和健康数据 / 用户资料 / 训练和计划数据 / 报告」**只读**授权给你的账号
（设置 → 个人资料与隐私 → 授权查看者；最多 20 个连接，可随时撤销）。
**不需要对方给密码、不需要对方有电脑、不触碰「不得共享凭据」条款** —— 这是 B 场景唯一官方合规的入口。
待验证：现有 `auth.py` / `client.py` 的同步链路能否读到「授权查看者」视角的数据。

代价：每天要跑一次 + 发一次；结果是静态图，不能点、不能翻历史。

### 路径 2：别人用 —— 代管中枢 + PWA（**推荐**，2–8 人日）

你出一台常开的机器（旧笔记本 / NAS / 闲置安卓机 / 迷你主机），
按用户分目录 + 分访问码；iPhone 添加到主屏幕，随时能翻今日、历史、教练、赛事。

现成的：`run.bat serve --lan`（`serve.py:960-1009`）已绑 `0.0.0.0` + 自动访问码 +
`gc` cookie；`ui.py` / `eventui.py` 已有动态页与响应式 CSS；`daily.bat` / `daily.sh` 已有同步链。

**仍缺的 4 项**（正是《iOS迁移评估》§7 与《交付形态调研》§9 B 列的清单）：

1. PWA 三件套：`manifest.json`、`sw.js`、`apple-touch-icon` —— 全盘 Grep **零命中**，项目完全没有
2. 开机自启 + 定时同步：`daily.bat` / `setup-termux.sh` 都没注册计划任务，靠手动点图标
3. PIN 登录：现在只是 `token_urlsafe(5)` 的 URL 一次性码，无输入框、无失败锁定、cookie 无 `Secure`
4. **HTTPS**：`serve.py:975` 是裸 `ThreadingHTTPServer`。最省事的做法是**复用路径 0 的 relay HTTPS 域名**，
   或前面挂 Caddy / Tailscale Serve；别让 iPhone 直接吃 `http://192.168.x.x:8765`

用户侧：零安装、零硬件、不买 Mac。缺点是中枢得有人维护，且多用户隔离要自己写。

### 路径 3：完全自助 PWA（40–60 人日，现阶段不推荐）

纯前端 + 用户自己导出 FIT/GPX → IndexedDB 离线算。零凭据、可公开分发，
但 `metrics/coach/nutrition/body/brief` 约 3–4 千行要移植 JS、出图改 canvas，
且**瓶颈在入口**：iPhone 上导出佳明数据很别扭（《交付形态调研》§9 C 已给同结论）。

一个值得验证但别现在押注的变量：上一轮发现的**国区官方 Personal API**。
若它开放 CORS，iPhone PWA 可自己存 Key、自己拉数据，中枢都不需要；
但 CORS 未验证、Key 放前端有风险、算法仍要移植，**先当假设，不当方案**。

## 六、隐私红线（上线前必读）

- 《交付形态调研》§5.2 明写「**不要把真实看板发布到公网**」，而实测云端那份 46 KB HTML
  就是含恢复度、睡眠、HRV、体重、体成分的真实看板。**自用没问题，转发给别人之前必须处理。**
- 分享码是硬编码在 `llm.py:114-115` 的常量，且 relay 看板路径本身零鉴权 →
  链接一旦外泄，任何拿到的人都能看完整健康档案。至少要：换码、加 PIN 页、或只发脱敏版。
- 轨迹 = 精确行踪。`privacy.py` 的 `trim` / `hide` 已在出图前脱敏，对外投递版建议强制 `trim`。
- B 场景务必做到「一人一目录、一人一码」，绝不能把多个人的健康数据放进同一个 `garmin.db`
  （现有 `store.py` 的表**没有 `user_id`**，这是多用户改造的第一步）。

## 七、明确不推荐

| 方案 | 为什么 |
|---|---|
| iOS 原生 App（内嵌 CPython） | 38–56 人日 + 必须有 Mac + 免费签名 7 天过期 / TestFlight $99 / 上架要软著与备案。对「没有电脑」的用户最不友好 |
| 微信小程序 | 见《小程序可行性评估》：60–100+ 人日 + 数据授权 + 敏感信息合规 + 主体资质 |
| 局域网纯 HTTP PWA | iOS 下不是安全上下文，service worker / 离线 / 持久存储全降级；且用户出了家门就打不开 |

## 八、下一步

先回答一个问题：**苹果用户是你自己，还是要给别人用？**

- **自己用** → 今天就能给一条可添加到主屏的链接。我可以直接把最新 `site/` 重新发布，
  并补上 `daily.bat` 的自动同步 + 看板鉴权（约 0.5–1 人日）。
- **给别人用** → 先定人数、以及是否愿意代管一台常开的机器。
  人数 ≤5 且不常看 → 路径 1；想要完整体验 → 路径 2。
- 无论哪条，**先验证国区官方 Personal API**（《小程序可行性评估》§6 实验 1）：
  若通，替换 `auth.py` 的逆向登录，所有方案同时减负。
