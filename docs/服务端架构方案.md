## 一、决策摘要

| 决策项 | 结论 | 状态 |
|---|---|---|
| 苹果端入口 | **PWA**（添加到主屏幕），不做原生 App | 方案定，未实施 |
| 总体架构 | **一套代码、两个宿主**：安卓端本地跑，网页端服务端跑 | 方案定，未实施 |
| 数据归属 | **按端隔离**：安卓数据在手机，网页数据在服务器，不互通 | 接受为设计约束 |
| 视频 / 长图 | 服务端**单并发串行队列**，不提高并发 | 方案定，未实施 |
| 数据同步 | 登录留在用户设备，服务端只拿现成 token 读；全局队列错峰 | 方案定，未实施 |
| 服务器容量 | 看板几百并发；同步 50–200 人；视频串行约 30 个/天 | 实测评估，非承诺 |
| 主体 | 个体户；软著为个人名义，需补《著作权授权书》 | 已定（见软著文档 §8） |
| 收费服务 | 个体户办不了经营性 ICP 许可证 → 与上架解耦，不混在一起 | 已定 |

一句话：**安卓用户零改动继续本地跑；网页用户走服务端；重活串行排队；登录不下放给服务器。**

## 二、现状盘点（实测，不靠印象）

### 2.1 客户端：安卓端其实是 WebView 壳

真实的 UI 链路是：`MainActivity` 用 WebView 加载 `127.0.0.1`，Python（Chaquopy 内嵌 CPython）
在本地起 HTTP 服务，输出 `garmin_cn/card.py`、`actcard.py`、`aiui.py` 等模块生成的 HTML。

**推论**：iOS 上跑不了 Chaquopy、跑不了内嵌 CPython、也就没有 `127.0.0.1` 可加载。
“本地计算 + WebView” 这条路在苹果端天然断掉，必须借服务端。

### 2.2 服务端：能力有了，但内核还没上去

| 项 | 实测结果 |
|---|---|
| 规模 | 8542 行，14 个 py；含用户组、远征、排行榜、bingo、支付、邮件 |
| `/opt/runnercoach/garmin_cn/` | **MISSING** —— 服务端完全没有 Python 内核 |
| `deploy/install.sh` 拷贝列表 | 只有 6 个 `server/*.py`，不含内核 |
| 渲染工具 | 服务器**没有** chrome、没有 ffmpeg |
| Python 版本 | 服务端 3.12，客户端 3.13（需注意兼容） |
| 已有路由 | `/`、`/dashboard` 等静态 HTML，以及 `/v1/auth` 设备令牌 |

“复用同一份代码”是目标架构，**不是现状**。要打通需一次性部署动作，见 §7。

### 2.3 线上服务器配置

实测 `admin@39.106.174.153`：

| 项 | 值 |
|---|---|
| CPU | 2 核 Xeon |
| 内存 | 1.6 GB，**无 swap** |
| 磁盘 | 40 GB，剩 35 GB |
| 当前进程 | 约 20 MB，负载 0.00 |

### 2.4 数据接入：两家都不是正规 OAuth

| 平台 | 当前方式 | 性质 |
|---|---|---|
| 佳明 | `sso.garmin.cn` 网页 SSO 拿 Cookie | 逆向登录 |
| 高驰 | `teamcnapi.coros.com` 移动端私有接口，登录一次存 token | 逆向登录；代码注释写明官方 Open API 要注册开发者应用 |

这直接决定了 §5 的 IP 策略。

## 三、苹果端：为什么选 PWA

### 3.1 三条路线

| 路线 | 结论 | 关键原因 |
|---|---|---|
| **PWA（选）** | ✅ 推荐 | 你的 UI 本来就是 HTML；服务端已有静态路由与 443 配置；无需 Mac、无需 $99 |
| 原生壳上架 App Store | ❌ 否 | 见下 |
| 桌面同步 + 云展示 | ❌ 否 | 用户不保证有 PC，且引入两套功能分层，加重架构 |

### 3.2 App Store 的硬障碍（不止是钱）

1. **Guideline 4.2**：纯套壳（把网页包进 WKWebView）会被拒，需证明原生 functionality。
2. **$99/年**开发者账号 + 必须有 Mac 才能打包。
3. **Guideline 3.1.1**：服务端已有余额、兑换码、微信支付。苹果要求数字商品走 IAP，
   这套充值逻辑在 iOS 过不了审，要为苹果单独做一套 IAP，成本陡增。
4. 健康类目、软著、App 备案同样绕不开。

### 3.3 PWA 要补的东西

- `manifest.json` + Service Worker + 图标（iOS 26 起“添加到主屏幕”默认全屏 Web App，
  这三项主要是图标和名字好看，不是必需）。
- 把 `card.py` / `actcard.py` / `aiui.py` 接进服务端路由，按登录用户出页面
  （这些模块是纯标准库“吃数据吐 HTML”，不用大改）。
- 登录复用 `/v1/auth` 设备令牌，网页端换 cookie 会话。
- **证书必须是可信 HTTPS**（Let's Encrypt 或 Cloudflare）。现在 8443 自签证书不行，
  Service Worker 不会注册。

**推送**：iOS 网页推送不需要 $99 开发者账号，VAPID 标准密钥即可；
但只在“添加到主屏幕”之后可用，且必须有可见通知、不能静默推。赛事提醒、同步完成提醒够用。

**冲突要注意**：此前定的 Cloudflare Access 是“访问前先验证身份”，
PWA 对外服务就不能挂 Access，否则 iPhone 每次打开都过人机验证。域名与备案口径需重新捋。

## 四、容量：瓶颈不在硬件

### 4.1 分档

| 搬上来的功能 | 这台机器能撑 | 真正的限制 |
|---|---|---|
| 只做看板 / 榜单 / HTML 展示 | **几百并发** | 单请求 20–50 ms；1.6 GB 够用 |
| 加数据同步（每人每天一次） | **50–200 人** | 不是服务器，是**佳明 / 高驰风控** |
| 加视频 / 一图流渲染 | 并发 2–3 就满 | chrome + ffmpeg 吃满 2 核，且可能 OOM → 改串行，见 §6 |

### 4.2 实测依据

- 渲染很轻：import 渲染模块 0.23 s、内存峰值 9.5 MB；出一份看板 HTML 是毫秒级。
- 存储宽裕：重度用户（194 条活动、297 天数据）库 15 MB，35 GB 可放 2000+ 人。
- 同步很慢：代码人为限速 0.2–0.25 s/请求防 429；30 天回溯几十个请求，单人 8–16 s。
  这是网络等待，不占 CPU，但占时间。

### 4.3 两根短板

1. **上游 API 风控**：所有用户共用服务器出口 IP，几十个账号高频拉取像爬虫。
   429 退避是“被限流后补救”，不是“不被封”。
2. **视频 / 长图渲染**：`video.py` 用无头 chrome 逐帧截图 + ffmpeg 合成，
   45 秒片子上千帧，单个几十秒到几分钟 CPU。2 核同时跑 2–3 个就满载；
   1.6 GB 无 swap，再多直接 OOM。

## 五、IP 与 token：把「登录」和「读数据」拆开

这是本节最关键的判断。上一版容量图里“几十人即危险”的前提是**服务器代替用户登录**。
若登录留在用户自己设备上，该结论不成立。

### 5.1 风险分级

| 动作 | 平台视角 | 风险 |
|---|---|---|
| 登录拿 token | 一个 IP 上反复出现不同账号登录 | **高危**，像撞库 / 爬虫 |
| 拿现成 token 读数据 | 某账号今天从两处访问（手机 + 服务器） | 正常，等同换网络 / 多设备 |

**约束：登录动作钉死在客户端，服务端只读取用户上传的现成 token。
服务端永不碰密码、不做登录请求——这条写进架构约束，别开例外。**

### 5.2 真实请求量低到不像话

按 `sync_day` 代码算，每人每天同步一次：

- 日汇总 1 + 睡眠 1 + HRV 1（区间接口可批量省掉）+ 活动列表 1 ≈ **4 个请求**
- 开 extras（压力、身体电量）最多 **6 个**

50 用户 = 300 请求/天 = 每小时 12 个，每 5 分钟一个。加上 0.2 s 间隔和随机抖动，
对佳明 / 高驰完全静默。**低频 + 各用各的 token，同 IP 不是主要矛盾。**

### 5.3 真正的坑：token 过期

代码中写明：高驰 Web token 服务端不提供 refresh，约 24 小时过期（返回 `result=1019`）。
若把重登放到服务器上，就变成“同一 IP 每天替几十个账号登录”——**这才真会被封**。

处理方式：

1. 过期后走**用户授权**，不走服务端自动重登。推送提醒“高驰授权已过期，点此重新连接”，
   链接打开登录页，用户自己完成。一天一次有点烦，但安全第一。
2. 长期解：申请官方 OAuth2。高驰 `open.coros.com` 有官方通道、带 refresh token，值得申请；
   佳明个人开发者基本拿不到 Connect API 授权，短期不指望。可并行尝试，不作为上线前置。
3. 全局同步队列 + 随机抖动：别让所有人早上 8 点同时点同步，打散到全天，串行执行。

## 六、重任务：单并发串行队列

**核心思路：不提高并发，改成排队吞吐。**

两个前提叠加后答案就变了：频次不高（视频偶尔点一次）+ 单一架构（服务端统一提供）。
同一时刻只允许一个渲染任务跑，其余排队 —— CPU 和内存永远只被一个 chrome + ffmpeg 占用，
2 核绰绰有余，永远不会 OOM。代价只是“点击后等一两分钟”，低频场景完全可接受。

### 6.1 复用现有范式

`server/tick.py` 已经是“cron 触发 + 数据库行锁抢任务 + 逐条短事务”模式，
且专门处理了跨进程安全（`BEGIN IMMEDIATE` 抢锁，不是进程内锁）。
渲染队列照抄即可，不引入 Celery / Redis，保持纯标准库风格。

### 6.2 要加的组件

| 组件 | 做法 |
|---|---|
| 任务表 | `render_jobs(id, user_id, kind, params, status, created, finished)` |
| 提交 | 点“生成视频”→ 插 `pending` 记录，立即返回任务号 |
| 执行 | 常驻 worker（或 cron 每分钟拉一次）用 `BEGIN IMMEDIATE` 抢一条，标 `running` |
| 进程内闸门 | `threading.Lock()` 或文件锁，**保证同时只跑一个**（内存不爆的关键） |
| 轮询 | 前端拿任务号每 2 秒问一次状态，完成给下载链接 |
| 失败 / 超时 | 记错误、自动重试一次，超过 N 次标 `failed` |

`video.py` 的 `export()` 已有 `workers` 参数，2 核默认算出 2，锁成 1 即可保证单任务独占。

### 6.3 容量重算

- 单个视频 1–2 分钟，串行一天理论 **700–1400 个**。
- 200 用户每人每周 1 次 = 30 个/天，机器闲得发慌。
- 内存：单 chrome 300 MB + ffmpeg 100 MB + 系统 450 MB + 服务 20 MB ≈ 870 MB，1.6 GB 内安全。
  **闸门守住“同时一个”就不会 OOM。**

同步队列可共用同一套“任务表 + worker”框架，架构反而更统一。

## 七、最终架构：一套代码、两个宿主

**安卓端继续本地跑，网页端才用服务器。** 这不是两套功能，是同一份 Python 代码跑在两个宿主上。
安卓用户本来就在本地同步、本地渲染，让他们继续这样，服务器压力直接砍掉大头；
网页用户（含全部 iPhone 用户）走服务端串行队列。用户看到的功能一致。

### 7.1 三笔一次性成本

| # | 事项 | 说明 |
|---|---|---|
| 1 | 部署内核到服务器 | `garmin_cn/` 加进 `deploy/install.sh` 拷贝列表；装 chrome + ffmpeg；验证 Python 3.12 兼容 |
| 2 | 多租户数据隔离 | 安卓端是 `GARMIN_HOME` 单用户目录，网页端要给每人独立 HOME（如 `/data/users/<uid>/`），改造 `store.py` 路径逻辑 —— **唯一需要动内核代码的地方** |
| 3 | 网页端 API 层 | 把 `sync` / `render` / `export` 包成任务，走 §6 串行队列；相对最轻 |

另注意：新增模块漏加进 `deploy/install.sh` 不会报错，而是 ImportError 让整个 groups 服务挂掉
（线上表现：组接口 503）。改表结构前后都要备份 `data/groups.db`。

### 7.2 必须接受的取舍：各端数据不互通

安卓数据在本机，网页数据在服务器。同一账号今天用安卓同步、明天用 iPhone 网页看，
**看不到昨天的安卓数据**。这是“各端本地优先”的天然结果。

建议明确接受，写进设计文档，避免以后被当成 bug。若要打通就得做云同步，是另一个量级的工程。

### 7.3 合规红线

“全搬服务器”意味着用户健康数据（睡眠、心率、体重、轨迹）上云，与原始“数据不出本机”定位冲突。
隐私说明要重写，需**告知同意 + 账号删除能力**（这也是 ICP / App 备案的硬性要求）。
凭证（佳明 / 高驰 token）在服务器上要加密存储，不能明文进 SQLite。

## 八、被否掉的方案及原因（别再反复）

| 方案 | 否掉的原因 |
|---|---|
| **视频 / 重任务放客户端** | 不能保证用户有 PC；且会引入两套功能分层，加重架构。用户明确否 |
| **iPhone 视频降级成 PNG / 留在 Mac 生成** | 同上；Unity 架构原则是一套体验供所有用户 |
| 全部搬到服务器 + 实时并发渲染 | 2 核 / 1.6 GB 扛不住 chrome + ffmpeg 并发 → 改单并发串行队列 |
| 原生壳上架 App Store | 4.2 套壳 + $99 + IAP 冲突（余额 / 兑换码）+ 健康类目 + 备案 |
| 微信小程序 | 成本高、主体与敏感信息合规难 |
| 纯局域网 HTTP PWA | iOS 下非安全上下文，SW / 离线 / 持久存储全降级；出门打不开 |
| 完全自助 PWA（用户自导数据） | 40–60 人日；iPhone 导出佳明数据很别扭 |
| 服务端代用户登录 | 同一 IP 每天替多账号登录 → 真会被平台封 |
