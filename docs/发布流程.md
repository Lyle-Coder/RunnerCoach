# 发布流程

发布仓库：`https://gitee.com/liyufei-lyle/RunnerCoach`（remote 名 `gitee`，SSH）。
`origin` 是 GitHub 镜像，只做备份，**不发 Release**。分支与合并约定见
[`协作流程.md`](协作流程.md)——发版只能从已合并的 `main` 打 tag。
发布助手是 `tools/release.py`，启动器 `release.bat` / `release.sh`，纯标准库、
零第三方依赖。除 `upload` 外全部离线；`upload` 的令牌只从 `GITEE_TOKEN`
环境变量读取，不落盘、不进产物、不进日志。

## 一、版本与 Tag 规范

- 语义化版本 `X.Y.Z`，标签统一 `vX.Y.Z`，一律用**附注标签**（`git tag -a`）。
- **Python 内核版本的唯一来源**是 `garmin_cn/__init__.py` 的 `__version__`。
  发版前先改它、提交并推送；`tag` / `upload` 都会校验 tag 与它一致，防止发错版本。
- APK 版本在 `android/app/build.gradle.kts` 的 `versionName` / `versionCode`，
  与仓库 tag **独立维护**，但 0.1.4 起两端已对齐：内核 `__version__ = 0.1.5`、
  APK `0.1.5 (code 6)`。Release Notes 会自动带上 APK 版本行，避免再次混淆。
- 同一个 tag 只发一次。`upload` 遇到同名 Release 会复用它，但**不会覆盖同名附件**：
  重传前先到网页删掉旧附件，或直接发一个新补丁版本。
- 提交信息用简短中文或英文说明「改了什么、为什么」。**不要写真实活动 ID、
  日期、GPS 坐标或健康数值**——Release Notes 由 `git log` 自动生成，
  提交信息会原样出现在公开 Release 里。

## 二、发版前检查

1. 改完代码先跑项目自检：`run.bat selftest`（POSIX `./run.sh selftest`）
   + `py -3 -m py_compile` 关键模块；改过发布脚本时再跑 `release.bat selftest`。
2. 涉及 App 接口时冒烟 `py -3 -m garmin_cn.appapi env`，并确认
   `android/sync_python.bat` 已把最新 `garmin_cn/` 同步进 APK。
3. 需要分发 APK 时先构建：`cd android && build.bat assembleRelease`，产物在
   `app/build/outputs/apk/release/app-release.apk`（debug 包同理）。
4. 提交并推送所有改动，确认 `git status` 干净、`main` 与 `gitee/main` 同步。
   发版只在 `main` 上做：`dev/<账号>` 分支的改动要先按 [`协作流程.md`](协作流程.md)
   评估并合并进 `main`，再打 tag。
5. `release.bat check`：校验分支、工作区、远端同步状态，以及版本库里
   没有敏感路径。只读、离线，不通过就直接停下来处理。
   若报「本地 HEAD 与 origin/main 不一致」（脚本按上游分支比对，这里说的是
   实际发布仓库），说明还有提交没推送：先 `git push gitee main` 再重试。

## 三、prepare：生成本地产物

```
release.bat check
release.bat prepare
```

| 产物（`dist/`，已被 `.gitignore` 排除） | 说明 |
|---|---|
| `RunnerCoach-vX.Y.Z-source.zip` | 只含 `git ls-files` 的跟踪文件，包内统一前缀；mtime 固定为 HEAD 提交时间（UTC），同一提交可复现 |
| `RunnerCoach-vX.Y.Z-debug.apk` / `-release.apk` | 在 Gradle 输出目录找到 APK 时复制重命名，没有就跳过并在 Notes 里说明 |
| `SHA256SUMS.txt` | 源码包与 APK 的 SHA256 |
| `RELEASE_NOTES-vX.Y.Z.md` | 从上一个 tag 到 HEAD 的提交列表 + 校验方式 + 版本说明草稿，发布前人工过一遍 |

打包走 `git ls-files`，天然排除所有未跟踪与被忽略的本机数据；另外还有一份
敏感路径黑名单双保险——即使 `config.json`、`data/`、`*.db`、
`tools/make_plan.py` 被误加进版本库，`check` 会直接报错而不是悄悄打包出去。

## 四、Gitee Release 上传

```
release.bat tag --push
```

令牌只在**当前终端会话**里设置，不要写进任何文件：

```powershell
$env:GITEE_TOKEN = "<Gitee 私人令牌>"    # PowerShell
```

```bat
set GITEE_TOKEN=<Gitee 私人令牌>          :: cmd
```

```bash
export GITEE_TOKEN=<Gitee 私人令牌>       # POSIX
```

先预览再上传（dry-run 不联网、不读令牌）：

```
release.bat upload --tag v0.1.5 --dry-run
release.bat upload --tag v0.1.5
```

`upload` 用标准库 `urllib` 依次做：

1. `GET /api/v5/user` 验证令牌并打印登录名；
2. `GET /repos/{owner}/{repo}/releases/tags/{tag}` 查同名 Release，没有才
   `POST /releases` 创建（`target_commitish=main`，body 是 Release Notes）；
3. 逐个 `POST /releases/{id}/attach_files`，multipart 字段 `access_token` + `file`。

前置条件：tag 已推到远端、dist 里有 prepare 产物、`GITEE_TOKEN` 是具备该仓库
权限的私人令牌（Gitee「设置 → 私人令牌」生成）。脚本对错误响应做脱敏，
不会把令牌打印出来；单个附件上限约 100 MB（APK 约 23 MB，通常不成问题），
超限会跳过并提示。

**没有令牌也能发**：`prepare` 之后到 Gitee 网页「发行版 / Releases」新建
Release，手动上传 `dist/` 里的附件，正文粘贴 `RELEASE_NOTES-*.md`。
`upload --dry-run` 就是给这条手工路径用的清单。

## 五、APK 分发

### 正式签名（1.0 起强制）

`release` 构建读 `android/local.properties` 里的四行，缺任何一项就退回 debug 签名；
**1.0 起 `release.bat check` 会在仍是 debug 签名时直接报错**，不会再让你发出去。

```properties
# android/local.properties（已在 .gitignore，不提交）
rc.storeFile=../keys/runnercoach.jks
rc.storePassword=******
rc.keyAlias=runnercoach
rc.keyPassword=******
```

- keystore 与口令**必须自己备份**（网盘 + 离线各一份）。丢了就无法给老用户发升级包——
  只能让他们卸载重装，而 App 是 `allowBackup=false`，历史会跟着没。
- 也支持 `-Prc.storePassword=...` 临时覆盖，适合 CI，不落盘。
- 证书指纹核对：`apksigner verify --print-certs app-release.apk`，
  正式包应与上一次发布的证书一致。

- APK **不进仓库**（`.gitignore` 排除 `*.apk` 与 `dist/`），只作为 Release
  附件或朋友间互传。
- 改过 `garmin_cn/` 后必须先跑 `android/sync_python.bat`，否则 APK 里还是旧内核。
- 安装前核对 SHA256；分享活动图时用内置脱敏档位（`--privacy trim|hide` 或 App 的
  出图前确认），轨迹等于精确行踪，发原图前务必自己确认一次。
- 构建与安装的完整说明见 [`android/README.md`](../android/README.md)。

## 六、校验与回滚

- 下载后校验：`sha256sum -c SHA256SUMS.txt`；Windows 用
  `Get-FileHash -Algorithm SHA256 <文件名>` 对照 `SHA256SUMS.txt`。
- 解压源码包检查：应只有代码与文档，不含 `config.json`、`data/`、`output/`、
  数据库、会话或凭据文件。
- 内容发错：在 Gitee 网页编辑 Release Notes 或删除附件；**已推送的 tag 不要
  强推覆盖**，改用新的补丁版本（如 `v0.1.1`）重新发一次。
- 误把真实数据发出去：先按 README「隐私与安全」处理，必要时改写历史并轮换凭据。

## 七、命令速查

| 命令 | 作用 | 联网 |
|---|---|---|
| `release.bat status` | 版本 / APK 版本 / 最近 tag / dist 清单 | ❌ |
| `release.bat selftest` | 发布脚本自身离线自检 | ❌ |
| `release.bat check` | 发版前置校验 | ❌ |
| `release.bat prepare` | 生成本地产物 | ❌ |
| `release.bat tag --push` | 创建并推送附注标签 | 仅推送 |
| `release.bat upload --tag vX.Y.Z --dry-run` | 预览上传计划 | ❌ |
| `release.bat upload --tag vX.Y.Z` | 创建 Release 并上传附件 | ✅ |

POSIX 把 `release.bat` 换成 `./release.sh`；也可直接
`py -3 tools/release.py <子命令>`。`tag` / `upload` 都不自动改代码或改版本号，
所有外部动作都由调用方显式触发。
