# 网页版（iPhone / 浏览器）方案

> 2026-11-23 决策：**Android 继续用 APK（本地优先），iPhone 用网页版**。
> **状态：P0 + P1 已落地**（登录、连接数据源、今日/历史/看板/计划/赛事/我的、
> PWA 壳），代码在 `server/webapp.py`、`server/web_render.py`、`server/web_sync.py`；
> 已部署到 `39.106.174.153:8443/app`，等备案通过后由 Caddy 挂到域名。
> 域名/备案见 `域名与访问.md`。

## 0. 一句话

网页版不是把 `ui.py` 的 HTML 直接挂出去：iPhone 上没有本地 Python、没有本地
佳明会话，**必须由服务器替每个用户同步和渲染**。这会改掉之前「服务端不碰密码」
的约束，是本项目最大的一次架构变化。

## 1. 现状：为什么不能直接开网页

服务端现在只有三块：

| 路径 | 内容 | 能否给 iPhone 用 |
|---|---|---|
| `/w` | 组内成员只读页（榜单、赛事、远征） | 能，但不是完整 App |
| `/manage` | 组长后台 | 能，但不是普通用户页面 |
| `/v1/*` | 给 Android App 的接口 | 能，但没有页面 |
| `garmin_cn/ui.py` | 今日/历史/计划/我的的 HTML 渲染 | **只能在有本地数据的进程里跑** |

缺的是：每用户独立数据、服务端同步、网页会话、PWA 外壳。

## 2. 关键决策：iPhone 的数据从哪来

Android 是「登录在客户端、数据在本地」；iPhone 浏览器做不到。三条路：

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A. 服务端代登录**（推荐内测） | 用户网页填佳明/高驰账密，服务器加密保存，每天串行同步 | iPhone 体验与 App 接近 | 同一 IP 多账号登录，可能触发风控；必须加密、限流、可删除 |
| B. 导入 Cookie / Token | 用户在 Safari 登录佳明后复制 Cookie 粘进来 | 不存密码 | iPhone 取 Cookie 很麻烦，几小时过期，体验差 |
| C. 只读镜像 | iPhone 只看另一台 Android/电脑上传的数据 | 最安全 | 不是独立应用，iPhone-only 用户没数据 |

**推荐 A，但必须写死几条护栏**：

1. 账密用 AES-GCM 加密，主密钥 `/etc/runnercoach/web.key`（0600，root）；
2. 只在用户点「连接数据源」时写入，页面上可一键删除；
3. 同步串行 + 每用户随机抖动，禁止并发登录；
4. 登录失败/需要验证码时停在该用户，不重试轰炸；
5. 日志不出现账密、Cookie、Token；
6. 只对朋友内测开放，注册要邀请码。

## 3. 多租户结构

```text
/opt/runnercoach/
├─ data/groups.db            # 现有：账号、组、余额
├─ users/
│  └─ <uid>/
│     ├─ data/garmin.db      # 该用户的每日/活动/体重
│     ├─ session.json        # 佳明 Cookie
│     ├─ keep_auth.json      # 可选
│     └─ web.json            # 加密后的账密（AES-GCM）
├─ web/                      # 网页版代码（新）
└─ app.py                    # 现有网关
```

**不能直接 import `garmin_cn.appapi` 多用户共用**：它用模块级 `HOME`/`DB`，
一个进程只能服务一个用户。MVP 用「每请求一个子进程」：

```text
web 请求 → 校验 cookie → 取 uid
        → subprocess: GARMIN_HOME=/opt/runnercoach/users/<uid> python web/render.py <page>
        → 返回 HTML
```

- 渲染本身毫秒级，import 约 0.2 s，几十个朋友够用；
- 同步必须走独立队列，不在请求线程里跑；
- 以后要优化再做 worker 池，不提前引入框架。

## 4. 网页路由（MVP）

| 路径 | 页面 | 说明 |
|---|---|---|
| `/app/login` | 邮箱验证码登录 | 复用 `/v1/auth`，登录后种 HttpOnly Cookie |
| `/app/connect` | 连接数据源 | 佳明用登录态导入；高驰用账密（AES-GCM）；可删除 |
| `/app` | 今日 | 复用 `ui.home_page()` 的渲染结果 |
| `/app/history` | 历史 | 复用 `history.history_page()` |
| `/app/view?date=` | 按日看板 | 复用 `history.view_page()` |
| `/app/act?aid=` | 单次活动图 | 复用 `appapi.act_card_html()`；1080 宽整页塞进 iframe，按视口等比缩放，子页 `postMessage` 回传高度 |
| `/app/basemap/<png>` | 活动图底图 | 只从该用户 `data/basemaps/` 取，文件名白名单 |
| `/app/import` | 导入佳明登录态 | 粘贴 `session.json`，写 `users/<uid>/data/session.json` |
| `/app/me` | 我的 | 数据源状态、删除数据、退出 |
| `/app/group` | 小组 | 直接跳 `/w`，不重复做 |
| `/manifest.webmanifest` | PWA | 名称、图标、standalone |
| `/sw.js` | Service Worker | 只缓存壳与静态资源，不缓存健康数据 |

底部导航：今日 / 历史 / 小组 / 我的。页面 HTML 由 Python 渲染，外层套一个
移动端壳（`<meta viewport>`、安全区、底栏），不复用 Android 的 `data-act` 桥。

## 5. 同步队列

```text
web_sync_jobs(id, uid, source, status, created, started, finished, error)
```

- 用户点「同步」→ 插 pending；后台 worker 每 30 秒抢一条；
- 同一 uid 同时只跑一条（行锁 `BEGIN IMMEDIATE`）；
- 全局同时只跑 1–2 条，避开佳明风控和 1.6G 内存；
- 每天最多自动同步 1 次，随机延迟 0–6 小时；
- 失败分类：`need_login`（要验证码/密码错）→ 页面提示；网络错误 → 退避重试。

## 6. 分期

| 期 | 内容 | 验收 |
|---|---|---|
| **P0** | 多租户目录、加密账密、登录 Cookie、连接数据源页 | 能登录、能保存/删除账密，密码不出现在日志 |
| **P1** | 服务端同步佳明 + 今日/历史/看板渲染、PWA 壳 | iPhone Safari 能看自己的今日与历史 |
| **P2** | 计划、活动图、AI 对话、我的页完整化 | 与 Android 功能对齐 80% |
| **P3** | 高驰/Keep、小组互动、推送 | 朋友日常可用 |

## 7. 风险与边界

- **佳明风控**：同一服务器 IP 给多个账号登录，和 Android 本地登录不同。
  必须串行、抖动、失败即停；朋友规模控制在个位数到十几人。
- **合规**：账密与健康数据都在服务器，隐私说明要重写；必须能删除账号与数据。
- **容量**：2 核 1.6G 无 swap；同步是网络等待，渲染是毫秒级；视频/长图仍串行。
- **不做**：不在网页端做视频渲染、不做实时多人并发、不把 `/manage` 暴露给普通用户。

## 8. 已确认与实现

4. **未验证**：真实佳明账号的服务端登录/同步（需要一台真机 + 朋友账号试）；

## 9. 佳明登录改版（2026-11-23，改变了同步的前提）

佳明把国区 Web 登录从 `/sso/login` 迁到 SSO Portal（Vue SPA）。两个后果：

1. **老票据作废**。`POST sso.garmin.cn/mobile/api/login` 仍返回 SUCCESSFUL 和
   `serviceTicketId`，但那张票在 `connect.garmin.cn/app?ticket=` 换不出
   `JWT_WEB`，服务端反而 `Set-Cookie: JWT_WEB=; Max-Age=0` 清空会话。
   表现就是「账号密码明明对，一直提示登录失效」。现在走：
   - `POST https://sso.garmin.cn/portal/api/login?clientId=GarminConnect&service=<connect>/app`
   - 之前必须先打开 `/portal/sso/zh-CN/sign-in?...`（用桌面 Chrome UA），
     否则 400 `Previous captcha evaluation is mandatory`。

2. **机房 IP 过不去**。阿里云这台访问 `sso.garmin.cn/portal/*` 一律
   403 + `cf-mitigated: challenge`（Cloudflare 人机挑战，HTML 和 API 都挡）。
   也就是说**服务器无法代登录佳明**；而 `connect.garmin.cn/gc-api` 不受影响，
   只要有一份有效 `JWT_WEB` 就能正常同步（实测导入后 60 条活动 / 30 天日报）。

### 现在的登录态怎么来

| 来源 | 路径 | 说明 |
|---|---|---|
| 安卓 App | 同步成功后自动 `POST /v1/web/session` | 纯 Python（`garmin_cn/websession.py`），代码包即可，不用重打 APK；同一份会话 3 小时内不重传 |
| 桌面浏览器 | 「连接数据源」页粘贴 `session.json` | 手动兜底 |
| 境外中转 | `RC_LOGIN_RELAY` + `deploy/cf-login-relay.js` | Cloudflare Worker 代过挑战，只把 Cookie 交回服务器；iPhone-only 用户靠这条 |

服务器侧落在 `users/<uid>/data/session.json`（0600），`web_sync.py` 在没有账密
时也能靠它同步；过期后同步任务会提示「用安卓 App 同步一次」。

**取舍**：登录态由设备生产，服务器只借用——少存一份密码，但网页版需要
设备先登录一次。iPhone-only 用户靠第 10 节的中转机解决。

## 10. 登录中转：多台设备 + 无感静默（2026-11-23）

服务端 `relay_jobs` 队列 + `/v1/relay/pull`、`/v1/relay/push`：服务器把
「用某个用户的佳明账号登一次」排成任务，中转设备来领、登录、交回 Cookie。

### 多台

`RC_RELAY_USER` 支持多个邮箱，逗号/分号/空格分隔：

```ini
RC_RELAY_USER=yufei.lyle@qq.com,friend-with-android@example.com
```

- **谁能领**：这些账号名下的设备。空 = 中转功能完全关闭。
- **怎么分**：谁先来领谁拿。`UPDATE ... AND status='pending'` 的 rowcount
  做乐观锁，两台机同时到只有一个成功，不会重复登录同一个账号。
- **为什么要多台**：国产 ROM 会冻结后台任务，一台手机歇了另一台能接上。

### 无感静默（用户视角）

页面上**只有两样东西**：正文 + 一行「数据更新于 12:30」。没有「同步排队中」、
没有「正在同步」、没有「上次同步失败」。状态分三类，只有一类会打扰人：

| 后台状态 | 含义 | 用户看到 |
|---|---|---|
| `pending` / `running` | 正在同步 | 什么都不显示 |
| `done` | 同步完成 | 只有「数据更新于」的时间变了 |
| `wait` | 失败了但**能自愈**（网络、DNS、佳明 5xx、超时、登录态过期等中转） | 什么都不显示，后台按 30 分钟退避重试 |
| `error` | **必须本人动手**（密码错、要验证码、账号异常、没存账密） | 一条横幅 + 「去重新连接」 |

中转任务同样分两类：`_relay_fatal()` 命中密码/验证码/锁定这类关键词才落到
`error` 并回调 `_flag_action()` 把话挂到页面上；其余记 `wait`，静默重试。

页面自动刷新：`_sync_on_load()` 在 `pending`/`running`/`wait` 时每 25 秒
换一次页，带 `_w` 计数、最多 4 次（约 2 分钟）——用户开着页面等就能等到，
但不会无限轮询。

### 预热（配合中转，见 8.x）

`preheat_tick()` 在会话剩余 < 40 分钟时提前排任务，所以白天打开网页通常
几秒就能同步完。三条护栏：只服务 24 小时内打开过网页的人、只在 07:00–23:00、
手机 App 6 小时内推过会话就让路（避免和 App 互踢会话）。
