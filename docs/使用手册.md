# 佳明国区 → 每日看板 / 电子教练

把 Garmin Connect 中国区（connect.garmin.cn）的数据拉到本地，生成每日看板，
并让 WorkBuddy 基于真实数据写教练点评。

- 纯标准库实现，**不需要安装任何第三方包**
- 数据只落在本机 `data/`，不上传任何地方
- 国区账号专用（国际区账号不适用这套接口）

## 目录

## 三步跑起来

> **Windows 上建议一律用 `run.bat`**：部分机器 PATH 里有 Microsoft Store 的
> 0 字节 `python.exe` 占位符，执行它没有任何输出、直接返回退出码 9009，
> 看起来像「没反应」。`run.bat` 会自动挑一个真正可用的解释器。

```bat
cd /d <项目目录>

rem 0) 先体检，确认解释器和网络都通
run.bat doctor

rem 1) 登录（提示输入邮箱+密码，可能需要邮箱验证码）
run.bat login

rem 2) 同步最近 30 天
run.bat sync --days 30

rem 3) 生成看板
run.bat report --open
```

不想交互输密码，可以一次性传参：`run.bat login --email 你的邮箱 --password 你的密码`。

看板输出在 `output/dashboard-<日期>.html`，同时有一份 `output/latest.html`。

不想用真实账号先看效果：`run.bat demo --open`（60 天仿真数据）。
也可以直接双击 `login.bat` / `daily.bat`。

## 登录失败怎么办

国区这条链路的实际机制（都是实测出来的，不是猜的）：

```
POST sso.garmin.cn/mobile/api/login          → serviceTicketId
GET  connect.garmin.cn/app/?ticket=…         → 下发 JWT_WEB + session 两个 Cookie
GET  connect.garmin.cn/app/                  → 页面 <meta name="csrf-token"> 里取令牌
GET  connect.garmin.cn/gc-api/…              → Cookie + Connect-Csrf-Token 头，缺一不可
```

三个容易踩的坑，对照着看：

| 现象 | 原因 |
|---|---|
| `403` 且 body 长度 0 | 缺 `Sec-Fetch-Site: same-origin`（被网关挡在会话校验之前），或缺少 CSRF 令牌 |
| `401` 且 body 长度 0 | 网关头对了，但会话无效 / 只有 `JWT_WEB` 没有 `session` Cookie |
| `200` | 正常，返回 JSON |

`run.bat debug-login` 会打印每一步的状态码和 Cookie 名（不含密码），对不上时先跑它。
CSRF 令牌会随会话轮换，代码里遇到空 403 会自动重新取一次再重试。

其它情况：

1. **密码不对**：国区必须用注册邮箱，不能用手机号。
2. **要求图形验证码**：先在浏览器登录一次 `https://connect.garmin.cn`，完成设备验证后再试。
3. **`sso.garmin.cn/sso/login` 返回 500**：国区 Web 表单登录已废弃，属正常，走的就是移动端 API。
4. **实在搞不定**：改用 Cookie 导入。浏览器登录国区 Connect → F12 → Network →
   任一 `gc-api` 请求 → 复制整条 `Cookie`（要含 `JWT_WEB` 和 `session`）：

   ```bat
   run.bat import-cookies --cookie "JWT_WEB=...; GARMIN-SSO=...; ..."
   ```

会话保存在 `data/session.json`，**它等同密码**，不要提交到 git、不要发给别人。
过期后重新 `login` 即可。

## 用法

| 命令 | 作用 |
|---|---|
| `run.bat doctor` | 环境自检：解释器、模块、数据库、网络 |
| `run.bat status` | 看登录状态、数据范围、上次同步时间 |
| `run.bat sync --days 30` | 同步最近 30 天（顺带给新跑步活动出图；`--no-cards` 跳过出图，`--no-body` 跳过体重） |
| `run.bat sync --days 30 --force` | 整段重拉。默认是**增量**：已过完且拉过的日子直接跳过，日常刷新只请求今天/昨天 |
| `run.bat sync --days 7 --extras` | 额外拉压力/身体电量明细（更慢） |
| `run.bat report --date YYYY-MM-DD --open` | 指定日期出看板 |
| `run.bat card` | 生成竖版一图流 PNG（日看板） |
| `run.bat act --date YYYY-MM-DD --card` | 单次活动明细 + 活动图（轨迹/分区/分圈） |
| `run.bat act --card --privacy trim\|hide` | 出**脱敏版**活动图：首尾各裁 200 m / 完全隐藏轨迹 |
| `run.bat act --id <activity_id> --force` | 按活动 ID 抓取，`--force` 忽略缓存 |
| `run.bat brief` | 最近一次跑步的简报（纯文本，可直接发微信） |
| `run.bat serve --lan` | 手机看板：把 `output/` 只读挂到局域网，打印带访问码的地址 |
| `run.bat brief --last 3` | 最近三次活动的简报，一次问一批 |
| `run.bat watch --hours 3` | 有新跑完的活动就出简报；已推过的不会重复（定时任务用） |
| `run.bat body` | 体重/体成分趋势与结论（缺数据时提示怎么导） |
| `run.bat body --import 小米.csv` | 导入小米运动健康「数据副本」导出或 Zepp Life 导出 |
| `run.bat body --garmin` | 把佳明里的 weigh-in 拉进本地表（含历史手动录入） |
| `run.bat mi login` | 登录小米账号（体脂秤数据源，只存 passToken 不存密码） |
| `run.bat mi status` / `mi probe` | 体检凭据、看云端记录数与最近一次读数（`probe` 附带原始字段） |
| `run.bat body --mi` | 从小米健康云拉最近 120 天体重/体成分入库（`--mi-days` 改范围） |
| `run.bat nutri` | 今天吃多少：热量与三大营养素目标（`--goal cut/maintain/gain` 切换并保存） |
| `run.bat backfill` | 批量补齐历史活动明细（步频修正 + 轨迹 + 天气） |
| `run.bat backfill --force` | 重算全部历史明细（改过修正规则后用） |
| `run.bat coach` | 打印教练上下文（Markdown，给模型看的） |
| `run.bat note --file 点评.txt` | 把教练点评写进当天，看板会渲染 |
| `run.bat debug-login` | 登录诊断（每步 HTTP 状态 + Cookie 名） |
| `run.bat selftest` | 离线自检（不联网） |
| `run.bat demo --open` | 仿真数据预览看板 |

每天自动跑：双击 `daily.bat`，或用 Windows 任务计划程序指向它。
它做三件事：`sync --days 3`（佳明数据 + 顺手拉小米秤的体重/体成分）→ `report`（网页看板）
→ `card`（竖版一图流 PNG）。体重那一步失败只提示一行，不影响看板生成。
看板和一图流都会带上当天算好的「今日营养」（热量 + 蛋白/碳水/脂肪）。

`JWT_WEB` 只有 2 小时有效期，所以 `sync` 遇到会话过期会用 `config.json` 里保存的
账号密码自动续期一次；需要邮箱验证码时会提示你手动 `login`。

## 手机上怎么看（不用装 App）

看板本身就是自包含 HTML（0 个外部请求），差的只是"怎么递到手机上"。

```bat
run.bat serve            :: 只给本机看：http://127.0.0.1:8765/
run.bat serve --lan      :: 手机同 WiFi 看：打印 http://192.168.x.x:8765/?k=xxxxx
run.bat serve --lan --port 8800 --open
```

手机打开那串**完整地址**（带 `?k=`），进去是一页按「今日 / 看板 / 图 / 活动 / 计划」
分组的列表，点开就是完整看板，可以直接在手机浏览器里左右滑动看。

几条刻意的设计：

- **只读**：服务只读 `output/` 下的已生成文件，没有任何写入口，同步还得回电脑上跑。
- **默认只听 127.0.0.1**：`--lan` 才绑 `0.0.0.0`，且自动生成访问码；
  访问码用 cookie 记住，地址栏里的 `?k=` 会立刻 302 掉，截图/投屏不会把令牌带走。
- **同一 WiFi ≠ 可信网络**（宿舍、共享办公、咖啡馆）：看完关掉窗口即失效。
- 一图流 `card-*.html` 加了 `width=1080` 视口声明，手机打开会整张缩放贴合屏幕，
  不出 PNG 也能看、能截图。

更彻底的做法（手机自己跑同步、家里常开设备当中枢、纯前端 PWA）
见 `docs/交付形态调研.md` 第九节。

## 在手机上跑（安卓 + Termux，不用电脑）

**iPhone 不行**：iOS 上没有能常驻的 Python 运行时，只能让别的设备跑完把结果递过来。
安卓可以整机跑完同步、分析、出看板，数据一直在手机里。

### 三步装好

```bash
# 1) 从应用商店装 Termux（F-Droid 版；Play 商店版已停止更新）
# 2) 把项目文件夹拷进 Termux 家目录（数据线 / 微信文件 / git 都行），然后：
cd ~/garmin-coach
bash setup-termux.sh
```

`setup-termux.sh` 只做四件事：装 `python`（必需）、装 `ffmpeg`（可选，只影响 MP4）、
装 `termux-api`（可选，唤醒锁）、把 `run.sh` 加执行权限并生成桌面快捷方式。
它不碰数据、不问账号。

之后所有命令把 `run.bat` 换成 `./run.sh` 即可（脚本会顺手写两个 alias，
所以照着提示敲 `run.bat sync` 也能跑）：

```bash
./run.sh doctor            # 体检
./run.sh login             # 登录佳明（邮箱 + 密码 + 验证码）
./run.sh sync --days 30    # 拉数据
./run.sh report            # 出看板
./run.sh serve             # 手机浏览器打开 http://127.0.0.1:8765
```

### 能力边界（和 Windows 版不一样的地方）

| 功能 | Termux | 原因 / 替代 |
|---|---|---|
| 同步 / 指标 / 看板 / 简报 / 营养 | ✅ 完整 | — |
| 一图流 | ⚠️ 只出 HTML | 没有无头 Chromium；`card-*.html` 已加 `width=1080` 视口，手机打开整张缩放，长按存图 |
| 单次活动图 | ⚠️ 只出 HTML | 同上 |
| 轨迹回放（网页） | ✅ 完整 | 本来就是 canvas 页面 |
| 轨迹回放导 MP4 | ❌ | 需要 `ffmpeg` + 逐帧无头截图，第二项没有 |
| 照片归组 / EXIF 匹配 | ✅ | 纯 Python |

> 上面说的是 Termux 版。**APK 版没有无头浏览器的限制**：一图流和单次活动图
> 都由 WebView 截成 PNG 存相册，成品统一 1080×1920（9:16），可直接分享。
> 0.1.5 修好了「分享预览只剩放大一角」：HTML 的布局视口写死 1080 CSS px，
> 而 WebView 控件只有 1080 物理像素，页面会按屏幕密度被放大到画布外。现在
> 探针读 `visualViewport.width`，App 给版心套 `transform: scale(f)` 后再截，
> 并留一圈同色安全带防分享面板 centerCrop。相册里的原图始终是完整的。
> **0.1.4 起点活动出图会先弹「分享前脱敏」**：原图 / 裁首尾各 200 m（默认）/
> 完全隐藏轨迹。脱敏在生成 HTML 前完成，图片和 `output/*.html` 里都不留原始折线、
> 底图或精确起跑时间；桌面用 `act --card --privacy trim|hide`。
> 见 `docs/APP方案.md`。

`doctor` 会把「无头浏览器 没找到」单独列一行——**这是预期，不是故障**。
想跳过截图排查慢在哪里，可以 `GARMIN_NO_BROWSER=1 ./run.sh card`。

### 安卓特有的两个坑

1. **后台被杀**：设置 → 应用 → Termux → 电池 → 选「不受限制」；通知栏的常驻通知别划掉。
2. **长同步被挂起**：`daily.sh` 会先 `termux-wake-lock`（装了 Termux:API 才生效）。

### 每天自动跑

装 **Termux:Widget** 后，长按桌面 → 小部件 → Termux，会看到 `setup-termux.sh` 写好的
「每日同步」「手机看板」两个图标，点一下就是 `daily.sh` / `serve`。
想用系统级定时，再上 `termux-job-scheduler`（需要 Termux:API）。

### 隐私

数据全在 Termux 的私有目录（`~/garmin-coach/data/`），不进共享存储、不需要存储权限，
卸载 Termux 就一起没了。`serve` 默认只监听 `127.0.0.1`，不给 `--lan` 的话
同一 WiFi 的别人也连不上。

### APK 版本

`android/` 是「Python 内核 + WebView 壳」：APK 里跑的还是这份 `garmin_cn/`，
界面是指向本机只读服务的 WebView，密码存在 Android Keystore。已经能一键构建，
成品在 `dist/garmin-coach-0.1.5-debug.apk`（朋友之间互传安装即可）。

相比 Termux 版，APK 版用 WebView 自己截图，**一图流和活动图都能导出 PNG 并分享**；
看板里的活动行点一下就出该活动的图。**同步不设按钮：页面顶部下拉即可**，
剩下的导出项收在顶部 ⋮ 菜单里，界面上没有覆盖内容的操作层。
取舍与代价见 `docs/APP方案.md`，构建与交互细节见 `android/README.md`。

两者不冲突：Termux 版给愿意折腾的人，APK 给不想碰命令行的人。

## 跑完自动提醒（微信）

`brief` 和 `watch` 只负责**把活动压成一段能直接发出去的话**，不含任何推送凭证、
不联网发消息；发到哪儿由调用方决定（微信助理、企业微信 bot、Server酱 都吃纯文本）。

```text
11-01 周日 中午跑 · 陕西·西安
10.01 km ｜ 47:34 ｜ 4'45"/km
心率 174 ｜ 步频 190 ｜ 步幅 111
爬升 14 m ｜ 主要益处 乳酸阈值 ｜ 有氧 4.1 / 无氧 0.1
后半程快了 6″，状态不错
13℃ 湿度 77% 多云
```

排版上刻意不用 markdown：微信聊天窗口不渲染 `#`、`**`、`|`，表格会退化成一行挤在
一起的符号。这里只用全角竖线和换行，粘到任何聊天框都不变形。

**结论不是罗列出来的，是算出来的。** `verdict()` 比对前后半程：

| 现象 | 输出 |
|---|---|
| 掉速 > 2% 且心率升 ≥ 4 | 后半程掉速 N″、心率还升了 M，起步偏快或耐力吃紧 |
| 掉速 > 2%，心率没升 | 后半程掉速 N″，起步可以再稳一点 |
| 快 > 2% 且心率不漂 | 后半程快了 N″、心率没漂，状态不错 |
| 两者都在 2% 内 | 上下半程几乎同速，节奏很稳 |
| 没有前后半程（单圈/短距离） | 退回分圈配速的离散度（CV < 3% 算稳） |

两条阈值都取 2%，是因为 GPS 抖动与配速换算本身就有这个量级的噪声，再严就会
把「正常起伏」报成「掉速」。

**幂等**：`watch` 把推过的活动记在 `meta` 表的 `pushed:<活动ID>` 上，所以它可以每
10 分钟跑一次而不刷屏；`--dry-run` 只看不写标记。

定时任务的三种落点，能力边界不一样：

| 通道 | 能否主动推 | 注意 |
|---|---|---|
| WorkBuddy 微信助理（Clawbot） | 任务完成有通知 | **48 小时要在微信里互动一次**，否则断连；断连后任务照跑但你收不到 |
| 企业微信机器人 | 可以 | 在定时任务编辑窗口左下角打开「消息推送到企业微信」；用的是助理已绑定的 bot |
| Server酱 / PushPlus | 可以 | 第三方，免费额度 5 条/天（PushPlus 200 条，需实名），只推文字+链接，图片要公网地址 |

活动图含 GPS 轨迹，属于个人位置信息，**不上传到任何第三方图床**；需要在微信里看图，
走「微信里问一句」的路径（`brief` 会把图片路径一并返回，由助理把本地文件附上）。
要直接发图，先用 `--privacy trim`（首尾各裁 200 m）或 `--privacy hide`（连折线形状
都不出现）；App 里出图前会自动问一次档位。产物文件名带 `-trim` / `-hide` 后缀，
不会和原图互相覆盖。

## 体重与体成分（小米秤 ms116）

佳明里只有手动录入的体重（`bodyFat/bodyWater/muscleMass` 全 null），小米秤的数据
不会自动过去。所以体成分单独存 `body` 表，允许一天多次称重，来源只记在 `source` 里。

ms116（米家体脂秤 S400）本身不存历史——秤只做蓝牙广播，App 连上才把结果算出来传云。
所以历史只存在于小米健康云，三条取数路线：

| 路线 | 做法 | 代价 |
|---|---|---|
| **云端逆向**（已实现） | `run.bat mi login` 一次 → `run.bat body --mi` 增量拉 | 小米改协议就会断，但日常零操作 |
| 官方数据副本 | 隐私中心申请「数据副本」→ 邮件给下载链接 → `run.bat body --import 文件` | 要等邮件、只到申请日为止；接口稳，适合当兜底 |
| 蓝牙直读 | 本机 BLE 监听秤广播（0x181D / 0x181B） | 电脑得常开在秤旁边，8 电极的体脂还得 App 算 |

### 数据怎么进看板

体成分不是只在 `run.bat body` 里看一眼，两个看板出口都会带上：

- **网页看板**（`report`）：6 项指标下面是独立的「身体成分」三栏 —— 体重曲线（7 天均值
  变化 + 4 周变化 + 趋势线）、体成分 8 格（体脂率 / 脂肪量 / 肌肉量 / 瘦体重 / 水分率 /
  内脏脂肪 / 基础代谢 / BMI）、以及「体重 × 负荷」的联合判断。
- **一图流**（`card`）：ACWR / CTL / ATL / TSB 下面固定一行四格 —— 体重（带 7 天变化）、
  体脂、肌肉、水分。位置每天一致，才看得出「掉的是水还是脂肪」。

自动更新有两条：

1. `sync` 结束时会顺手跑一次小米云增量（等价于 `body --mi`，默认 30 天窗口；`--no-body`
   可关掉）。没登录或云端没数据只提示一行，不影响佳明数据入库。
2. 入库后按日把均值回填进 `daily` 表的 `weight_kg / body_fat_pct / muscle_kg / water_pct`
   四列，教练上下文、MCP、活动分析、看板读的都是同一份口径。

同一天既有秤的读数、又有佳明里的手动录入时，**只认秤的那条**（`body._prefer`）：混着取
均值会把趋势抹平，也说不清权重。秤优先，其次导入的 CSV，最后才是佳明手动录入。

### 云端逆向怎么用

```bat
run.bat mi login        :: 账号 + 密码（只留 passToken，不落密码）
run.bat mi status       :: 凭据能不能用、云端有多少条、最近一次读数
run.bat body --mi       :: 拉最近 120 天入库（--mi-days 改范围）
```

凭据写在 `data/mi_auth.json`（600 权限，`data/` 已在 `.gitignore` 里），只存
`userId / passToken / ssecurity / 会话 Cookie`，密码用完即弃。

**关于 Cookie：`serviceToken` 是按服务发的。** 从 `i.mi.com` 抄来的 `serviceToken`
只对 `i.mi.com` 有效，拿去换 `miothealth` 的票会被 `70016` 挡回来（表现在「有
`location`，但没有 `ssecurity`——未登录时它也照样给 `location`，所以 `location`
不能当成功标志）。

**`ssecurity` 不一定在 JSON 里。** 小米把它放在跳转响应的
`extension-pragma: {"ssecurity": "..."}` 头里，浏览器一跳转就消费掉了，只抓 body
的实现永远拿不到。代码现在会逐跳读这个头。

三条导入路线，按省事排序：

| 路线 | 做法 | 备注 |
|---|---|---|
| 账号密码（已打通） | `run.bat mi login` | 新设备会被要求**短信验证**，程序会把图形验证码弹出来让你认字，再收短信码，全程在终端走完 |
| 整串 Cookie | 浏览器登录后复制 `Cookie:` 整行 → `run.bat mi login --cookie-file mi_cookie.txt` | 登录过之后 Cookie 里才会有 `passToken` |
| 响应头 / JSON | F12 → Network → 过滤 `serviceLoginAuth2` → 点最后一条 → Response Headers 整段复制存文件 | 兜底路线，`ssecurity` 一定在里面 |

```bat
run.bat mi login --json-file mi_login.txt   :: 响应头整段或 serviceLogin 的 JSON 都吃
run.bat mi status
```

### 新设备登录：短信安全验证怎么自动走完

小米对「新设备 / 异地」的密码登录不弹「手机点确认」，而是返回
`securityStatus: 16` + 一个 `notificationUrl`，页面里只有**短信验证码**一条路
（`options=[4]`）。这段已经完全 API 化，`run.bat mi login` 会自己走：

```
GET  /identity/list?context=…                     ← 拿 identity_session + applyToken
GET  /pass/getCode?icodeType=login                ← 图形验证码（JPEG，存 data/captcha.jpg 并自动打开）
POST /identity/auth/sendPhoneTicket  {icode, ick} ← 认字对了才发短信
POST /identity/auth/verifyPhone      {ticket}     ← 短信码；成功返回 location
GET  <location>                                   ← 换到健康服务会话
```

几个容易踩空的点：`/identity/list` 必须带 `X-Requested-With: XMLHttpRequest`，
否则返回的是前端页面外壳而不是 JSON；图形验证码要连同 `ick` Cookie 一起回传；
验证后那一跳只种健康服务会话、**没有** `serviceToken`，所以跟跳时不能强求它。

**`verifyPhone` 成功后拿不到 `ssecurity` 是常态**——那一跳只给落地 `location`，
密钥在 `serviceLoginAuth2` 的跳转响应头里（`extension-pragma`）。所以验证一通过，
程序会**用同一账号自动再提交一次 `auth2`**（带上 `identity_session` / `deviceId`），
这一次设备已被信任，`extension-pragma` 就带上了 `ssecurity`，全程不需要你再动手。
账号密码只在内存里留到这一步，`save()` 时不会写进文件。

图形验证码没认对不会发短信，直接回车就换一张，最多三轮。短信码输错（`10001` /
`87001`）可以重试三次；但**验证通过后换不到密钥不会让你重输短信码**——码是一次性的，
那种情况直接换路径。
走完之后 `passToken`（或会话）落在 `data/mi_auth.json`，以后 `body --mi` 不再需要验证。


导入器会按顺序找 `ssecurity`：JSON 字段 → `extension-pragma` 头 → 裸文本里的
`ssecurity:` 行；找到后再用 `location`/`ticket` 换 `serviceToken`。没有 `ssecurity`
时会明确说「拿到的是已登录但没给 ssecurity」，并给出下一步，不会静默失败。

已有一份能用于 `miothealth` 的整串 Cookie 时，也可以 `--cookie` / `--cookie-file`
直接导入（会存整串，不再要求 `passToken`）。
Cookie 会话比 `passToken` 短命，失效时 `mi status` 会明说，重抄一次即可。

**协议要点**（以后断了先看这里）：`POST https://hlth.io.mi.com/app/v1/data/get_fitness_data_by_time`，
业务参数整个塞进 `data`（JSON 字符串），外面套一层 RC4（**丢弃前 1024 字节密钥流**）
+ 双签名：明文的 `data` 先算 `rc4_hash__`，再把 `data`/`rc4_hash__` 各自加密、用密文
算 `signature`，`_nonce` 随请求带上；`sn = sha256(ssecurity + nonce)`，`ssecurity` 来自登录跳转的
`extension-pragma` 头。响应也是 base64 + RC4。登录走 `account.xiaomi.com/pass/serviceLoginAuth2`，
`sid=miothealth`。实现在 `garmin_cn/mi.py`，`run.bat selftest` 会对签名与解析做离线校验。

**单位坑**：云端给的是 `body_fat_rate / muscle_rate / moisture_rate` 三个**百分比**，
不是 kg。肌肉量按 `体重 × 肌肉率%` 换算——有些开源实现直接把 `muscle_rate` 当
`muscle_mass_kg`，只有少数机型碰巧对得上。

**取不到数据时先分清两种失败**，`run.bat mi status` 现在会直接用步数当对照：

- **有步数、没体重** → 账号、会话、签名全都是好的，问题在数据源：秤没绑在
  「小米运动健康」。三种情况：绑在「米家」（数据在米家云，两朵云不互通）、
  用的是 Zepp Life（另一套云）、绑的是家里人的账号。去 App 里把秤重绑一次，
  称完并打开 App 让它上传。
- **连步数都没有** → 登的不是称重那个小米账号，换账号重登。

`run.bat mi probe` 会额外打印云端原始字段与近 30 天步数条数，一眼看出是哪一种。
米家云（`api.io.mi.com`）用同一个 `passToken` 能换到它自己的 `ssecurity`
与 `serviceToken`，但设备列表接口另外算签名，当前版本没有接入。

导入仍支持中英文表头（`测量时间/体重(kg)/体脂率/肌肉量/水分率/内脏脂肪/基础代谢`，或
`Date/Weight/Body Fat/Muscle Mass`），重量 >300 自动按克处理；表头别名见
`garmin_cn/body.py` 的 `ALIASES`。CSV 与 JSON 都吃。

判断只在趋势上做，且要和负荷一起看：`体重在掉 + CTL 在涨` 是能量摄入不足（RED-S）
最早的信号；单日掉超过 0.8 kg 但 7 天均值没动，判成脱水和不吃进结论。体脂是 BIA
估算，跨度不到 14 天、变化不到 1 pt 不写进结论。

## 今天吃多少（营养建议）

看板原来只回答「今天怎么练」，吃多少全靠自己估。加上体重和体成分之后，这两件事
必须一起看——减脂期真正容易出错的不是赤字本身，而是**赤字里掉的是脂肪还是肌肉**。

```bat
run.bat nutri                    :: 今天的热量与三大营养素目标
run.bat nutri --goal maintain    :: 切成维持体重（写进 config.json，看板跟着变）
run.bat nutri --goal gain        :: 增重
```

算出来的东西同时出现在三处，数字同源（`nutrition.targets()`，看板 / 一图流 /
教练上下文 / MCP 都读它）：

- **网页看板**：「今日营养」三栏 —— 目标摄入与依据、三大营养素配比条、今天怎么吃
- **一图流**：今日处方下方一行 `吃 1879 kcal · 蛋白 118 g · 碳水 248 g · 脂肪 46 g`
- **教练上下文 / MCP**：`## 营养参考` 段，模型写点评时直接引用，不用自己乘系数

### 口径

| 项 | 算法 | 为什么 |
|---|---|---|
| 消耗基线 | 近 7 天 `totalKilocalories` 均值（**不含当天**） | 当天往往只过了一半，混进均值会把目标压低 |
| 缺口 | 减脂 400 kcal、维持 0、增重 −250（盈余） | ≈0.35 kg/周，比「一周掉 1 kg」更可持续 |
| 目标摄入 | 消耗基线 − 缺口，**不低于 BMR** | 长期吃不到 BMR 先掉的是肌肉和恢复能力 |
| 蛋白 | 1.8 g/kg（掉肌肉时 2.0） | 减脂期保肌肉的关键项，优先级高于总热量 |
| 碳水 | 4.5 g/kg 起，按近 4 周日均训练时长分 3.5 / 4.5 / 5.5 / 6.5 档 | 休息日和长距离日不该吃一样多 |
| 脂肪 | 剩余热量，下限取「0.6 g/kg」与「总热量 22%」的较大值 | 为了凑热量把脂肪压到 20 g 以内，掉的是激素水平 |

碳水档位用**近 4 周**而不是近 7 天：只看 7 天会被恢复周骗到（一天没练就掉到 3.5 g/kg）；
本周日均超过 4 周基线的 1.5 倍时才算真的加量，改用本周数据。

### 速率校准

目标按 −0.5% 体重/周换算。实际比目标快 0.25 kg 以上时提示，
但有一条前置判断：**如果 4 周累计几乎没动（<0.5 kg），这一周的跌幅判为水分波动，
不给「再加缺口」的建议**——和 `body.verdict()` 是同一条原则。今天的实例：

```
单周降幅明显，但 31 天累计几乎没动：属于水分波动，别为了数字再减饭
```

### 已知限制

- **不记录饮食**：只给目标值，没有食物库、不算每一餐。真要做成记账软件，数据量和
  使用成本都会劝退，而且记不准的记录比不记更误导。
- 体脂/肌肉来自 BIA，绝对误差 ±3~5 pt；蛋白提到 2.0 g/kg 只看「肌肉 14 天掉 ≥0.4 kg」。
- 消耗基线依赖 Garmin 的日汇总；库里不足 3 天完整记录时按 `BMR × 1.4` 估算，并在
  建议里标明「是估算值」。

## 跑完步：把素材丢进去，一键出片

```bat
:: 照片、视频、动态照片直接放进这个目录——微信、飞书、数据线、AirDrop 都行
data/inbox/

run.bat ingest              :: 自动认出是哪次跑步 → 出片
run.bat ingest --dry-run    :: 只看归组结果，不动文件
run.bat ingest --duration 30 --mute
```

不用先告诉它这是哪个活动：按文件的**拍摄时间**去找前后 6 小时内的活动，
跑步一般一小时以内，时间就够定位了。同一天跑两次也能分开（取开跑时刻最近的）。

- 时间读的是文件自身（照片 EXIF、视频 `mvhd`）；读不到才退回文件修改时间，并在输出里标出来。
- 视频的 `mvhd` 差整 8 小时（相机把本地时间当 UTC）会按活动窗口自动纠回来。
- 归好组就复制进 `data/photos/<活动ID>/`，然后逐个出片。重复文件按大小跳过，可以反复跑。

## 动态轨迹回放（motion）

把一次跑步渲染成 1080×1920 的竖版回放：轨迹逐段生长、左上角实时里程/配速/心率/用时，
跑到拍照地点时镜头推近、照片弹出放大。

```bat
run.bat motion --date YYYY-MM-DD        :: 选当天最长的一次
run.bat motion --id <activity_id>           :: 指定活动
run.bat motion --id <activity_id> --mp4     :: 同时导出 MP4（需要 ffmpeg）
run.bat motion --id <activity_id> --mp4 --keep-frames   :: 保留逐帧图片
run.bat photo --id <activity_id>            :: 先检查照片有没有 GPS
```

产物在 `output/motion-<日期>-<活动ID>.html`，双击即可播放（空格暂停、←/→ 跳 2 秒）。

### 数据从哪来

| 需要什么 | 来源 | 说明 |
|---|---|---|
| 轨迹几何 + 时间戳 | `/details` 的 `geoPolylineDTO.polyline` | 每点带 time(ms)/speed，实测与 1Hz 序列逐点对齐 |
| 心率 / 配速 / 里程 | 同一次响应的 1Hz 指标 | `directHeartRate`、`directSpeed`、`sumDistance` |
| 底图 | 高德静态图（`basemap`） | 540×960 @ scale=2，拿回正好 1080×1920 |
| 照片位置 | 照片 EXIF 的 GPS | WGS-84，投图前统一转 GCJ-02 |

`route.py` 把前两者合成一条 `{t, lat, lon, d, hr, v, seg}`。**旧活动的明细里没有这条
时间轴**（早期版本只存了 lat/lon，把 time 丢了），第一次跑 `motion` 会自动重抓一次。

### 照片怎么放

```
data/photos/<活动ID>/IMG_xxx.jpg
```

必须是**原图**：微信/QQ 转发会抹掉 EXIF，小米云要选「下载原图」。
先跑 `run.bat photo --id <活动ID>` 自检，输出会直接告诉你每张有没有 GPS、能不能挂上轨迹。

匹配规则：

1. **拍摄时间**落在活动时段内（前 5 分钟到结束后 15 分钟的余量）
2. **有坐标时**：到轨迹最近点 ≤ 80 m（EXIF 定位常态误差 5~30 m，楼间/桥下会漂）
3. **没有坐标时**：直接按拍摄时间落到轨迹上那一刻的位置，卡片上标「按时间定位」

第 3 条是给视频留的：很多安卓机默认不写视频的位置（隐私开关），但跑步时拍的
东西，时间本身就定位了位置——轨迹在那一刻只有一个点，坐标只是交叉验证。
照片也一样适用，只要它确实是在活动过程中拍的。

不满足的不会被静默丢掉，`motion` 会把「未匹配清单 + 原因」打在终端里（比如
「不在活动时段」「离轨迹 340 m」）。相距 25 m 内的多张照片合并成一个点，播放时并排显示
（两张会统一成同样大小的格子、中心裁切，尺寸不一会像贴歪的照片墙）。

### 实况 / 随手拍的 1~3 秒视频

视频和照片放同一个目录，按同样的规则吸附：

```
data/photos/<活动ID>/VID_20261101_112052.mp4      :: 或 .mov
```

「什么时候、在哪拍的」直接从文件里读，不用管文件名：

| 需要什么 | 从哪读 |
|---|---|
| 拍摄时间 | `moov/mvhd.creation_time`（1904 纪元，UTC） |
| GPS（安卓 / ffmpeg） | `udta/loci`（ISO 6709 二进制）或 `udta/©xyz` |
| GPS（iPhone） | Apple keys 里的 `com.apple.quicktime.location.ISO6709` |
| 时长 / 尺寸 / 编码 | `mvhd`、`tkhd`、`stsd` |

- **两种实况形态都认**：JPEG + 同名 MP4 的成对文件（直接用 MP4）；以及单文件
  动态照片（JPEG 尾部内嵌 MP4）——后者会按 `ftyp` 定位、切出视频并缓存，
  时间与坐标继承照片的 EXIF。
- **时长上限 6 秒**，更长的会跳过（那是要剪的素材，不是实况）。
- **HEVC 会自动转 H.264**：iPhone 实况是 HEIC + HEVC 的 MOV，Windows 上的 Chrome
  解不了。转码时顺手把 GOP 压到 0.5 秒，逐帧 seek 才快（缓存到 `data/motion_cache/`）。
- **同一个点既有照片又有视频时视频优先**，照片只当封面。
- **停留窗口按片段长度自适应**（片段 2 秒 → 停 2.55 秒），不会出现视频播完干等。
- 画面用 `<video>` + `drawImage` 直接上 canvas：实测 1080×1920 逐帧 seek 约 2.6 ms，
  比抽成帧序列省得多（那样 389 KB/帧、2 秒就 23 MB）。
- **相机把「本地时间」当 UTC 写的情况会自动纠正**：`mvhd.creation_time` 差整
  8/9 小时时，按活动窗口试出来并标注 `mvhd+8h`。不这么做，这类视频永远
  「不在活动时段」。

声音默认保留：MP4 会混一条等长静音轨，把各段原声按各自的起点延时叠上去；
网页版受浏览器自动播放限制，需要点一下画面才出声。`--mute` 可关掉整条音轨。

### 没有照片时先造几张

真实照片还没整理好，可以先用合成样张把链路跑通：

```bat
python tools/mk_test_photos.py --id <activity_id> --src output/_gen --clean
```

它把 `--src` 下任意图片转成 JPEG，按轨迹里程反推经纬度写进 EXIF 的 GPS IFD，
拍摄时间取该点的 UTC 时刻，然后落到 `data/photos/<活动ID>/`。默认造 5 张，覆盖
这些情况：单张横拍、单张竖拍、同地两张（并排）、EXIF `Orientation=6` 的旋转存盘、
以及一张**故意错开时段**的（应当被判「不在活动时段」，用来验证未匹配清单）。

样张目录里会留一份 `_TEST_PHOTOS.txt` 说明来源。换真实照片时删掉目录里的
`IMG_*.jpg` 即可——别把合成图当成真实素材发出去。

### 几个刻意的取舍

- **全部画在 canvas 里，没有 DOM 层**。`canvas.toBlob()` 只能拿到 canvas 自己，
  DOM 上的角标在导出的视频里会整块消失；两套渲染逻辑迟早走形。
- **一张底图 + canvas 缩放**做「镜头推近」。静态图配额 5000 次/日，逐帧取图不可能；
  放大超过约 1.3 倍就会糊。
- **时间按「距离/时间轴」播放，不是按轨迹点序号**。2 小时的活动有 7000 多个点，
  按点播会把停顿段拉得极慢。
- **照片处减速而不是全程变慢**。否则 3 秒停留会吃掉整片 1/15 的时长。
- **时间轴按「速度」设计，不按位置折线**：0.7 秒半余弦减速 → 完全静止 → 0.7 秒加速回原速。
  位置折线会让速度在进出照片处硬切换（实测 33 倍突变），看着就是一顿一窜；
  改成速度剖面后逐帧差异曲线是连续收敛到 0 的。
- **停留期间轨迹时间冻结**。原来停留 3 秒里轨迹还在走，镜头会跟着再退 11%，背景在
  静止的照片卡后面缓慢漂移——那是「卡」的主要来源。现在停留区间内整帧逐像素相同。
- **镜头锚点固定在照片点、只缩放不平移**，缩放 1.12。锚点跟着跑者走的话，缩放和位移
  同时发生，眼睛跟不上；1.12 是数字裁切的极限，再放大静态图就糊。
- **车头按时间插值**，不用离散轨迹点。1 Hz 采样在屏幕上每点差 1.8 px，慢速段会变成
  「每 2.5 秒跳一下」的台阶。
- **底图压暗烘焙一次**，不再每帧过 `ctx.filter`；轨迹的 `shadowBlur` 换成多层递减描边。
- **时间轴按「速度」设计，不按位置折线**：0.7 秒半余弦减速 → 完全静止 → 0.7 秒加速回原速。
  位置折线会让速度在进出照片处硬切换（实测 33 倍突变），看着就是一顿一窜；
  改成速度剖面后逐帧差异曲线是连续收敛到 0 的。
- **停留期间轨迹时间冻结**。原来停留 3 秒里轨迹还在走，镜头会跟着再退 11%，背景在
  静止的照片卡后面缓慢漂移——那是「卡」的主要来源。现在停留区间内整帧逐像素相同。
- **镜头锚点固定在照片点、只缩放不平移**，缩放 1.12。锚点跟着跑者走的话，缩放和位移
  同时发生，眼睛跟不上；1.12 是数字裁切的极限，再放大静态图就糊。
- **车头按时间插值**，不用离散轨迹点。1 Hz 采样在屏幕上每点差 1.8 px，慢速段会变成
  「每 2.5 秒跳一下」的台阶。
- **底图压暗烘焙一次**，不再每帧过 `ctx.filter`；轨迹的 `shadowBlur` 换成多层递减描边。
- **配速取 15 秒滑窗**。1Hz 瞬时配速在 ±40s/km 之间摆，直接上角标就是噪音。
- **GPS 丢失 >12 秒处断线**，不画一条直线穿过建筑。
- **照片先按格子的尺寸预渲染成小画布**，每帧只做一次拷贝。每帧都把几 MB 的原图
  缩放着画一遍，多开浏览器时 Chrome 会回收解码数据、`drawImage` 静静跳过——
  成片里就会凭空少一张照片。

### 导出 MP4

需要 ffmpeg，二选一：

```bat
winget install --id Gyan.FFmpeg -e
```

或者下载解压后把 `ffmpeg.exe` 放进项目的 `tools/` 目录（`video.py` 会优先找这里）。

逐帧渲染是「一个页面自己循环截图 → 本地 HTTP 回传」，默认按核数开 2~6 路
（`--workers` 可改）。某一帧迟迟不到（浏览器崩溃/卡住）会自动换进程补渲，
最多重试 3 轮；整片 45 秒约 3~5 分钟。产物：

- `output/_frames/` 帧序列。合成成功后**自动删掉**（一版 45 秒约 1350 张、450 MB），
  想留着排查就加 `--keep-frames`；中途失败时不会删，那是补渲和定位的依据；
- Chrome 的临时 profile（系统临时目录 `garmin-motion-profiles/`，六路共约 400 MB）也一并清掉；
  `--keep-frames` 时两者都保留，方便对着帧排查或加速重跑。

导出不走「每帧起一个 Chrome 截图」——实测 1.8 秒/帧，45 秒的片子要 40 分钟。改成
页面自己循环 `seek → toBlob → POST 回本地服务写盘`，约 0.1 秒/帧，整片两三分钟。
为此图片由本地 HTTP 服务提供（`file://` 会被判跨源，`toBlob` 直接失败）。

### 隐私与合规

- 轨迹 + 底图 = 更精确的个人位置信息，只本地出图，不随日看板上线。
- 图上的「地图数据 © 高德地图」不要裁；底图也不能存下来当素材再分发。
- 回放会暴露家门口。**MP4 回放导出暂未接入自动脱敏**（0.1.4 只覆盖静态活动图
  与 App 分享）；打算发出去的话，先用 `--duration` 看看首尾几帧的位置，必要时
  手动裁掉开头/结尾几秒再发。

## 指标口径

| 指标 | 定义 |
|---|---|
| 恢复度 | 睡眠 35% + HRV 30% + 静息心率 20% + 身体电量 15%；各分量与 28 天中位数基线比较后归一化到 0–100，缺项按剩余权重重新归一 |
| 睡眠债 | 近 7 天每晚「需求 − (主睡眠 + 小睡)」的正向累计。需求用佳明动态值 `sleepNeed.actual`（按训练/睡眠史/HRV/小睡逐日调整，实测 420~540 分），无则回退 480；小睡来自 `napTimeSeconds`（**不包含**在主睡眠里，须单独累加），全额抵扣。已知约 20 分/晚的重复计算：佳明也会用 napAdjustment 调低次日需求，暂不对冲 |
| 每日负荷 | 优先用 Garmin 的 `activityTrainingLoad`；缺失时用 TRIMP 估算 `分钟 × HRr × 0.64 × e^(1.92·HRr)` |
| CTL / ATL | 42 天 / 7 天指数移动平均 |
| TSB | CTL − ATL（正数=新鲜，负数=疲劳积累） |
| 体重趋势 | 同一天多次称重先取均值，再比「最近 7 天均值」与「前 7 天均值」，变化按百分比/周计。绝对值不进判断——水分、进食、糖原都能让体重一天晃 1 kg |
| 体成分 | 小米秤的体脂/肌肉/水分是生物电阻抗（BIA）估算，绝对误差 ±3~5 pt，只在跨度 ≥14 天、变化 ≥1 pt 时才写进结论 |
| ACWR | 近 7 天负荷 ÷（近 28 天负荷 ÷ 4）；>1.5 视为激增 |

阈值都在 `garmin_cn/metrics.py` 与 `garmin_cn/coach.py` 里，可直接改。

### 步频与步幅为什么要自己重算

佳明的 `/gc-api` 里 `directRunCadence` 是**单侧**步频（一步/单腿），
`directDoubleCadence` 才是总步频，两者比值恒为 2。活动级汇总字段
`averageRunningCadenceInStepsPerMinute` 也是混了单侧值、停顿和走路的平均值，
同样不可信（实测出现过 4'48" 配速配 116 spm 的组合）。

因此 `garmin_cn/activity.py` 的做法是：**丢弃所有汇总值，用 1Hz 时序重算**。

- 步频取 `directDoubleCadence`，缺失时用 `directRunCadence × 2`；
  若速度已明显是跑动（≥2.5 m/s）但步频仍落在单侧区间，再乘 2 兜底
- 步幅不采信 `directStrideLength`，直接用 `speed × 60 ÷ cadence × 100`（cm）
- 偏离全活动步幅中位数 30% 的样本判为速度/步频错位，**按比例回正**而不是置空：
  步幅 ≈2 倍中位数就把步频 ×2、步幅 ÷2，≈0.5 倍则反过来；其余夹回 ±30% 边界。
  回正过的点在活动图的步态走势图上打一个橙点，图例只在真有橙点时才出现
- 统计只取速度 ≥2.2 m/s 的跑动样本；分圈按 `startTimeGMT` 时间窗回溯时序重算

修正后步频与步幅会明显收敛（佳明原值在相邻区间抖动）。

### 单次活动图的版式约定

从上到下：抬头 → 距离 + 配速（两个并排大数字）+ 六项指标（用时/爬升/主要益处
/步频/步幅/心率，上 3 下 3）→ 左轨迹右心率分区 → 配速与心率双泳道曲线 →
跑步技术 + 负荷 → 每公里/分段。

顶部两个大数字是刻意平级的：跑者第一眼看「跑了多远 + 多快」，距离缩成右侧小格
等于没强调。室内/力量课没有距离（<50 m）时只留主指标一块，不会出现 "0.00 公里"。
右侧那格「主要益处」取 Garmin 的 `trainingEffectLabel`（`RECOVERY`→恢复、
`TEMPO`→节奏…），标签缺失时按有氧 TE 分级兜底（<1 热身、2 维持、3 提升）。它是
文字不是数字，字号要降一档（`.st.wd`）且必须 `white-space:nowrap`——"乳酸阈值"
一旦折行会把行高顶起来，第二行的步频步幅心率就被挤出卡片底边。

曲线卡两套刻度都在左侧：上泳道蓝=配速、下泳道橙=心率，颜色跟曲线一致，
不用读图例也知道哪根轴配哪条线。功率分区条按需求去掉了（平常不看）。

宽度不写死：一律从版心 1008px 反推卡片内容宽（`actcard.py` 顶部的 `TRK_CW` /
`ZC_CW` / `CH_CW`），早前曲线按 1000px 硬写过一次，右端刻度被裁到卡片外面。
中段两卡同高（`MID_H`），轨迹画面高度由分区卡内容反推，别单独调一个。
心率与功率共用同一条堆叠条的样式，粗细一致才不显错位。

### 真实地图底图（可选，只本地）

在 `data/amap.json` 写 `{"key": "你的 Key"}`，或设环境变量 `AMAP_KEY`，轨迹卡就会铺
一张高德静态地图；没有 Key 时自动回落到矢量轨迹，其余行为不变。

**Key 怎么拿**（免费，10 分钟）

1. 打开 <https://lbs.amap.com/>，右上角「登录/注册」，用手机号或高德 App 扫码登录。
2. 实名认证：控制台左侧 **账号中心 → 账号认证 → 个人开发者认证**（身份证 + 人脸/短信，
   当场通过）。不做认证拿不到 Key，这是硬门槛。
3. 控制台 → **应用管理 → 我的应用**，右上角 **创建新应用**。名称随便写（如
   `garmin-coach`），应用类型选「出行」或其它都行，不影响调用。
4. 在该应用条目右侧点 **添加 Key**。**服务平台必须选「Web服务」**——选成
   「Web端(JS API)」就会拿到 `sk-`/`js-` 开头的 Key，静态地图调用一律报
   `10009 USERKEY_PLAT_NOMATCH`。
5. **IP 白名单**留「无」（本地家用宽带 IP 会变，绑了容易失效）。
6. 提交后列表里那串 32 位十六进制就是 Key，复制。
7. 存进项目并当场验证：

   ```
   run.bat key --set 你的Key
   ```

   会写入 `data/amap.json` 并真打一次静态地图，输出「✓ 探活通过」就说明能用；
   失败会直接给高德错误码对应的人话（如配额用完、平台选错、IP 白名单）。

之后的常用命令：`run.bat key`（看当前 Key 与探活）、`run.bat key --clear`（删掉）、
`run.bat doctor`（自检里也含这一项）。配额见控制台「用量管理」，个人认证静态地图
5000 次/日，一次活动一张，用不完。

**实现细节**

- **坐标系：Garmin 返回的是 WGS-84，高德底图是 GCJ-02，必须纠偏。** 两者在国内差
  400~500 m，不纠偏的话整条轨迹会平移到大路旁边一个街区的西侧（症状很像「整体向西北偏」）。
  `AMAP_DATUM` 默认就是 `wgs84`＝开纠偏；只有当数据源本身已经是 GCJ 时才设 `AMAP_DATUM=gcj`。
- 这条**判断反过一次**，值得记下来：当时把高德 POI 的坐标直投到底图，落在图标上，就断言
  「数据已是 GCJ」。这是自证——POI 和底图本来就都是 GCJ，怎么投都对。真正的判据是拿
  **高德自己的路径规划**（`walking`，返回的折线必然压在路网上）去比：不纠偏时两条线
  **平行错开约 50 px（≈410 m）**，纠偏后贴在一起。命令：
  `py tools/mapcheck.py --id <活动ID> --road`，会打印「路面距离中位数 / 横向偏移」并出
  `output/_roadcheck.png`（绿＝高德路线，洋红＝我们的轨迹）。改坐标系或取景后跑这两个
  检查：`--road` 验坐标基准，不带 `--road` 验投影几何。
- 取景由我们自己定：`basemap.fit()` 按轨迹范围算出中心点与**整数 zoom**，URL 里带
  `location`+`zoom`（不是让高德自动取景）。这样 `to_px()` 能把经纬度算成画幅内像素，
  **轨迹线仍是我们自己画的**——自动取景的内边距是黑盒，第一版硬叠必然错位。
- **关键坑：高德静态地图一个 zoom 级别对应 `512×2^zoom` 的世界像素宽，不是 Web 墨卡托的
  `256×2^zoom`**（等价于别人家的 zoom+1）。按 256 算，整张底图就比轨迹「放大一倍」，
  怎么调平移都对不上。`basemap.WORLD_TILE = 512` 这一个常数就是全部修正。判据用
  `tools/mapcheck.py`：让高德自己按 `paths` 画同一条轨迹，和我们投影的线比是否重合。
- 整数 zoom 的粒度是 2 倍，所以「刚好装下」的那一档会留大半空白。做法是**跳到深一档**
  再整体缩回 `s≤1`（`basemap.fit` 直接返回 `s` 与图片尺寸）：底图只缩不放（缩不糊，
  `scale=2` 还给了 2 倍像素），轨迹占位更满。也**不要**为了撑满画幅去放大底图。
- 底图与轨迹共用**同一个** `p' = p*s + t` 变换。别写成 `translate/scale/translate`
  三段串联——那样缩放锚点落在图像角上，底图只会覆盖画幅一角，四周露出卡片底色。
  `t` 还要夹住，保证 `s<1` 时底图仍盖满画幅（图片是按 `w/s × h/s` 取的，所以缩回后正好铺满）。
- 轨迹卡标题右侧显示「省·市」（如「陕西·西安」），由高德逆地理编码
  `basemap.regeo()` 按取景中心点取，跟 meta 一起缓存。
- 起终点标记**同一尺寸**：起点绿圆点、终点红方块（边长=圆直径）。只有两者相距不到一个
  标记宽（绕圈/折返跑）时才并成一个「红方块里嵌绿点」，位置取中点——否则红方块会把
  绿点啃掉一半，看着像画重了。
- 滤镜用 SVG 原生原语（`feColorMatrix` saturate + `feComponentTransfer` 线性压亮提对比），
  参数在 `actcard.MAP_BRIGHT / MAP_CONTRAST / MAP_SAT`。**别改回 CSS `filter:grayscale()`**：
  无头 Chrome 对 SVG `<image>` 的 CSS filter 函数串不生效，底图会原样亮出来。
  也**不做反相**：反相会把高德水印一起改掉，属于修改地图内容。
- 署名：底图自带高德水印；外圈可能被裁，所以右下角另加一行淡色「高德地图」兜底，别删。
- 取回的图、取景参数、地名一起缓存在 `data/basemaps/<活动ID>-<宽>x<h>.png` + 同名
  `.json`；meta 里带 `rev`，取景算法一改（`basemap.REV`）就自动重取，
  **不用手动删缓存**。手动删也一样会重拉。
- 对齐出问题时先跑 `py tools/mapcheck.py --id <活动ID>`：它会请高德按 `paths` 把同一条
  轨迹画出来，再叠上我们算的线，重合=投影对；整体平移=中心错；一头大一头小=比例错。
- 合规：底图走持证服务商在线接口（不能自己画国界/行政区划），水印不能裁；
  轨迹+底图属更精确的个人位置信息，因此只在本地出图，不随日看板上线。

## 已知限制

- 国区没有官方 Personal API，这套走的是 App 使用的 `/gc-api/` 通道，Garmin 改接口时可能失效
  （届时看 `data/` 里的报错，或 `run.bat coach` 的字段是否为空）。
- 心率区间边界取不到（`/biometric-service/biometric/hrZones` 返回 null），
  只能用服务端算好的每区时长，无法还原精确的分区阈值。
- 左右触地平衡需要 HRM-Pro 一类双模设备，本设备无此数据。
- 活动图的轨迹默认是自绘折线；配了高德 Key 才铺真实底图（见上节）。
- 轨迹属于个人信息（能暴露常跑路线与居住区域），活动图默认只出本地，不自动发布。
- 接口是拉取式，没有推送；同步频率建议每天 1 次，别高频轮询（会 429）。
- 部分专有字段（VO2max、恢复时间、训练效果等）在 API 里可能缺失，与手动导出 `.fit` 的完整度不同。
