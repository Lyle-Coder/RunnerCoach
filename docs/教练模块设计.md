# 教练模块设计（v1 草案，待定稿）

> 目标：把「一场比赛」变成系统里的一等公民，让训练计划、赛事资料、路线、推送、
> 复盘围绕同一份赛事档案运转，并在一图流看板上用一张卡把它讲清楚。
>
> 状态：**设计稿，未开发**。末尾「待确认」一节是动手前必须先拍板的事。

---

## 1. 为什么现在做

现在的 105K 备赛能力是「拼出来的」：

| 能力 | 现有实现 | 形态 |
|---|---|---|
| 课表数据 | `tools/make_plan.py` 的 `WEEKS`（21 周硬编码） | Python 源码 |
| 课表读取 | `garmin_cn/raceplan.py` | 动态加载 WEEKS |
| 推送到手表 | `garmin_cn/workout.py` | Connect workout API |
| 赛事成绩 | `race_results` 表（1 条记录） | SQLite |
| 赛后复盘 | `garmin_cn/racecard.py` | 竖版 PNG |
| 外部计划 | `garmin_cn/plan.py`（佳明日历 / Garmin Coach） | 只读归一化 |
| 展示 | `card.py`（一图流 PNG）、`report.py`（网页） | 各自一套 |

问题不在于缺功能，而在于**没有「赛事」这个实体**：

- 赛事信息散落在 `WEEKS` 的注释、`raceplan.py` 的常量、`make_plan.py` 的 HTML 文案、
  以及你的记忆里（起终点、关门、强制装备、补给站）。
- 换一场比赛（比如再来一次全马）就要改源码。
- 路线（GPX / 爬升剖面 / 补给点）完全没有入口，只能看赛事官网。
- 一图流上「距比赛还有几天」是算出来的，但「强制装备准备了几项」「路线最难那段在哪」看不见。

这次要补的就是这三块：**赛事实体 + 资料/路线管理 + 教练卡**。

---

## 2. 边界：新模块不做什么

明确划出去，避免又长成一个巨型模块：

- **不做训练计划生成器**。计划仍由 `WEEKS`（本地）或佳明（外部）提供，新层只做「适配 + 关联 + 展开」。
- **不做社交/报名/缴费**。赛事官网能做的事不重复。
- **不做食谱与训练动作库**。营养走 `nutrition.py`，动作走 `workout.POWER`。
- **不改 `WEEKS` 的数据结构**。它是运行良好的主力，只加一层包装。

一句话：**新模块是「档案 + 索引 + 视图」，不是第二个计划引擎。**

## 3. 数据模型

新增三张表（`store.py` 里加，`IF NOT EXISTS` 幂等建表，与现有 7 张表共存）。

### 3.1 `event` —— 赛事档案

```sql
CREATE TABLE IF NOT EXISTS event (
  id            INTEGER PRIMARY KEY,
  slug          TEXT UNIQUE NOT NULL,   -- panda-105k-2027
  name          TEXT NOT NULL,          -- 熊猫蜀道山越野赛
  group_name    TEXT,                   -- 105K 组
  date          TEXT NOT NULL,          -- 2027-03-27
  start_at      TEXT,                   -- 2027-03-27T06:00
  distance_km   REAL,
  ascent_m      INTEGER,
  cutoff_s      INTEGER,                -- 关门秒数（29h = 104400）
  start_place   TEXT,
  finish_place  TEXT,
  status        TEXT,                   -- announced|registered|confirmed|done|cancelled
  bib           TEXT,
  goal_s        INTEGER,                -- 目标完赛秒数
  plan_key      TEXT,                   -- 关联哪套课表：local-105k
  website       TEXT,
  note          TEXT,
  raw           TEXT,                   -- 原样留存的报名/中签信息
  created_at    TEXT,
  updated_at    TEXT
);
```

`status` 用固定枚举而不是自由文本，因为它决定看板显示什么：
`announced`（未报名）→ `registered`（已报名待抽签）→ `confirmed`（中签/确定）→ `done` / `cancelled`。
这次「出签」就是把 `registered` 改成 `confirmed`，看板上的倒计时从「预计」变成「确认」。

### 3.2 `event_doc` —— 资料条目

```sql
CREATE TABLE IF NOT EXISTS event_doc (
  id          INTEGER PRIMARY KEY,
  event_id    INTEGER NOT NULL REFERENCES event(id) ON DELETE CASCADE,
  kind        TEXT NOT NULL,     -- gear|rule|logistics|aid|entry|result|misc
  title       TEXT NOT NULL,
  body        TEXT,              -- Markdown / 纯文本（短条目）
  url         TEXT,              -- 外链（官网规程、报名页）
  file_path   TEXT,              -- 本地文件相对路径
  due_at      TEXT,              -- 到期日（YYYY-MM-DD）：进看板提醒，如赛前 7 天
  pinned      INTEGER DEFAULT 0, -- 置顶（强制装备、领物单）
  sort        INTEGER DEFAULT 0,
  updated_at  TEXT
);
```

`kind` 的六类，对应六种真实需求：

| kind | 存什么 | 展示位置 |
|---|---|---|
| `gear` | 强制装备清单（逐项勾选状态） | 教练卡底部「装备 7/12」 |
| `rule` | 关门时间、罚则、号码布规定 | 赛事页详情 |
| `logistics` | 交通、住宿、领物时间地点 | 赛事页 + 赛前 7 天提醒 |
| `aid` | 补给站表（km / 关门 / 热食 / 换装包） | 路线剖面下方 |
| `entry` | 报名确认、中签截图、参赛号 | 赛事页附件 |
| `result` | 官方成绩、完赛证书 | 赛后复盘自动关联 |

**装备清单需要逐项状态**，所以 `gear` 的 `body` 用固定格式（一行一项，`- [x] 头灯 + 备用电池`），
展示时解析成勾选进度。不另建表——用 Markdown checklist 就够，也方便手改。

### 3.3 `course` —— 路线

```sql
CREATE TABLE IF NOT EXISTS course (
  id           INTEGER PRIMARY KEY,
  event_id     INTEGER NOT NULL REFERENCES event(id) ON DELETE CASCADE,
  label        TEXT,              -- 官方 GPX / 2026 实测
  source       TEXT,              -- gpx|activity|manual
  distance_m   REAL,
  ascent_m     INTEGER,
  descent_m    INTEGER,
  point_count  INTEGER,
  profile      TEXT,              -- JSON [[km, ele], ...] 每 500 m 一个采样点
  geom         TEXT,              -- JSON [[lat, lon], ...] 抽稀到 ≤500 点
  aid_json     TEXT,              -- JSON [{km, name, cutoff, dropbag, hot_food}]
  file_path    TEXT,              -- 原始 GPX
  created_at   TEXT
);
```

一个赛事允许多条路线（官方 / 实测 / 自己规划的备选），看板默认取 `source='gpx'` 且最新的一条。

### 3.4 文件放哪

```
data/events/<slug>/
    official.gpx
    handbook.pdf
    entry-confirm.png
```

DB 里只存**相对路径**（`events/panda-105k-2027/official.gpx`），这样 `run.bat export`
打包换机时不丢。资料含个人信息（参赛号、身份证照片），已在 `.gitignore` 里排除 `data/`，
不进公开发布仓库——这条红线沿用现有约定。

## 4. 计划来源适配

### 4.1 现状与问题

现在有两条独立的读计划路径，输出结构不一样：

- `raceplan.day_info(date)` → 本地 WEEKS，字段齐全（kind/abbr/km/vert/minutes/hr/note）
- `plan.py` → 佳明日历 / Garmin Coach，归一化成另一套结构

展示层因此要写两套分支（`card.py` 里 `if rpi: ... else: ...`）。加第三种来源就爆炸。

### 4.2 统一接口

新增 `garmin_cn/plansource.py`，定义一个轻量适配协议，**不改两边的实现**，只做转换：

```python
class PlanSource:
    key: str                      # local-105k / garmin-calendar / garmin-coach
    label: str                    # 「105K 自建课表」
    capabilities: set[str]        # {"read", "push", "override"}

    def day(self, d: date) -> Day | None: ...
    def week(self, d: date) -> list[Day]: ...
    def range(self) -> tuple[date, date]: ...
```

`Day` 是一个 dataclass（不是 dict，避免字段拼错）：

```python
@dataclass
class Day:
    date: date
    kind: str          # rest/easy/quality/hill/long/b2b/str/race
    title: str
    abbr: str          # 卡片主行：2×10min@T
    km: float
    vert: int
    minutes: int
    hr: str | None     # Z2 / 135–160
    note: str
    source: str        # 哪个适配器给的
    race_slug: str | None
```

适配器只做一件事：把现有结构翻译成 `Day`。

| key | 数据源 | 能力 | 说明 |
|---|---|---|---|
| `local-105k` | `raceplan` + WEEKS + week_overrides | read, push, override | 主力，可写 |
| `garmin-calendar` | `plan.py` 日历 | read | 只读，用来对照「手表上实际排了什么」 |
| `garmin-coach` | Garmin Coach / FBT | read | 兜底 |
| `manual` | `data/manual.json` | read, override | 临时改某天（已有） |

**关键取舍**：适配层只读，不写回。要改计划仍然改 WEEKS 或写 `week_overrides.json`——
保持「单一事实源」，不让两套数据打架。

### 4.3 多赛事并存

现在 `WEEKS` 是「为 105K 排的 21 周」。如果以后同时备两场（比如春季 105K + 秋季全马），
需要 `plan_key` 指向不同的计划档案。

本期不做多计划生成，只做**预留**：`event.plan_key` 字段先落库，值固定 `local-105k`。
真要并行时，把 WEEKS 拆成 `plans/105k.py`、`plans/marathon.py`，`raceplan` 按 key 加载——
那是下一步的事，不在这次范围。

## 5. 计划推送适配

### 5.1 现状

`workout.py` 已经把「Day → Connect workout JSON → 建课 → 排程」跑通，包括两次真机踩坑
（配速单位 m/s、RepeatGroup 要 numberOfIterations）。这块**不动**。

### 5.2 要抽象的是「推到哪」

```python
class PushTarget:
    key: str              # garmin-connect / fit-file / ics
    capabilities: set[str]  # {"workout", "schedule", "replace"}
    def push(self, days: list[Day], *, replace=False) -> PushResult: ...
```

| key | 状态 | 用途 |
|---|---|---|
| `garmin-connect` | **已实现** | 主力，手表直接读 |
| `fit-file` | 待做（兜底） | 生成 FIT 拷到 `GARMIN/NewFiles`，Connect API 挂掉时用 |
| `ics` | 已有（`make_plan.py` 出 ics） | 给日历订阅 / 非佳明设备 |

本期只做一层薄包装（把 `workout.push_range` 套进 `PushTarget`），不重写推送逻辑。

### 5.3 推送与赛事的关系

推送时课程名带周次（`W15 周六 45km@E`），**不带赛事名**。如果将来多赛事并行，
同名课程会在日历里打架。本期约定：**同一时间只有一个 active 赛事**，
`event.plan_key` 保证课表与赛事对应；多赛事留到下一步。

## 6. 资料管理方式

### 6.1 三种录入途径，按成本从低到高

1. **CLI 一行命令**（主力）：`run.bat event doc add panda-105k-2027 --kind gear --title 强制装备 --stdin`
2. **直接编辑 Markdown 文件**：`data/events/<slug>/notes.md`，导入时整篇挂到 `kind=misc`
3. **附件拖进目录**：`data/events/<slug>/`，`run.bat event scan` 自动识别 GPX/PDF/图片并登记

不做图形化管理界面——这个项目一直是 CLI + 静态页面，加个后台管理会带来账号、上传、
权限一堆问题，收益不匹配。

### 6.2 读取与展示

- `run.bat event show <slug>`：终端输出完整档案（赛事字段 + 资料分组 + 路线摘要 + 装备勾选进度）
- 网页看板新增「赛事」区块：资料按 kind 分组，附件给相对链接（`serve` 已能挂 output/）
- 一图流只挑 3 项：装备进度、路线爬升、下一个里程碑

### 6.3 装备清单的格式约定

```markdown
- [x] 头灯 + 备用电池（2 组）
- [x] 冲锋衣（压胶，非一次性）
- [ ] 保温毯
- [ ] 急救包
```

解析规则：`- [x]` 已完成、`- [ ]` 未完成，其余行当普通说明。展示成 `7/12 已备`。

### 6.4 与赛前提醒联动（已确认要做）

`gear` 类条目建的时候带 `due_at`（默认 = 比赛日 − 7 天）。看板出图前跑一条检查：

```
我需要的装备还没勾满  且  today >= due_at - 7   →  进「需要注意」区
```

文案形如「强制装备 7/12，距起跑 5 天，还差：保温毯、急救包、备用头灯电池」。
不满 7 天但已过期就不重复喊，只显示一次「已过期」。

实现上只是一个纯函数 `event.gear_gap(slug, today) -> (done, total, missing, urgent)`，
不写库、不缓存，看板每次出图现算——避免状态不同步。

## 7. 路线管理

官方 GPX 现在没有（赛事一般赛前 1–2 个月才发），所以这一期做**手填关键点**，
GPX 解析留好接口但不实现。等文件到了，填进去就能用，不用改结构。

### 7.1 本期：手填关键点（不做 GPX）

`course` 表先只填三样东西：总距离、总爬升、补给站列表。

```
run.bat event course panda-105k-2027 set --dist 105 --ascent 5550 --descent 5550
run.bat event aid panda-105k-2027 add --km 18.5 --name CP1 --cutoff 3h20 --dropbag
run.bat event aid panda-105k-2027 add --km 42 --name CP4 --cutoff 8h00 --hot-food
```

数据来自赛事规程（官网/公众号推文），一条条录进去，`source='manual'`。

**为什么这样也够用**：教练模块要回答的不是「第 63 km 海拔多少」，而是
「到 CP4 时我还有多少关门余量」。有了 km + 关门时间 + 目标配速，这个就能算，
不需要完整剖面。

`profile` 和 `geom` 字段先留空，`course.py` 里 GPX 相关函数写成 TODO 占位。

### 7.2 关门余量表（本期核心产出）

这是路线管理真正的价值，也是 105K 唯一不能出错的地方——**被关门就结束了**。

```
CP      距离    关门      计划到达   余量
CP1     18.5    3h20      2h50      +30 min
CP4     42.0    8h00      6h40      +1h20
CP7     68.0    13h30     11h10     +2h20
终点    105.0   29h00     20h30     +8h30
```

「计划到达」由目标完赛时间（`event.goal_s`）按距离与爬升加权分配到各 CP，
不是平均分。算法简单：累计等效距离 = 距离 + 爬升/100，按比例分摊总时间。

余量为负 = 这个 CP 会被关门，红色标注，并在教练卡上直接提示。

### 7.3 赛前 GPX 到位后（延后实现）

接口留好，实现时补：

1. **累计爬升必须滤波**。GPS 高程噪声 ±3–5 m，直接累加能把 5,550 m 算成 8,000 m。
   滑动平均（窗口 5 点）后只累计上升超过 3 m 的段落；和官方数字差 >10% 就标「自算」。
2. **剖面采样**每 500 m 一点，105 km → 210 点，JSON 约 4 KB，够画 sparkline。
3. **折线抽稀**用 Douglas-Peucker（容差 30 m）压到 ≤500 点存 `geom`。

届时 `source` 从 `manual` 变 `gpx`，补给点用 `<wpt>` 自动识别，手填值作对照。

### 7.4 与训练计划的对接

- 把每 10 km 的计划用时写进 `WEEKS` 的周说明（专项期长课），让训练直接对着比赛分段练。
- 赛后把 `route.py` 的实测轨迹叠到路线上，看哪里掉速最多（复盘图数据源，本期不做）。

### 7.5 3D 赛道呈现（这次讨论的重点）

目标：让选手在赛前"走过一遍"赛道——哪段最陡、哪个 CP 前有连续爬升、哪里是夜间段、
补给该放在第几公里。**不是做一个炫技的 3D 地球，是做一份能用来做决策的赛前简报。**

#### 形态选择：视频为主，交互为辅

| 形态 | 优点 | 缺点 | 定位 |
|---|---|---|---|
| **分段特写 MP4** | 手机上直接看、能发微信、离线、每段 4–6 秒 | 不能转视角 | **主产物** |
| 交互式 3D 页面（WebGL） | 可拖拽、可量距离 | 低端机 WebView 性能不稳 | 辅助（`serve` 打开时有） |
| 一图流小剖面 | 每天都能看到 | 只有轮廓 | 已规划（§8.1） |

选视频为主的三个理由：① 你的主场景是微信里看图/看片，不是坐电脑前转模型；
② `motion.py` 已经有「headless Chrome 抓帧 + ffmpeg 合成」的成熟链路，复用成本最低；
③ 3D 交互要处理 WebGL 上下文丢失、触摸手势、低端机降级，投入产出不划算。

#### 五个镜头（自动生成，不用手调）

| 镜头 | 时长 | 内容 | 用途 |
|---|---|---|---|
| 全局鹰眼 | 3 s | 整条赛道悬在地形上，CP 依次亮起 | 建立整体印象 |
| 分段特写 ×N | 每段 4–6 s | 相机沿该段推进，坡度着色，最高点标注 | 逐段理解 |
| 最难段环绕 | 5 s | 对「难度分最高」那一段做 180° 环绕 | 重点记忆 |
| 爬升剖面联动 | 4 s | 左侧剖面游标 + 右侧 3D 同步推进 | 把数字和地形对上 |
| 夜间段 | 4 s | 时间轴调到 19:00 后，地形变暗、赛道变亮 | 夜间策略 |

段数由 CP 数决定（105K 通常 7–9 个 CP），全片 40–70 秒。

#### 技术链路

```
GPX + CP 表
  → 按 CP 切段，每段算 d+/d-/平均坡度/最陡 500m
  → DEM 采样（AWS terrarium 瓦片，z12≈38 m/px）
  → 裁出赛道走廊（buffer 5 km）建地形 mesh（降到 ≤200×200 顶点）
  → 赛道折线贴地（DEM 双线性插值，不平滑会浮空/穿地）
  → 按坡度着色（绿→黄→红），CP 用 billboard 标注
  → 相机关键帧（鹰眼→推进→环绕），逐帧渲染
  → headless Chrome 抓帧 + ffmpeg 合成 MP4
```

#### 难度分解（务实版）

| 环节 | 难度 | 关键坑 |
|---|---|---|
| DEM 瓦片拉取与解码 | 中 | terrarium 格式：`ele = R*256 + G + B/256 - 32768`；瓦片要缓存 |
| 地形 mesh 构建 | 中 | 顶点数必须降采样，2 万顶点在 WebView 里直接卡死 |
| 赛道贴地 | 中 | 不贴地会浮空；要按累计距离插值再查 DEM，不是逐点查 |
| 坡度着色 + CP 标注 | 低 | billboard 要朝向相机 |
| 相机动画 | 中 | 关键帧插值要防抖动，加减速曲线比匀速自然 |
| 视频合成 | 低 | 复用 `motion.py` 的链路 |

**总量估算**：预渲染视频这条线约 **3–4 天**；交互式 3D 再加 **2–3 天**，建议后置。

#### 三个必须提前说的风险

1. **没有 GPX 就没有 3D**。地形可以自动拿，赛道线不能凭空生成。官方 GPX 一般赛前 1–2
   个月才发（这个赛事大概 2027 年 1 月底）。在此之前，3D 只能做「地形预览 + 你手填的
   CP 大致位置」，价值有限——所以 3D 排在 P4，不阻塞前面的功能。
2. **DEM 精度决定了"最陡坡"的可靠性**。SRTM 30 m 在 105K 尺度够看趋势，但判「
   这 200 m 是不是 25% 陡坡」会失真。所以文案只写到「连续 4 km 上坡、平均 6%」，
   不承诺具体单点坡度。
3. **图像与国区地图合规**。只用公开地形/卫星瓦片做**离线渲染**，不对外提供地图服务、
   不做在线瓦片分发——这和现有 `basemap.py` 用高德底图的处理方式保持一致。

## 12. 数据源三分法（横切全模块）

> 每个新增数据项都要先回答一个问题：**这个能不能不问用户？**
> 原则：能自动拿的绝不问；必须问的只问一次，并且给默认值让用户"确认"而不是"填空"。

### 12.1 A 类 · 软件自己取（爬虫 / 公开 API）

| 数据 | 来源 | 时机 | 失败时 | 实测 |
|---|---|---|---|---|
| 地形 DEM | AWS `elevation-tiles-prod`（terrarium，免费无 key） | 建档一次 + 缓存 | 退 2D 剖面，不做 3D | 已通（200） |
| 卫星影像 | Esri World Imagery | 可选 | 纯地形晕渲 | 已通（200） |
| 赛事基础信息 | 官网 tsaigu.com / 「柴古唐斯」公众号 / 最酷 | 建档 + 每周复查 | 手填兜底 | 已抓：105K / 5550 m / 29 h / 3-27 06:00 / 白鹿音乐广场 |
| CP 距离与关门 | 官方推文的分段剖面图（OCR）+ 赛事指南页 | 建档 + 赛前 1 个月复查 | 手填 | 推文里确有按段 D+/D-/关门图 |
| 赛道特色注释 | 赛记、测评、官方文案 → LLM 摘要 | 建档 | 不展示 | 需你确认，见 12.4 |
| 历史同期天气 | Open-Meteo archive | 建档 | 不展示 | 已通（彭州海拔 1081 m） |
| 比赛日预报 | Open-Meteo forecast | 赛前 14 天起每日 | 不展示 | 同上 |
| 完赛率 / 成绩分布 | 官网成绩页 | 赛后 | 不展示 | — |
| 日落时刻 | 本地天文算法（无需 API） | 建档 | 固定 19:00 估算 | — |

**边界**：只抓公开页面、只做一次性快照存本地，不做高频轮询、不绕登录墙。
公众号内容通过文章 URL 抓（`mp.weixin.qq.com` 单篇可读），不模拟客户端接口。

### 12.2 B 类 · 需要用户提供

| 数据 | 为什么只能你给 | 输入方式 | 默认值策略 |
|---|---|---|---|
| **GPX 轨迹** | 官网未必放，且必须是 105K 组那条 | 拖进 `data/events/<slug>/` | 无默认，硬依赖 |
| **目标完赛时间** | 只有你知道要跑多少 | 一个「时:分」 | 用半马 1:29 + 全马 3:13 推算 20–22 h，给你三档选 |
| 装备准备状态 | 东西在你手上 | 勾选 | 预置 12 项强制装备模板，只需勾 |
| 补给偏好 | 肠胃个体差异 | 三档（保守 / 常规 / 激进） | 常规 |
| 交通住宿 | 私人安排 | 可选文本 | 留空就不显示，不催填 |
| 伤病 / 身体约束 | 只有你知道 | 选项 | 沿用教练模块已有字段 |

B 类只有 6 项，其中**真正阻塞功能的只有 GPX 和 目标时间**这两个。

### 12.3 C 类 · 不需要外部数据源（本地算）

| 数据 | 算法 |
|---|---|
| 关门余量 | `目标分摊到达 − CP 关门`，负值告警 |
| 分段目标用时 | 等效距离 `km + d+/100` 按比例分摊总目标 |
| 赛段难度分 | 平均坡度 × 0.4 + 段爬升/100 × 0.4 + 距离/10 × 0.2，归一到 1–5 |
| 掉速风险点 | 坡度 >15% 且连续 >2 km 的段 |
| 训练匹配度 | 本周长课的爬升/时长 vs 对应赛段特征 |
| 装备进度 | 勾选统计 |
| 夜间段 | 到达时刻 > 日落时刻 的段 |

C 类是纯函数，不落库、不缓存、每次现算——避免状态不同步。

### 12.4 交互逻辑：先猜后确认，不让用户填空

四层递进，越往后用户越省力：

1. **零输入**（A 类全覆盖）：地形、天气、坡度、难度分、日落——建档即得。
2. **一次拖拽**（唯一的硬输入）：GPX 拖进目录，自动解析距离、爬升、`<wpt>` 航点。
3. **确认式**：CP 表和赛道特色，软件先给出猜测，用户只回答「对 / 改」。
   例：`CP4 42.0 km · 关门 8h00 —— 抓自官方推文，对吗？[对] [改]`
4. **勾选式**：装备清单，预置模板只勾不写。

**反例（必须避免）**：让用户手填 9 个 CP 的距离和关门时间——那是 18 个数字，
没人愿意填。正确做法是软件先 OCR 出猜测，用户只纠正错的那两个。
抓不到时才退回手填，且只填缺失项。

### 12.5 结构化呈现：一份 `course.json` 驱动四端

3D 分段、关门余量表、一图流小剖面、教练卡提示，全部读同一个结构，
避免四处各算一遍、数字还打架：

```json
{
  "event": "panda-105k-2027",
  "distance_km": 105.0,
  "ascent_m": 5550,
  "goal_s": 75600,
  "sunset": "19:12",
  "segments": [
    {
      "idx": 1,
      "from": {"km": 0.0, "name": "白鹿音乐广场", "ele": 780},
      "to":   {"km": 18.5, "name": "CP1 海窝子", "ele": 920, "cutoff_s": 12000},
      "stats": {"d_plus": 620, "d_minus": 480, "avg_grade": 3.4,
                "max_grade": 18.2, "steepest_km": 12.3},
      "surface": ["公路", "土路"],
      "features": ["连续 4 km 上坡", "夜间段"],
      "difficulty": 3,
      "plan_arrive_s": 10200,
      "margin_s": 1800,
      "source": "ocr"
    }
  ]
}
```

`source` 字段记来源（`ocr` / `manual` / `gpx`），展示时对 `manual` 标注「手填」，
让你知道哪个数字不可靠。

### 12.6 缺数据时的降级阶梯

这是"尽可能减少输入"的兜底设计——**任何一档都能用，不会因为缺一项就白做**：

| 手上的东西 | 能做什么 | 不能做什么 |
|---|---|---|
| GPX + CP 表 | 全部：3D 分段、余量表、难度分、训练匹配 | — |
| GPX，无 CP | 3D 全赛道、按坡度自动切段、剖面 | 关门余量（无关门数据） |
| 无 GPX，有 CP | 余量表（按 km 直线插值）、CP 一览 | 3D、剖面、坡度 |
| 什么都没有 | 赛事倒计时、目标分解、装备清单、训练匹配（按总距离/爬升） | 以上全部 |

即使最差那档，教练模块对"怎么练、什么时候该准备什么"依然有用——
3D 只是锦上添花，不是地基。

## 14. P4 已交付：3D 赛道简报（2026-11-11）

`tools/make_3d.py`，27 秒 / 1280×720 / 24 fps，输出 `output/plan-105k-3d.mp4`。

### 14.1 链路

```
GPX + terrarium DEM（AWS，z12≈38 m/px，25 张瓦片）
  → scene.json（瓦片 base64 内嵌，避开跨域）
  → scene.html（WebGL：250×250 地形 mesh + 轨迹带 + CP 标签 + 相机关键帧）
  → 本地服务逐帧收 JPEG（复用 serve 的 /__frame）
  → ffmpeg 合成
```

命令：`python tools/make_3d.py`；调镜头用 `--still 17 --size 1280x720`。
每片 220 帧分段渲染（Chrome 单次跑完整段会撞上命令行 10 分钟上限）。

### 14.2 五个镜头

| 时间 | 镜头 | 内容 |
|---|---|---|
| 0–3 s | 鹰眼 | 全赛道悬在地形上，轨迹逐步画出，11 个 CP 依次点亮 |
| 3–8 s | 跟拍 | 起点 → CP1 的夜爬（起跑 06:00 天未亮） |
| 8–13 s | 跟拍 | CP2 前后的大下降（-22.6% 连续 1 km） |
| 13–18 s | 跟拍 | CP8 → CP9 的陡爬（2027 同段 6.9%） |
| 18–23 s | 跟拍 | 最后下坡进城（-20.6%） |
| 23–27 s | 夜段 | 时间轴过 21:30，画面压暗、轨迹发光 |

### 14.3 四个坑（都是视觉上能直接看出来的）

1. **16 位索引**：WebGL1 默认不支持 32 位索引，用 Uint32Array 会什么都画不出；
   250×250 网格 = 62.5k 顶点，正好卡在 65535 以内。
2. **轨迹带要逐边采样地形**：横坡上两条边共用一个中心高程，上坡侧会埋进山体，
   渲染出来是一排锯齿缺口。改成左右边缘各自查 DEM。
3. **轨迹要沿程重采样**（每 45 m）：只用 GPX 两端点高程会把中间埋掉。
4. **导出要合成两层画布**：只 `toBlob(WebGL canvas)` 会丢掉 CP 标签和里程尺，
   必须把 2D 覆盖层 drawImage 到合成画布再编码。

### 14.4 已知限制

- 轨迹是 **2026 届**（2027 官方 GPX 未发布），成片常驻「2026 参考轨迹 · 非比赛路线」；
  2027 改线段（CP2–CP8 各差 2.6 km）与实跑路线不一致。
- DEM 38 m/px + 250 网格（约 150 m 单元），只适合看山形与坡度趋势，
  不能用来判断具体某个坡的精确陡度。
- 无音轨、无解说；时长 27 s，扩到 60 s 只需在 `buildShots()` 里加分段。

**2027 GPX 到手后**：覆盖 `data/events/panda-105k-2027/track.gpx`，
`python tools/make_3d.py` 重跑即可，标签与镜头自动跟着新轨迹走。

## 15. 编辑入口与补给计划（2026-11-12，对应 ③⑤）

### 15.1 手机能改，不再依赖电脑

`/event` 底部新增「调整」，两块折叠表单，都走 **POST + 303 回跳**（与装备勾选同一套）：

| 表单 | 字段 | 校验 |
|---|---|---|
| 目标 / 状态 / 起跑 | `goal_h` `status` `start_time` | 10–34 h；状态枚举；HH:MM |
| CP 表 | `km_<idx>` `cut_<idx>` | 里程必须严格递增且小于赛道总长，否则**整表不保存** |

失败不弹 JSON，而是 303 回 `/event?err=…`，页面顶部一条红色横条说明原因——
手机上看到一堆 JSON 等于没提示。

### 15.2 补给计划的模型

`event.fuel_plan()` 按**分段时长**算，不按整天平均：

- 参数（`event.json.fuel`，页面可改）：碳水 75 g/h、水 500 ml/h、钠 500 mg/h、
  自带比例 0.5、携水 1200 ml、CP 停留 3 min、换装点 12 min、气温。
- 每段：碳水 = 速率 × 段时长；其中 `carry_ratio` 部分算「自带」（胶/能量棒），
  其余算「站内吃热食」——全按胶算会得出「背 40 支胶」这种没人这么干的结果。
- 水：`carry_ml = min(需求, 携带容量)`；需求超过容量就警告「中途必须补水」。
- 长段（≥2 h）单独提示确认水源。
- 22 h / 75 g·h⁻¹ 的实测输出：总碳水 1650 g、水 11.0 L、钠 11 g、自带胶 38 支；
  警告集中在 CP6（2.5 h）、CP8（2.7 h）、CP9（2.9 h）三个夜段。

**假设（写清楚了才敢用）**：每个 CP 有水与热食；换装点只有一个（CP5 海窝子）。
若某届赛事不是这样，先改 `course.json` 的 `dropbag` 与 `features`。

### 15.3 换装点

页面直接给 CP5 的换装清单：换鞋袜 / 换上衣加保暖 / 补电解质 / 头灯换电池 /
湿衣物装袋。停留时间取 `dropbag_stop_min`，会吃掉余量——这一点在余量表里已经算进去了
（计划到达是纯行进时间，实际要再加上停留，所以页面同时给出余量，别把停留算漏）。

## 16. 赛中模式：点一下已过 CP，剩下自动重算（2026-11-12）

比赛当天最需要回答的问题不是「我练得怎么样」，而是「我现在还来不来得及」。
所以 `/event` 的余量表在赛中变成可打点的赛况页。

### 16.1 交互

- 起跑点「开始比赛」→ 记下 `start`；
- 每到一个 CP 点「到达」→ 记下当前时间，**该行变灰**并标注「已过 08:08」，
  后面所有 CP 的预测立即重算；
- 点错随时「撤销」；「重置」带二次确认（会清空当天所有打点）。

工具栏同时给出三件事：已用时、已过 n/N、与计划比快/慢多少，以及
「按现节奏能不能保住目标」——需要 1.02× 配速就写 1.02×，保不住就直说。

### 16.2 算法（两个口径，回答两个问题）

| 口径 | 算法 | 回答的问题 |
|---|---|---|
| 平移预测 | 后面每个 CP = 计划到达 + 最后一个已过 CP 的落后量 | 照这个节奏跑，会不会被关门 |
| 保目标倍率 | (目标用时 − 已过 CP 的计划用时) ÷ (目标用时 − 实际用时) | 想保住 22 h，剩下这段得多快 |

**所有比较都用「相对起点的用时」相减，不直接减绝对时刻。** 这条是踩出来的：
第一版用绝对时间相减，手机是 2026 年、计划是 2027 年，落后量算成了 3239 小时。
现在另有保护：落后量 >24 h 时判定为时间基准异常，画面提示检查日期与手机时间。

### 16.3 状态存哪

`data/events/<slug>/race.json`，与 `event.json` 分开：

```json
{"start": "2027-03-27T06:00:00",
 "passed": {"1": "2027-03-27T08:08:00", "2": "2027-03-27T10:32:00"},
 "finished": null}
```

分开的理由：比赛当天的打点要能一键清空，不该和档案混在一个文件里；
`data/` 本身不进仓库，赛后这份记录也不会被推到远端。

### 16.4 已知局限

- 只按**最后一个已过 CP** 的落后量平移，不做逐段配速重估（第 3 段慢了不代表第 5 段也慢）；
- CP 停留没有单独建模：到达时间就是实际时间，停留造成的落后会自然进入下一段；
- 手表数据不会自动同步过来，全靠手点（下一步可做：赛后从活动 splits 对齐核对）；
- 页面时间是打开那一刻算的，停留久了要刷新一次（点任一 CP 会刷新）。

## 17. 多赛事（2026-11-12，对应 ④）

### 17.1 一场变成四场

```
data/events/
  qinling-43k-2026/     2026-11-29  43.0 km / +1500   训练赛（C）
  fuzhou-marathon-2026/ 2026-12-27  42.2 km / +120    B 级目标赛
  sim-60k-2027/         2027-01-16  60.0 km / +2800   专项自测（C）
  panda-105k-2027/      2027-03-27  103.3 km / +5547  主赛（A），有 CP 表
```

每场一个目录，四件东西各自独立：`event.json`（档案）、`course.json`（赛道）、
`gear.md`（装备，每场内容不同）、`race.json`（赛中打点）。

### 17.2 「当前赛事」怎么定

不做「手动指定当前赛事」的持久开关。规则是**按日期自动取下一场**：

```python
active_slug() → nearest_upcoming()      # 日期未过、状态不是 done/cancelled，取最近一场
              → 全过期时取最近一场已完赛
```

理由：指定了就会在赛后继续显示上一场，还得有人记得去改。比赛一过，倒计时自然
切到下一场——11/30 打开 App 看到的就是福州全马，不用操作。

页面上的切换条（`/event?slug=xxx`）只影响这一次渲染，不落盘：
你点开 105K 看装备，看板与教练上下文仍然指向「下一场」。

**所有表单都带 `slug`**：页面能切赛事之后，任何一个表单少这一行都会把 A 场的
目标写到 B 场去。这是这轮最容易出的 bug，`render_page` 里统一用 `HID` 注入。

### 17.3 没有 CP 表的三场怎么办

43K / 全马 / 自测拿不到中途关门时间。三种做法里选了第三种：

| 做法 | 问题 |
|---|---|
| 编一套 CP 与关门 | 会让人按假数据做决策，比没有更危险 |
| 干脆不支持 | 这三场就进不了 App，等于没做多赛事 |
| **单段合成赛道** | 只给总距离/爬升/总用时/补给，余量留空 |

`_synthetic_course()` 把整场压成一段：`km = 总距离, dplus = 总爬升`，终点名就叫
「终点」，`cutoff` 只在 `duration_h` 有值时才填（全马按 6 h 的兜底关门，并标注
「以官方为准」）。`plan_and_margin` 对没有 cutoff 的段返回 `margin_s = None`，
页面显示「—」而不是 0。

**拿到官方关门后**：在页面「调整 → CP 表」里填上，余量立刻出现、黄色的
「这场还没有关门时间」提示自动消失（提示挂在「有没有余量」上，不是「有没有 CP 表」）。

### 17.4 改动清单

- `event.EVENT_SEEDS`：四场种子；`ensure_seeds()` **只补缺不覆盖**（后来新增的
  字段如 `short` / `priority` / `role` 只做填空，不碰用户改过的目标与状态）。
- `list_events(today=)` / `nearest_upcoming(today=)` / `active_slug(slug=None)`；
  所有 `xxx(slug=None)` 的默认值从「写死 105K」改成 `active_slug(slug)`（11 处）。
- `countdown()` 增加 `slug / short / priority / role / has_course / cps`，
  `duration_h` 允许为 None，`tightest` 在无余量时为 None。
- `/event`：顶部赛事切换条；标题与副标题跟着赛事变；单段赛事隐藏「CPn」前缀、
  段落标题叫「赛况」。
- `card.py` / `report.py`：教练横带与看板 chip 都按「下一场」，没有余量时只报
  距离与爬升，不编数字。
- `coach._event_lines()`：同时给【下一场】与【主赛】两段——11/29 的 43K 是训练赛，
  真正在备的是 3 月 105K，只给一条会让模型把训练赛当主赛来安排。
- `run.bat event --list`：列出四场与倒计时，`*` 标出「下一场」。

### 17.5 两个坑

1. **`set_target` 写死 10–34 h**：那是 105K 的范围，43K 设 5.5 h 直接被拒。
   现在范围按规模算：`lo = 距离 × 0.045`，`hi = 关闭时间 or 距离 × 0.5`。
2. **文案里的字面量 `%`**：「长课按比赛配速的 80–90% 执行」用 `%` 格式化会抛
   `ValueError`，而外层 `except` 会把它吞掉——整块赛事上下文静默消失，
   现象是「AI 教练又不知道你在备赛了」。改 f-string，并在 selftest 里断言
   上下文必须含「备赛赛事」。
