# 手机端轨迹回放视频：可行性方案

> 状态：**P0–P2 已实现**（见文末「落地情况」）。
>
> 结论：**能实现**，而且动画本身一行都不用重画——`motion.py` 的播放器
> 已经暴露了 `__motion.seek/frames/ready` 和 `?export=1` 逐帧推帧机制。
> 真正缺的只有「帧 → MP4」这一步：桌面用 ffmpeg，APK 里没有，得换成
> Android 原生 `MediaCodec` + `MediaMuxer`。

## 一、现状：链路已经通了 80%

| 环节 | 桌面 | 手机 | 差距 |
|---|---|---|---|
| 动画 HTML（轨迹 / 照片 / 片段 / 镜头推近） | `motion.render()` | 同一份代码 | 无 |
| 逐帧渲染 | 页面 `?export=1` 把 JPG POST 到本机服务 | 同样能跑 | 只差接收路由 |
| 帧 → MP4 | `ffmpeg -framerate 30 -i f_%05d.jpg …` | ❌ 无 ffmpeg | **要原生编码** |
| 音频混流 | ffmpeg `amix` | ❌ | 二期再说 |
| 素材选择 / 裁剪 | `clip.py`（ffmpeg 转码 + 时间轴） | ❌ | 要重写成原生 |

关键发现：`motion.py` 的 JS 里已经有

```js
window.__motion = { duration, seek: seekTo, play, pause, frames, ready };
```

且 `?export=1` 会让页面自己按 `seek(i/fps)` 逐帧画好、把 JPG POST 到
`/__frame?i=<n>&run=<id>`。**这套东西在 WebView 里原样可用**，只要本机服务
愿意收帧。

## 二、方案：页面推帧 + 原生编码

```text
App 点「生成回放视频」
  └─ appapi.motion_html(id, fps, duration)       # 复用 motion.render()
       └─ 返回 output/motion-<id>.html
  └─ 离屏 WebView 加载 .../motion-<id>.html?export=1&run=<id>
       └─ 页面逐帧 seek + POST /__frame  → serve 落盘 output/_frames/f_00001.jpg
  └─ Python 收到 /__done → run 标记完成
  └─ Kotlin 读帧序列：BitmapFactory → YUV420 → MediaCodec(H.264) → MediaMuxer
       └─ 输出 output/motion-<id>.mp4（1080×1920 · 30fps · 无声）
  └─ 分享 / 存相册
```

### 为什么不让 Kotlin 主动逐帧驱动

`evaluateJavascript("__motion.seek(t)")` 是异步的（内部 `await drawFrame`），
原生拿不到「这一帧画完了」的信号，只能轮询 `window.__frameReady`，每帧两次
IPC，210 帧要多花一倍时间。让页面自己连续推帧，是最快的路径，也是桌面验证过
的路径。

### 编码器（Kotlin，~250 行）

1. `MediaCodec.createEncoderByType("video/avc")`，配置
   `COLOR_FormatYUV420Flexible` + `bitrate≈8Mbps` + `I-frame-interval=1s`；
2. 每帧：`BitmapFactory.decodeFile(jpg)` → `getPixels` → 转 YUV420（I420/NV12
   由 `codecInfo` 决定）→ `queueInputBuffer`；
3. `dequeueOutputBuffer` → `MediaMuxer.writeSampleData`；
4. `1080×1920` 不是 16 的倍数，部分编码器要求宽高对齐到 16：配置时用
   `1088` 再靠 `crop` 或直接试 1080（多数国产机 OK），失败自动降到 `1080×1920`
   的 `720×1280` 兜底。

### serve 新增两条路由（~60 行）

| 路由 | 用途 |
|---|---|
| `POST /__frame?i=&run=` | 收逐帧 JPG（只写 `output/_frames/`，校验 run 号与帧号范围） |
| `POST /__done?from=&run=` | 标记该 run 收帧完成 |
| `GET /media/<name>` | 素材片段给 `<video>` 用（和 `/basemap/` 同一套白名单） |

`/__frame` 只在回环地址开放，且 `run` 必须等于当前任务 id，防止旧页面把帧塞进
新一轮。

## 三、素材裁剪管理（第二期）

### 交互（沿用 `docs/交互树.md` 的规则）

```text
我的 → 素材片段
  ├─ 列表：缩略图 / 文件名 / 时长 / 起止 / 已用
  ├─ ＋ 添加：系统相册选择（PickVisualMedia，不需要存储权限）
  │    └─ 进入裁剪页：VideoView 预览 + 双滑块选起止 + 「保存」
  └─ 长按删除
```

### 无损剪辑（不重新编码）

`MediaExtractor` 读源文件两条轨（视频 + 音频），把起止区间内的样本按
`MediaMuxer` 重新封装：

* 起点吸附到最近的关键帧（否则前几秒会是花屏）；
* 结束点取最后一个 `SAMPLE_FLAG_SYNC` 之后的位置；
* 有音频轨一起搬，保证素材有原声。

代价是起止点可能偏 0.5~2 秒，对「素材点缀」够用，且**几秒就能完成**（不解码）。
需要精确到帧时再走 `MediaCodec` 重编码（第二期不做）。

### 数据与复用

* `data/clips.json`：`{id, path, start, end, name, added_at}`；
* 生成回放时把 clips 读出来传给 `motion.render(..., clips=[...])`——
  这个参数**现在就有**，播放器会把片段按时间轴插进动画；
* 片段文件放 `data/media/`，通过 `GET /media/<name>` 给 `<video>` 用
  （`file://` 和底图一样会被 WebView 拦）。

## 四、分期与工作量

| 期 | 内容 | 代码量 | 风险 |
|---|---|---|---|
| **P0** | 轨迹回放 MP4（无声，1080×1920/30fps） | ~350 行 | 编码器兼容性、出片时长 |
| **P1** | 素材片段：选择 / 裁剪 / 列表 / 参与回放 | ~300 行 | 关键帧吸附的体验 |
| **P2** | 音频：片段原声混入 / BGM | ~200 行 | 无 ffmpeg，要手写 AAC 混流 |

**建议先做 P0**：它已经把「能否在手机出片」这件事验证掉，素材管理是在它之上
的加法。P0 出片后你就能判断画质和耗时能不能接受，再决定要不要 P1。

## 五、风险与降级

| 风险 | 影响 | 降级 |
|---|---|---|
| 编码器不支持 1080×1920 | 出片失败 | 自动降到 720×1280 |
| 逐帧渲染慢（中端机 210 帧） | 等 1~3 分钟 | 降 fps 到 24 / 缩短时长；显示进度条 |
| 帧序列占空间 | 210×~120KB ≈ 25MB | 出片后立即清理 `_frames/` |
| WebView 软件层 draw 偶发黑帧 | 某几帧发黑 | 出片前抽检首尾帧；失败重试一次 |
| 片段无关键帧可吸附 | 起点偏差大 | 提示「建议从整秒开始截取」 |

## 六、验证清单

1. 30 秒回放能出 MP4，`ffprobe`（桌面）看得到 `h264 / 1080x1920 / 30fps`；
2. 帧号连续、无丢帧（比对 `_frames` 数量与 `duration*fps`）；
3. 出片后 `_frames/` 自动清空；
4. 素材片段裁剪后能在动画里按时间轴出现、有原声；
5. 全流程不联网（除底图，且底图可缓存）。

## 七、不做的事

* 不引入 ffmpeg 二进制（APK 会 +20MB，且要按 ABI 分发）——原生编码够用；
* 不做多轨时间轴剪辑（那是剪映的活），只做「片段点缀」；
* 不做云端渲染（破坏本地优先）。


## 八、落地情况（已实现）

| 环节 | 落点 |
|---|---|
| 收帧 | `serve.py` 的 `POST /__frame`、`/__done`、`/__timeline`，落在 `output/_frames/<run>/` |
| 素材/底图 | `GET /data/(basemaps|media|motion_cache)/*`，双白名单 + Range |
| 生成动画 | `appapi.motion_html(id, fps, duration, privacy)`，轨迹时间轴由 `_synth_route()` 现场合成 |
| 编码 | `MotionEncoder.kt`：JPEG → YUV420 → MediaCodec → MediaMuxer，1080×1920 失败自动降 720×1280 |
| 素材剪辑 | `ClipTrimmer.kt`：MediaExtractor 关键帧吸附 + MediaMuxer 无损重封装 |
| UI | 分享对话框「回放视频」；我的页「素材片段」（相册选片 → 双滑块裁剪 → 列表删除） |
| 脱敏 | `none` / `trim` 可生成，`hide` 直接拒绝（没有轨迹就没有回放） |

验证过的部分：帧路由（含越界 400）、页面推帧（Chrome 模拟 8 帧全部落地、JPEG 头正确）、
三档脱敏、`/data/` 底图 200、Kotlin 编译。**编码器与剪辑只能真机验证**。


## 九、排障：真机「一直 0/720 帧」（已修）

现象：点「回放视频」后进度条显示 `生成回放 0/720 帧` 一直不动，最后等满
10 分钟超时。**不是慢**——同一份代码在桌面 Chrome 下 48 帧只要 2 秒
（0.04 秒/帧）；真机 720 帧正常应该在 1–3 分钟量级。

三个原因叠在一起，都不报错：

1. **路径没转同源 URL**。`build_payload` 里的 `base` / `src` 是文件系统绝对
   路径。桌面恰好是 `.../data/basemaps/x.png`，被浏览器解析成 `/data/basemaps/x.png`，
   正好命中服务端白名单；真机是 `/data/user/0/<包名>/files/data/basemaps/x.png`，
   白名单不认，404 → 底图加载不出来。
   → 新增 `motion._web_url()`，`build_payload(web=True)` 时把 `data/` 下的路径
   改成 `/data/...`；`appapi.motion_html` 传 `web=True`。
2. **`toURL()` 给已有前导 `/` 的路径又补了一个 `/`**，拼成 `//data/basemaps/x.png`。
   双斜杠是**协议相对 URL**，浏览器会去访问主机名为 `data` 的地址，请求根本
   到不了 `127.0.0.1`。
   → `if (n.startsWith('/')) return n;`
3. **`ready` 把底图、照片、视频三者绑成硬条件**，任何一项失败都直接 `return`，
   一帧不推也不报错。而分享对话框默认档位、素材视频在 WebView 里加载失败
   都是常见情况。
   → 只把底图当硬条件（缺了整段全黑且帧数齐，导出端发现不了）；照片/视频缺失
   只降级画面质量。

顺带修掉的两个坑：

- `/__done` 用的是 GET，而服务端只在 `do_POST` 里写完成标记 → 标记永远写不上，
  调用方会白等到超时。改为 POST，且原生侧「帧数齐了就走」，不再死等 `done`。
- 新增**诊断回传**：页面启动后 `POST /__diag` 上报 `{base, missing, clips, vidOk}`。
  原生侧读到「30 秒仍 0 帧」就直接给出具体原因（如「底图没能加载：先去
  我的 → 地图底图 配置高德 Key」），不再让人对着转圈猜。

回归断言已加进 `cli.py selftest`：同源路径改写、`toURL` 前导斜杠、
`__done` 用 POST、`ready` 只要求底图。
