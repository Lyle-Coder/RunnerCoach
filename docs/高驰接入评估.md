## 一、为什么值得接

项目当前的数据源是 Garmin 国区（Cookie 会话 + 邮箱验证码）。朋友们如果戴的是高驰手表，就只能手动导出 FIT 再导入。高驰 2026 年起官方开放了数据通路，是运动手表厂商里第一个对个人开发者友好开放的品牌。

## 二、三条通路对比（2026-11 调研）

| 维度 | ① 官方 Open API | ② 官方 MCP Server | ③ 非官方 Web API（抓包） |
|---|---|---|---|
| 入口 | open.coros.com 开发者后台 | `npm install -g coros-mcp`，OAuth 2.1 + PKCE | 社区逆向（coros-training-data 等） |
| 认证 | OAuth2，client_id/secret，需申请（个人可申请，有审核） | 扫码授权，token 自动续期 | 账号密码明文 |
| 数据 | 活动列表/详情（GPS、心率、配速）、训练日历 | 运动（100+ 类型）+ 健康全覆盖：睡眠分期、HRV、血氧、压力、恢复状态、VO2max | 仅运动记录，健康数据拿不到 |
| 稳定性 | 官方维护 | 官方维护（2026 年迭代很勤） | 随时失效，社区方案已归档 |
| 限额 | 未公开细节，申请时确认 | FIT 文件下载 24h 窗口 50 个、单次 ≤10 | 无保障 |
| 适合 | 打进本项目（替换 auth/client 层） | 快速验证数据完整性、个人分析 | 否决 |

## 三、与现有架构的契合度

- **分层友好**：本项目数据入口集中在 `auth.py` / `client.py` / `sync.py`，出图、指标（`metrics.py`）、脱敏（`privacy.py`）、看板/活动图都只认本地 SQLite。接高驰 = 新增一个 `coros.py` 数据源适配层，把活动/时序写进同一套表，**下游全部复用，零改动**。
- **字段映射是主要工作量**：运动类型码（高驰是数字码）、时序点格式（配速/心率/步频/海拔）、 laps 结构、FIT 原始文件解析。Garmin 字段名在库里已 Garmin 化，适配层负责翻译。
- **健康数据**：睡眠/HRV/压力/血氧——Open API 文档需确认覆盖度；官方 MCP 明确全有。若 Open API 缺健康数据，可用 MCP 作为补充通道（本地跑，数据落同一张表）。
- **离线优先不受影响**：同步时联网拉取，落本地库后一切照旧。

## 五、风险与边界

1. **审核与条款**：开发者应用有审核周期；给朋友分发 App 时每人用各自的 OAuth 授权，不共享 key，注意条款里「个人使用 vs 二次分发」的边界。
2. **限额**：FIT 下载 24h 50 个——本项目按需抓明细（`act.ensure` 缓存优先）的现有模式正好契合。
3. **接口演进**：MCP/Open API 都在快速迭代，适配层要留版本字段。
4. **隐私**：OAuth token 与 Garmin 会话同等对待（0600、不进 git、出图前走 `privacy.py`）。

## 六、建议路线

1. **第一步（验证）**：用官方 MCP 拉一次自己的全量数据，确认睡眠/HRV 等字段质量，半天。
2. **第二步（接入）**：Open API 直连，按上表实现；MCP 不打进 APK（需要 Node 运行时，与 Chaquopy 纯 Python 架构冲突）。
3. App 侧仅加一个「数据源：Garmin / COROS」的设置项（设置接口已预留，见 `appapi.set_llm_config` 同级的配置机制）。
