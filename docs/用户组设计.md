> 状态：方案设计，口径已确认，未开始实现。2026-11-16。
> 前提：复用 `server/app.py` 现有账号体系；服务器与 AI 网关同机（阿里云轻量 2C2G）。

## 〇、术语表

> 设计文档、接口注释、界面文案以此为准。**一个概念只用一个词**；
> 中文术语与代码标识符的对应关系固定，新词先加进本表再使用。

### 0.1 组织与角色

| 术语 | 代码 | 定义 | 不要用 |
|---|---|---|---|
| 组 / 跑团 | `group` | 一个训练小组，默认上限 50 人 | 群、圈子；“团队”仅用于“团队营地” |
| 组长 | `owner` | 创建者，唯一可转让与解散 | 群主 |
| 管理员 | `admin` | 组长指定，可踢人、建赛事 | 副组 |
| 成员 | `member` | 普通加入者 | 用户（“用户”指平台账号） |
| 邀请码 | `invite_code` | 8 位加入凭证，可轮换 | 分享码（那是 AI 平台的） |
| 退出 | `leave` | 成员主动离开 | 退群 |
| 移除 | `remove` | 组长/管理员踢人 | 删除 |

## 一、已定决策

| 项 | 结论 |
|---|---|
| 组形态 | 跑团 / 训练小组：周里程排行、成员训练完成度，不做社交动态 |
| 数据粒度 | **仅日汇总**：日期、距离、时长、次数、计划完成度。无轨迹、无心率、无体重 |
| 管理方式 | 只在 App 内：建组、邀请、踢人、换邀请码 |
| 部署 | 与现有 AI 网关同机（同容器同进程，独立 `groups.db`） |
| 身份 | 复用 `/v1/auth` 的手机/邮箱验证码登录与设备令牌，不新建账号体系 |
| 榜单口径 | 只累计**跑步类里程**（跑步 / 越野 / 跑步机 / 徒步）；时长与次数含全部运动 |
| 人数上限 | 默认 **50 人**（创建时可设 2–200） |
| 组内赛事 | **P0 就做**：累计里程 / 次数目标赛事，全组自动参与，完成度直接由日汇总求和 |
| 赛季玩法 | 4 周一季：分头探索 roguelike（局内）+ 团队营地养成（局外），只读训练数据、不要求加练 |

### 非目标（本阶段不做）

- 组内动态流、点赞评论、图片墙
- 轨迹 / 地图 / 路线共享
- 组内训练计划下发与课表同步（P1 再看）
- 教练角色与学员授权（P1，复用成员模型加角色）
- 公开组发现、附近跑团、陌生人社交

## 二、角色与权限

| 角色 | 建组 | 改组名 | 邀请码 | 踢人 | 赛事 | 转让 | 解散 |
|---|---|---|---|---|---|---|---|
| owner | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| admin | ✗ | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ |
| member | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |

- 赛事创建 / 提前结束仅 owner 与 admin；成员只能看完成度，不能改目标。

- **一个人最多同时加入 3 个组**（`MAX_GROUPS_PER_USER`，2026-11 起；早期版本是 1 个）。
  列表页每行显示「本周第 N/M 名 + 里程」，点进去就是那个组的详情。
- **一个人同时只能当 1 个组的组长**：已经是组长时再建组会被拒（409）。
  想建新组，先去原组**转让或解散**。
- 一个组默认上限 **50 人**（客户端建组表单预填 20），可设 2–200。
- **解散**只有组长能做，不可逆：`api_archive` 要求 `confirm=1`，之后
  `groups.archived=1`，列表、排名、赛事都不再出现，成员也看不到。
- **组数上限只数「还没解散」的组**：`group_members` 保留的历史行不算。
  早期按成员行计数的写法会造成「解散了却还是建不了新组」。
- 建组限流 **3 次/天**（防刷）；失败会带着原因回到列表页。
- 组名 2–20 字，简介 ≤ 80 字，禁止空名与纯空白。

## 三、数据边界

### 允许上传

| 字段 | 说明 |
|---|---|
| `date` | 用户本地日期，`YYYY-MM-DD`，不转 UTC |
| `distance_m` | 当日跑步类里程（`running` / `trail_running` / `treadmill_running` / `hiking`）取整 |
| `duration_s` | 当日全部运动总时长 |
| `acts` | 当日运动次数 |
| `plan_done` | `1` 完成 / `0` 未完成 / `null` 当天无计划 |
| `shape` | **路线形状**（2026-11-20 起）：轨迹按累计长度抽稀到 120 点，等比缩放到长边 1000 的相对坐标，`"x,y;x,y;..."`，约 900 字节。仅用于动态卡片画出这次路线——**不配底图、不标起终点** |

### 明确拒绝

- GPS 轨迹点、经纬度、起终点、路线名

> **形状和白名单的关系**（2026-11-20 用户确认）：这一条是**放宽**，所以要把
> 边界写死：出去的是「形状」，不是「位置」。归一化把绝对坐标、朝向基准、
> 起终点、时间全部丢掉了，剩下的只是一条 120 点的相对曲线。它无法反查到
> 具体路段，也不含任何可与其他数据关联的标识。
> 用户的原话是「没有底图，也看不出起终点和经纬度」——这正是实现方式：
> 界面**不配底图**（没有街道可以对照）、**不标起终点**、**不显示坐标**。
> 页面脚注和 `/feed` 正文必须把这三条写明，只写「上传形状」等于隐瞒。
> 只有形状仍然敏感的用户，可以在小组设置里关闭共享（`share_level`），
> 关闭后连摘要都不上传，剪影自然也没有。
- 心率、睡眠、HRV、身体电量原始序列
- 体重、体脂、肌肉量
- 佳明 / 高驰 / Keep 的账号、密码、令牌
- 活动截图、照片

> 组内只回答“练得怎么样”，不回答“练了哪条路”。里程与完成度足够形成激励，
> 轨迹一旦上云就等于交出住址与常跑路线。

### 展示口径

- 组内只显示 `alias`（成员自填昵称，默认“跑友 + 4 位随机”），**永不显示手机号/邮箱**。
- `share_level = off` 时不上报，榜单显示“未共享”，成员仍在组内。
- 榜单注明“数据由各成员设备上报，未做真实性校验”。

## 四、服务端设计

### 4.1 模块划分

```
server/
  app.py          # 现有网关：账号/余额/转发，只加路由分发
  groups.py       # 新增：组、成员、日汇总、榜单（纯标准库 + sqlite3）
  groups_db.py    # 可选：连接与建表；先并入 groups.py 也行
```

`app.py` 的 `do_GET/do_POST` 里以 `path.startswith("/v1/group")` 转发给 `groups.handle()`，
不把组逻辑塞进 1200 行的网关主体。数据库用独立文件 `data/groups.db`，避免与余额流水抢写锁。

### 4.2 表结构

```sql
CREATE TABLE IF NOT EXISTS groups(
  id           INTEGER PRIMARY KEY,
  name         TEXT NOT NULL,
  intro        TEXT NOT NULL DEFAULT '',
  owner_id     INTEGER NOT NULL REFERENCES users(id),
  invite_code  TEXT NOT NULL UNIQUE,
  max_members  INTEGER NOT NULL DEFAULT 50,
  created_at   INTEGER NOT NULL,
  archived     INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE IF NOT EXISTS group_members(
  group_id     INTEGER NOT NULL REFERENCES groups(id),
  user_id      INTEGER NOT NULL REFERENCES users(id),
  role         TEXT NOT NULL DEFAULT 'member',    -- owner/admin/member
  alias        TEXT NOT NULL,
  share_level  TEXT NOT NULL DEFAULT 'summary',   -- summary/off
  joined_at    INTEGER NOT NULL,
  status       TEXT NOT NULL DEFAULT 'active',    -- active/left/removed
  PRIMARY KEY(group_id, user_id)
);
CREATE INDEX IF NOT EXISTS idx_gmember_user ON group_members(user_id, status);

CREATE TABLE IF NOT EXISTS group_daily(
  group_id     INTEGER NOT NULL,
  user_id      INTEGER NOT NULL,
  date         TEXT NOT NULL,
  distance_m   INTEGER NOT NULL DEFAULT 0,
  duration_s   INTEGER NOT NULL DEFAULT 0,
  acts         INTEGER NOT NULL DEFAULT 0,
  plan_done    INTEGER,
  updated_at   INTEGER NOT NULL,
  PRIMARY KEY(group_id, user_id, date)
);
CREATE INDEX IF NOT EXISTS idx_gdaily_board ON group_daily(group_id, date);

CREATE TABLE IF NOT EXISTS group_challenges(
  id           INTEGER PRIMARY KEY,
  group_id     INTEGER NOT NULL REFERENCES groups(id),
  title        TEXT NOT NULL,
  kind         TEXT NOT NULL,          -- distance/acts/elevation/explore/speed
  target       INTEGER NOT NULL,
  start_date   TEXT NOT NULL,          -- 本地日期，含当天
  end_date     TEXT NOT NULL,          -- 本地日期，含当天
  created_by   INTEGER NOT NULL REFERENCES users(id),
  created_at   INTEGER NOT NULL,
  closed_at    INTEGER,                -- 提前结束；NULL 表示未手动结束
  archived     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_gchal_group ON group_challenges(group_id, end_date);

CREATE TABLE IF NOT EXISTS group_audit(
  id           INTEGER PRIMARY KEY,
  group_id     INTEGER NOT NULL,
  actor_id     INTEGER NOT NULL,
  -- create/join/leave/remove/rotate/transfer/archive
  -- challenge_create/challenge_close
  action       TEXT NOT NULL,
  target_id    INTEGER,
  ts           INTEGER NOT NULL
);
```

要点：

- 同一个人加入 3 个组会在 `group_daily` 存 3 份汇总（每行约 100 字节），换组隔离更干净，不做跨组视图。
- `date` 用本地日期字符串，服务器**不做时区换算**，否则“今天”会错位。
- `group_audit` 只记管理动作，不记上报明细，避免变成行为日志。

### 4.3 API 契约

所有接口都在 `Authorization: Bearer <device_token>` 下调用；令牌校验复用现有 `_device()`。

| 方法 | 路径 | 说明 |
|---|---|---|
| PATCH | `/v1/group/{id}` | 改组名 / 简介 / 人数上限（owner/admin） |
| POST | `/v1/group/create` | 建组，创建者自动成为 owner |
| POST | `/v1/group/join` | 用邀请码加入 |
| GET | `/v1/group/list` | 我加入的组（含未读数留空） |
| GET | `/v1/group/{id}` | 组信息 + 成员 + 我的角色；邀请码仅 owner/admin 可见 |
| POST | `/v1/group/{id}/report` | 批量上报日汇总（幂等 upsert） |
| GET | `/v1/group/{id}/board` | 周/月榜 |
| POST | `/v1/group/{id}/leave` | 退出组 |
| POST | `/v1/group/{id}/invite/rotate` | 换邀请码（owner/admin） |
| POST | `/v1/group/{id}/member/{uid}/remove` | 踢人（owner/admin） |
| POST | `/v1/group/{id}/transfer` | 转让组长（owner） |
| POST | `/v1/group/{id}/archive` | 解散（owner，需二次确认） |
| POST | `/v1/group/{id}/challenge/create` | 建赛事（owner/admin） |
| GET | `/v1/group/{id}/challenge/list` | 进行中 + 已结束的赛事 |
| GET | `/v1/group/{id}/challenge/{cid}` | 赛事完成度榜 |
| POST | `/v1/group/{id}/challenge/{cid}/close` | 提前结束（owner/admin） |

#### 建组

```json
→ {"name":"秦岭跑团","intro":"周末上山","max_members":50}
← {"ok":true,"group":{"id":7,"name":"秦岭跑团","invite_code":"QINL8X2K","role":"owner"}}
```

#### 加入

```json
→ {"invite_code":"qinl8x2k","alias":"老李"}
← {"ok":true,"group":{"id":7,"name":"秦岭跑团","role":"member"}}
```

错误：`404 邀请码无效`、`409 组已满`、`409 已在该组`、`409 已在其他组（需先退出）`、`403 账号未完成绑定`。

#### 上报

```json
→ {"days":[
     {"date":"2026-11-15","distance_m":5005,"duration_s":1629,"acts":1,"plan_done":1},
     {"date":"2026-11-14","distance_m":17122,"duration_s":28709,"acts":1,"plan_done":1}
   ]}
← {"ok":true,"saved":2,"skipped":0}
```

- 单次最多 60 天，日期不得晚于服务器今天 +1 天。
- 数值上限：`distance_m ≤ 300000`、`duration_s ≤ 86400`、`acts ≤ 10`。
- `share_level=off` 时直接返回 `{"ok":true,"saved":0,"skipped":N}`，不落库。
- 幂等：同一 `(group_id, user_id, date)` 覆盖更新，重复上报无副作用。

#### 榜单

```
GET /v1/group/7/board?range=week
← {"ok":true,"range":"week","from":"2026-11-10","to":"2026-11-16",
   "rows":[
     {"user_id":12,"alias":"老李","is_me":true,"distance_m":23000,
      "duration_s":7200,"acts":4,"plan_done":3,"plan_total":5},
     {"user_id":19,"alias":"小赵","is_me":false,"distance_m":18500,
      "duration_s":6000,"acts":3,"plan_done":2,"plan_total":4}
   ]}
```

- 周口径：**周一 00:00 起**，按 `date` 字符串区间取，不依赖服务器时区。
- 排序：`distance_m` 降序 → `acts` 降序 → `alias` 字典序。
- `plan_total` = `plan_done` 非 NULL 的天数；完成率 = `plan_done=1` / `plan_total`，无计划显示 `—`。
- 只返回 `status=active` 且 `share_level=summary` 的成员。

### 4.4 组内赛事（P0）

**形态**：组内累计目标型赛事，**全组自动参与**，不设报名表、不发奖励。

| 项 | 规则 |
|---|---|
| 类型 | `distance` 累计里程（存米）/ `acts` 累计次数 / `elevation` 累计爬升（米）/ `explore` 新踩格子（格）/ `speed` 平均配速（秒/公里） |
| 目标 | 里程 1–1000 km（存米，界面按公里输入）/ 次数 1–200 / 爬升 100 m–300 km / 格子 5–5000 / 配速 2'30"–15'00"（存 150–900 秒） |
| 周期 | `start_date`–`end_date`，含两端，最长 90 天；开始日不得早于 7 天前 |
| 并发 | 同一组同时进行最多 3 个；已结束的保留可查 |
| 完成度 | 直接 `SUM(group_daily)` 在周期内的对应列（`distance_m` / `acts` / `elevation_m` / `explorer`），**不另建完成度表** |
| 配速 | 全组加权平均 = `SUM(duration_s) / SUM(distance_m)`，取秒/公里；完成度 = 目标 ÷ 当前（越小越好，进了目标即 100%） |
| 状态 | 不依赖定时任务：`closed_at IS NULL AND end_date >= 今天` 即进行中 |
| 结束 | 到期自动视为结束；owner/admin 可提前关闭 |
| 排序 | 已达成按达成日期升序在前，未达成按完成率降序 |

#### 建赛事

```json
→ {"title":"本周 10 公里挑战","kind":"distance","target":10000,
   "start_date":"2026-11-16","end_date":"2026-11-22"}
← {"ok":true,"challenge":{"id":3,"title":"本周 10 公里挑战","kind":"distance",
   "target":10000,"from":"2026-11-16","to":"2026-11-22"}}
```

错误：`409 同时进行的赛事已达 3 个`、`400 周期超过 90 天`、`400 起始日早于 7 天前`。

#### 完成度榜

```
GET /v1/group/7/challenge/3
← {"ok":true,
   "challenge":{"id":3,"title":"本周 10 公里挑战","kind":"distance","target":10000,
                "current":18500,"pct":100,
                "from":"2026-11-16","to":"2026-11-22","status":"running"},
   "rows":[
     {"alias":"老李","is_me":true,"current":12300,"pct":100,"done_at":"2026-11-18"},
     {"alias":"小赵","is_me":false,"current":6200,"pct":62,"done_at":null}
   ]}
```

- `challenge.current / pct` 是**全组**进度：页面头部要用（组页那张卡只有合计，
  详情页要说清「这场打到哪了」）。速度类不能用每人配速求平均（平均的平均），
  必须用总时长 ÷ 总距离现算。
- `done_at`：按日累计首次 ≥ 目标的那一天；未达成返回 `null`。
- `share_level=off` 的成员不出现在 `rows`，组内显示“未共享”，不参与排名。
- 只统计 `status=active` 的成员；`group_daily` 里没有的日期按 0 计。
- 达成后只显示“已达成”徽章，不发积分、不发实物——避免催生刷数据。

**取舍**：不做报名、不做对手匹配、不做组间赛。赛事是“给一个共同目标”，
复杂度一旦上来（报名、分组、结算、奖励）就会吃掉 P0 的工期。

> P0 的完成度依赖成员**打开 App 才上报**，长期不打开的人榜单会滞后（最多一天）。
> 这是“不上后台任务”的直接代价，P1 接 WorkManager 后改为每日后台补传。
> 赛事页要显示每人的“数据更新于 X”，避免把滞后误读成没跑。

### 4.5 限频与风控

| 动作 | 限制 |
|---|---|
| 加入组 | 同账号 10 次/小时，同 IP 30 次/小时 |
| 建组 | 同账号 3 个/天；已在组内时不能建组 |
| 上报 | 同账号 60 次/小时 |
| 换邀请码 | 同组 10 次/天 |
| 建赛事 | 同组 5 个/天 |

沿用网关现有 `Gate` 异常风格统一返回 `{"ok":false,"error":"..."}`，不新增框架。

## 五、App 端设计

### 5.1 登录态：这是最容易踩的坑

现状：`platform_token` 存在 AI 设置里，语义是“AI 网关令牌”。用户组要用同一个令牌，
但如果沿用现在的入口，**用户关掉 AI 平台模式后就找不到登录口，也进不了组**。

改造：

1. 配置里新增账号级字段 `account_token` / `account_label`；
2. 首次读取时若 `account_token` 为空、`platform_token` 非空，自动迁移（幂等，只做一次）；
3. AI 平台模式改为读 `account_token`，旧字段保留一版做兼容；
4. 「我的」页新增一行「账号」：未登录 → 手机/邮箱登录；已登录 → 脱敏账号 + 退出；
5. 任何需要组的操作发现未登录，直接拉起同一个登录框，登录成功后回到原操作。

> 服务器 `/v1/auth` 不变（新号自动注册并送试用额度），组功能不读余额。

### 5.2 页面

P0 不新增底部导航，入口放在「我的 → 训练小组」，页面内三态：

```
组列表（我的组 / 加入 / 创建）
  └ 组详情
       ├ 我的名次 + 本周玩法（目标 / 让分赛 / 预言）
       ├ 本周榜（只排前 10，我排 10 名外时补一行）
       ├ 完整榜单（/groups/{id}/board，周 / 月在同一页切换）
       ├ 赛事（每张卡可点 → /groups/{id}/challenge/{cid} 看每人成绩）
       └ 大家的动态（最近 20 条，底部续加载；评论在卡片里展开）
```

- 组页榜单只放前 10：人一多，十几行榜单会把动态推到第三屏之后。完整名次和
  月榜都在 `/board`，口径切换不过组页——在 200 KB 的组页上重载一次只为换聚合
  口径，动态会被重刷、滚动位置也会丢。
- 月榜只排里程：六件衫和探索徽章都是**按周**结算的，挂到月榜上会被读成
  「这个月的衫」。

- 建组：名称 + 简介 + 人数上限。
- 加入：粘贴邀请码或扫码（二维码内容就是 8 位码，扫码复用现有相机/剪贴板能力）。
- 成员行：昵称、角色、本周里程、共享状态；owner/admin 左滑或长按出「踢出」。
- 我的共享开关：`summary` / `off`，关闭后立即停止上报并在榜单显示“未共享”。
- 赛事卡：顶部显示进行中的赛事（标题、我的 `current / target`、剩余天数、完成度条），
  点进去是按人排的完成度榜；owner/admin 底部有「新建赛事」与「提前结束」。
  已完成显示“已达成”，不发积分与实物。

### 5.3 上报队列

本地新增：

```sql
CREATE TABLE IF NOT EXISTS group_outbox(
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  group_id  INTEGER NOT NULL,
  payload   TEXT NOT NULL,
  tries     INTEGER NOT NULL DEFAULT 0,
  next_at   INTEGER NOT NULL DEFAULT 0
);
```

- 触发时机：App 进入前台、下拉刷新、数据刷新完成、进入组页面。
- 上报范围：最近 14 天；**首次加入组补 30 天**（让新成员立刻有榜可看）。
- 失败退避：1m → 5m → 30m → 2h，最多 8 次，之后等下次前台再试。
- 成功即删队列行；同一组同一批数据重复提交由服务端幂等兜底。
- 不做后台定时任务（P0），避免又加一个前台服务；WorkManager 留到 P1。

### 5.4 数据来源（已核对现有字段）

- 活动：`derive(store, today)["activities"]`，字段 `date` / `type` / `distance_m` / `duration_s` 齐全。
- 日汇总：按 `date` 聚合，跑步类累计里程，全部运动累计时长与次数。
- 计划完成度：`plan.attach()` 后的 `week[].done`；拿不到计划时传 `null`，不要伪造成 0。

## 七、部署与容量（阿里云轻量 2C2G）

### 7.1 结论

够用。组接口是轻量 SQLite 读写；1 万账号、10% 日活、每天一次上报 ≈ **0.012 QPS**。
汇总行约 100 字节，1 万人一年约 365 MB。真正的资源消耗仍是 AI 转发的 SSE 长连接。

### 7.2 配置建议

| 项 | 建议 |
|---|---|
| 规格 | 2C2G，系统盘 40G+ |
| 带宽 | 3–5 Mbps（只传 JSON 足够；图片一律走 OSS） |
| 运行时 | 同一容器同进程；`groups.db` 独立文件，WAL + `busy_timeout=5000` |
| 并发 | 网关整体并发上限 30–50，给组接口留线程 |
| HTTPS | nginx + Let's Encrypt，certbot 自动续期 |
| 备份 | 每日 `sqlite3 .backup` → OSS，保留 30 天；`/admin/db` 可手工快照 |
| 监控 | `/health` 增加组计数；轻量自带监控够用 |

### 7.3 上线前置条件（容易漏）

- **备案**：国内地域的 80/443 必须备案。没有备案域名时选香港/新加坡地域（免备案，
  延迟 +30ms 左右），或先用非标准端口 + 自签证书（Android 需额外信任配置）。
- **域名**：App 的 `base_url` 支持直接填域名，换机只改 `.env` 的 `RC_PUBLIC_BASE`。
- **时间**：Pn 全部按本地日期，服务器 NTP 必须准（偏差 >5 分钟会导致验证码与榜单口径错）。

## 九、分期与验收

### P0（约 4–5 人日）

建组 / 邀请码 / 加入 / 退出、日汇总上报与离线补传、周榜、
**组内赛事（建 / 完成度榜 / 提前结束）**、共享开关、隐私文案。
验收：

- 两个账号在两台设备上能建组、加入、看到彼此本周里程。
- 断网时上报进队列，恢复后补传成功且不重复。

多榜（6 衫 + 探索徽章）、让分赛（结对版）、预言投票、Bingo 卡、赛季隐藏分与称号。

### P3（约 3–4 人日）· 运营与分享

组长 Web 管理页、数据导出、教练角色、优质路线分享（主动授权才上传轨迹）、

## 十、已确认口径

2026-11-16 确认，不再作为开放问题：

1. **榜单只累计跑步类里程**（跑步 / 越野 / 跑步机 / 徒步）；时长与次数含全部运动。
   骑行与力量训练不进里程榜，避免不同运动的里程混在一起比。
2. **组人数上限默认 50**，创建时可设 2–200；**一人只能加入 1 个组**，不做多组并行。
3. **组内赛事进 P0**：累计里程 / 次数目标赛事，全组自动参与，完成度由日汇总求和，
   不设报名、不设奖励，达成只显示徽章。
4. 本设计文档**暂不提交 git**，留在工作区评审；实现开工前再决定是否随代码入库。
5. **营地做团队共享**，个人休整点贡献在成员页可见；增益全组共享、下季生效。
6. **休整点累积不清零**，团队池上限 = 40 × 有效成员数，满后提示去升级；
   升级成本 = 人均成本 × 有效成员数，避免大组升级过快。
7. **营地等级显示为组名后缀** `· Lv3 营地`，由客户端拼接，不写进 `groups.name`。

## 十一、赛季与远征玩法

> 2026-11-16 讨论定稿。核心原则：**远征只读取训练数据，不要求额外跑量**。

### 11.1 世界观与赛季结构

**《雪线之前》**：山那边的护林站入冬后封路半年。每年初雪前，镇上组一支“送冬队”，
把盐、药、信件与种子送过去。四幕对应四段路：

| 幕 | 周 | 路段 | 主题 | 关键岔路 |
|---|---|---|---|---|
| 一 | 1 | 河口镇 → 老鹰嘴 | 信任 | 请老背夫，还是只带地图 |
| 二 | 2 | 老鹰嘴 → 采药人小屋 | 代价 | 救掉队的驴友，还是赶路 |
| 三 | 3 | 小屋 → 冰河 | 取舍 | 走冰面，还是绕山腰 |
| 四 | 4 | 冰河 → 望雪站 | 选择 | 轻装冲顶，还是保物资 |

设定与机制一一对应：界桩 = 推进一格；无线电 = 揭示前方；队旗 = 士气（旗垂即士气低）；
旧日志 = 遗迹（3 处解锁隐藏结局）；初雪提前 = 赛季时间压力。**不做任何超自然解释。**

**段目标按周动态累加**：

每周一算一次“本周团队应完成格数” = Σ 成员本周目标 ÷ 5 × 0.8；
段目标 = 各周应完成量累加，**不预设绝对格数**。

| 幕 | 路段 | 50 人组参考值 |
|---|---|---|
| 一 | 河口镇 → 老鹰嘴 | 约 200 格 |
| 二 | 老鹰嘴 → 采药人小屋 | 累计约 400 格 |
| 三 | 小屋 → 冰河 | 累计约 600 格 |
| 四 | 冰河 → 望雪站 | 累计约 800 格 |

参考值按人均周跑 25 km 估算，只用于文案与预估。真正判定用动态值：全组减量周，
段目标同步降低，避免“科学减量反而走不完”与教练定位冲突。

四幕是**四段路，不是四个星期**：每周结算看团队落在哪一段，强队可能 3 周走完，
弱队 4 周停在第三段——这正是“初雪倒计时”的压力来源。段目标按人数等比缩放。

**0.8 这个系数不是随手写的，改它会直接毁掉整个玩法**（实测见
`preview/story/balance-report.md` 第三轮）：

| 系数 | 5 人团抵达 | 10 人团 | 50 人团 |
|---|---|---|---|
| 0.70 | 92% | 95% | 90% |
| **0.80** | **81%** | **84%** | **86%** |
| 0.90 | 37% | 31% | 35% |
| 1.00 | 1% | 0% | 0% |

0.8 → 0.9 是断崖（86% 掉到 35%），没有中间态。因为实际执行率的中位数是 0.875，
0.8 的容错刚好吃掉「偶尔一周没跑满」，0.9 就要求人人超额。

#### 小团（5–10 人）的额外规则

段目标按人数等比缩放，所以 5 人团和 50 人团是**同一套判定口径**，不会出现
「大团随便走完、小团永远走不完」。但小团有两个独有风险，必须单独处理：

1. **单个划水者的权重被放大 10 倍**。5 人团里 1 个人不来 = 20% 的目标没人完成，
   50 人团里同样 1 个人只占 2%。不处理的话实测 5 人团抵达率从 79% 掉到 **14%**。
2. **人数少导致方差大**。同样 13% 的缺口，50 人团还有 53% 能抵达，8 人团只剩 30%。

处理办法是**自动剔除长期不活跃者**，而不是踢人或催办：

| 规则 | 说明 |
|---|---|
| 判定 | 单周产出 < 1 格记为「本周没动」 |
| 剔除 | 连续两周都 < 1 格，从**目标分母**里扣掉，不产格也不算目标 |
| 恢复 | 任何一周跑够 1 格立即恢复计入，不通知、不通报 |
| 存档 | 仍留在队伍列表里，只是不参与本季判定 |

这是对「暂停者从分母扣除」的自动兜底——文档原本只写了手动暂停，但现实中
多数人不会主动点按钮，只是默默不跑了。剔除之后 5 人团 1 人划水的抵达率从
14% 回到 **80%**，2 人划水从 0% 回到 82%，与 50 人团收敛到同一区间。

**不惩罚团队的理由**：让 4 个人替 1 个不来的人跑完，与「不催办、不加练、
完成八成算八成」的定位直接冲突。数值能兜底的部分兜住，剩下的交给社交——
人少的时候谁没来，本来一眼就看出来，不需要系统再扣一次分。

**团队进度 = 所有成员贡献行程之和**；赛季目标 = 四周动态段目标的累加，
不再固定为“人均 20 格”。不取平均：多走一格就多一分，冒险与救援才有正反馈。

事件权重按幕分段：第一幕补给事件多（攒资源），第二、三幕试炼多（消耗），
第四幕叙事多（收束）。每季事件池 30 条左右，服务端 JSON 下发，换季不发版。

### 11.2 局内：分头探索

#### 赛季生命周期

| 节点 | 规则 |
|---|---|
| 开赛 | 每周一 00:00 自动开新赛季，不提供手动开赛（避免把周四当周一） |
| 中途加入 | 当周即可上报里程、计入团队行程；**岔路与事件从下一个周一起参与**，不补历史 |
| 退出再加入 | 退出后当季行程作废；加入新组按“中途加入”处理，不继承任何进度 |
| 结算 | 第 4 个周日 23:59 封账，按位置判结局、发称号 |
| 下季 | 营地等级与休整点继承；个人行程、补给、增益清零 |

中途加入的周目标按剩余天数折算：整周目标 × 剩余天数 ÷ 7，避免周三入组就背一整周的量。

#### 通知

服务端不做推送（2C2G 不跑推送服务），只提供待办状态，由 App 本地提醒：

| 时点 | 形式 |
|---|---|
| 周一 08:00 | 开周提醒：本周事件、岔路、个人目标 |
| 周日 20:00 | 结算提醒：还差多少格 |
| 受困后 24h | 救援请求：只推给未受困成员 |
| 赛事开始 / 结束 | 组内卡片 + 红点 |

App 每次前台刷新拉一次 `/v1/group/{id}/state`，有未读即标红点。

#### 最低活跃提醒

队伍会缩水，但系统**不催人、不点名、不惩罚**，只如实报数。

| 触发 | 文案 | 位置 |
|---|---|---|
| 有成员连续 2 周产出 < 1 格 | 「本周还有 N 人没动」 | 队伍页提示条 |
| 活跃 ≤ 总人数 60% | 「队伍只剩 N 人在走」 | 队伍页提示条 |
| 活跃 < 3 人 | 「只剩 N 人，后面的路会很难」 | 队伍页提示条 + 组卡角标 |

**为什么阈值是 60%**：实测正常情况下（没有人长期不跑）触发率是 **0%**——
放在 5 人团上是「5 人剩 3 人」，10 人团是「剩 6 人」，50 人团是「剩 30 人」。
也就是说它只在真的掉了一半人时才响，不会因为一次出差、一个休息周就报警。

反过来，5 人团掉 1 个人（剩 4 人，80%）**不提示**。这很重要：小团偶尔少一个人
是常态，一少人就弹提示，反而显得系统在指责没来的人。

**三条硬规矩**：

1. **不点名**。提示只报数字。谁没来是一眼能看出来的事，不需要系统公开处刑。
2. **不催办**。没有「快去跑步」「队伍需要你」这类话。提示只描述状态，不要求行动。
   与「完成八成算八成、不加练」的定位一致。
3. **不给建议**。不提示「请补人」「请降低目标」。人数少时怎么处理是队伍自己的事。

队长视角可以额外看到一个「本周未上报」的名单（仅队长可见，只显示有没有上报，
不显示原因——受伤和偷懒在系统里不该被区分对待）。

#### 周循环

| 时点 | 发生什么 |
|---|---|
| 周一 | 开周：抽 1 个本周事件（试炼/补给/叙事）+ 1 个岔路，显示个人目标 |
| 周内 | 跑步累计，每 5 km 记 1 格，封顶 = 本周目标；完成试炼 +2 格 |
| 周日 | 结算：个人行程 → 团队行程 → 判段目标 → 推进地图 → 解锁下周事件 |

**里程换格**

```
个人行程 = min(周里程, 周目标) / 5        ← 基础
         + 完成试炼 ? 2 : 0               ← 质量加成
         + 事件奖励                       ← 补给 / 叙事
团队行程 = 所有人个人行程之和
```

超额里程不计格，但照常进里程榜——不让“为了推进”变成加练的理由。

#### 初雪倒计时

赛季的时间预算固定 **28 天**（4 周）。初雪会提前 0–5 天来临，越早越难：

| 提前 | 概率 | 第四幕可用天数 |
|---|---|---|
| 0 天 | 28% | 7 天（满额） |
| 1 天 | 24% | 6 天 |
| 2 天 | 20% | 5 天 |
| 3 天 | 14% | 4 天 |
| 4 天 | 9% | 3 天 |
| 5 天 | 5% | 2 天 |

**初雪只压缩最后一段，不判死前面**。第三幕结算时已经走完的路不会回退，
被砍掉的只是「第四幕还能跑几天」——所以它问的是「最后一程赶不赶得上」，
而不是「前面全白走」。后者会让人当场退游。

被压缩的那几天，训练量和事件推进同比例折算。实测 88% 的季会被雪截掉
至少一天，但抵达率仍有 78%：因为正常玩家有约 10% 的超额，用来垫这一两天。

**这组概率是从 0–4 天调严来的**（原 35/25/20/12/8）。原来的版本 50 人团抵达
84%、迷失只有 5%，等于没有失败风险，倒计时成了背景板。调严后 78% / 12%；
同时 `smart`（78%）仍明显高于 `safe`（71%），说明「看天色做决定」有回报，
不是单纯拉高难度。

| 方案 | 平均提前 | 50 人抵达 | 50 人迷失 | 5 人抵达 | 10 人抵达 |
|---|---|---|---|---|---|
| 宽松 0–3 | 1.00 | 89% | 0% | 84% | 90% |
| 原案 0–4 | 1.33 | 84% | 5% | 80% | 83% |
| **现行 0–5** | **1.67** | **78%** | **12%** | **76%** | **76%** |
| 很严 0–7 | 2.26 | 70% | 20% | 66% | 65% |
| 必提前 1–5 | 2.48 | 72% | 18% | 68% | 66% |

再往后（0–7 天）失败率破 20%，小团掉到 65%，那是「运气比努力重要」的区间，
不建议。0–3 天则完全没有失败风险。**0–5 是唯一同时满足「有压力」和
「小团不掉队」的档位。**

**「等一晚」是唯一能动用时间预算的选择**。有 `time` 字段的选项会消耗天数：

| 事件 | 选项 | 消耗 |
|---|---|---|
| 四幕 `first_snow` | 等到明天 | 1 天 |
| 二幕 `hiker_again` | 抬他一起走 | 1 天 |

代价是真实的：第四幕本来只剩 3–7 天，等一晚就少一天的路。收益是补给 +1、
士气 +1，而且**队伍停在原地，本幕不会受困**——所以它是一个避险选项，
不是纯亏的拖延。

实测这个取舍是有效的：初雪没提前时（28% 的季）理性玩家会等一晚补物资，
初雪已经在路上时（72%）会立刻动身。两个选项的选中比例约 1:3，
既不是无人问津，也不是一边倒。

#### 本周目标从哪来

| 情况 | 目标来源 | 默认值 |
|---|---|---|
| App 内有训练计划 | 计划本周跑步类总里程 | 直接取，不由用户改 |
| 有外部计划、没录入 | 周初自报 | 近 4 周周均 × 0.8 |
| 完全没有计划 | 系统建议 | 近 4 周周均 × 0.8，可改 |

三条硬规则，保证不与原始计划冲突：

1. **只读不写**：远征只读 `plan.json`，绝不修改课表、不生成训练建议、不推送“该跑多少”。
2. **只能下调，不能上调**：周中可改小目标（受伤、出差、临时减量），不能改大，
   防止为了团队多拿几格而加练。
3. **目标只是上限**：完成 80% 拿 80% 的格；未完成不扣分、不催办、不进榜单。

特殊情况：减量周目标随计划降低，不补偿；比赛当天里程全额计入且不受封顶限制；
受伤/出差可点“暂停”，目标记 0、不产格，并从团队应完成量的分母中扣除。

**跑团活动联动**：周末约跑（组长发起“集结”）当天里程按 1.5 倍计入行程；
组内赛事完成 → 直接触发一次补给事件；有人跑比赛 → 全组士气 +2、当周团队行程 +10%。

**两个资源**

| 资源 | 范围 | 归属 | 作用 |
|---|---|---|---|
| 补给 | 0–10 | 个人 | 走险路的门票；<2 时高风险选项不可选 |
| 士气 | 0–10 | 团队 | 全组贡献加成，每 3 点 +5%，上限 +15% |

补给是个人消耗（各走各的路），士气是全组共享的一面队旗——救援能加士气，但补给要自己出。

**士气的增减**（2026-11-17 数值实测后补，见 `preview/story/balance-report.md`）：

| 时点 | 变化 |
|---|---|
| 受困 | 每 1 人全组 −1，单幕最多 −3 |
| 该幕试炼失败率 > 40% | 全组 −1（一个人失败不扣，一群人失败才扣） |
| 团队过半选了「抛下队友」 | 终局 −1 |
| 团队过半选了「救人」 | 终局 +1 |

没有消耗路径时士气只涨不跌，「绕行」结局会永远触发不了——实测四幕八次岔路里
只有 1 个选项扣士气，理性玩家永远选利他那项，士气冲到满值。所以受困和群体失败
必须计入团队士气，这既是机制需要，也符合「队伍散了就走不到」的叙事。

**岔路规则**（每幕 2–3 个）

1. 全组看到同一段描述与两个分支，**每个人独立选择**。
2. 选择前**实时显示当前占比**（如 32 人走安全 / 18 人走冒险），允许从众。
3. 选定后进入对应支线，各自抽 1–2 个事件；支线尽头即汇合点。
4. **超时不做决定**：本幕行程记 0，人留在原地，下幕照常参与；不默认、不代选。
5. 汇合点展示：选择占比、各人结果、受困名单。

支线内事件的权重：

| 事件 | 权重 | 效果 |
|---|---|---|
| 试炼 | 40% | 本周内完成一条质量试炼；成功 +3 格 +1 士气，失败 −1 补给 |
| 补给 | 35% | +2 补给 / 贡献上限 +2 km / 揭示前方 3 格 |
| 叙事 | 25% | 二选一分支，改写后续事件池，记录遗迹 |

#### 质量试炼（不增加跑量）

试炼只提高“精度”要求，距离仍是常规训练量。**判定由服务端做，不由用户自评。**

客户端只从 `activity_detail.laps` 里抽**原始分圈**（每圈的 `dist_m` / `dur_s` /
`cad` / `hr_avg` / `ele_gain`，最多 3 条候选活动），随 `/run/trial` 一起交。
服务端按上表逐条重算——交结论等于没交，改个包就全过了。

| 试炼 | 判定 | 难度 |
|---|---|---|
| 渐加速 5 km | 后 2.5 km 比前 2.5 km 每公里快 ≥15 s | 中 |
| 匀速 6 km | 每公里配速与均值的偏差 ≤5 s | 中 |
| 负分割 10 km | 后半程比前半程快 ≥30 s | 高 |
| 稳定步频 5 km | 每公里步频标准差 ≤3 spm | 中 |
| 心率不漂移 8 km | 后半程平均心率比前半程高 ≤5 bpm | 高 |
| 爬坡节奏 | 爬升 ≥200 m，且没有低于 6:30/km 的步行段 | 高 |

判定门槛：至少 3 个整圈且每圈 ≥200 m；距离允许短 5%（GPS 少算）；
**只截前 `distance_km` 这段**——跑 10 km 去应 5 km 的试炼，后半程再漂亮也不算。

三档结论，不是两档：

| level | 条件 | 奖励 |
|---|---|---|
| `verified` | 证据齐、逐条算过、达标 | 全额（格 / 士气 / 增益） |
| `failed` | 证据齐、算出来没达标 | 按失败（扣补给，可能受困） |
| `unverified` | 判不了（室内没圈、手表没同步） | 格数对折，不给士气与增益 |

`unverified` 是刻意留的：一刀切判失败会把“真跑了但手机没数据”的人罚掉，
比自评更伤。但随手点一下和跑完回来拿的东西必须不一样，否则这机制只是装饰。

周日 23:59 未完成即判定失败，扣 1 补给，不追溯、不补做。**不存配速明细**：
判完即弃，只留 `activity_id` 与 `level`。

#### 受困与救援

- **受困**：冒险支线末端试炼失败且补给 <2 → 本幕行程冻结，不计入团队进度。
- **全组透明**：谁受困、谁正在前往救援，实时显示在汇合点；不隐藏、不匿名。
- **救援窗口**：汇合点开启后 24 小时。
- **救援成本**：−1 补给、−1 格个人行程；受困者行程保留。
- **救援回报**：救援者 +1 士气，全组 +1 士气，得 `helper` 标签。
- 每人每幕最多救 1 人，不能自救；**救援不计榜单与赛季分**。
- 多人同时救同一人：先到先得，后到者成本原样退回；救援者自己已受困时不能救。
- 不救：下幕自动归队，行程清零，不退组、不扣分。

**结局**（赛季末判定）

| 结局 | 键 | 条件 |
|---|---|---|
| 抵达 | `arrive` | 团队行程达标且士气 ≥ 3 |
| 绕行 | `detour` | 团队行程达标但士气 < 3 |
| 少一个人 | `missing` | 团队行程达标，但有人赛季结束时还困在雪里 |
| 迷失 | `lost` | 团队行程未达标 |
| 发现者 | `discoverer` | 触发全部 3 个遗迹（隐藏结局，优先级最高） |

判定顺序与理由：`discoverer` 最高（集齐就是集齐了）；`missing` 排在
抵达/绕行前面——**人不在比没精神更重**；然后才轮到士气。

`missing` 只认「最后一幕结束时 `status = stranded`」的人：没人接，赛季也
没有下一幕让他自己归队。因两幕没动被剔出分母的**不算**——那多半是出差，
把它算进结局等于让「出差两周」变成一种失败。

不设“重开”。失败结局给一个下季可继承的徽章，不惩罚个人。

**翻篇**（赛季结束后怎么办）

结算在“赛季最后一天之后”才判定，所以判定当天就是结果可见的第一天。
**结果留一天**：结束后第二天才开新的一季。否则判定和翻篇落在同一次请求里，
结算页还没渲染就被下一季顶掉了，玩家永远看不到自己那一季的结局。

翻篇在冷路径里做（`BEGIN IMMEDIATE` + 条件 UPDATE）：

1. 把上一季结论压进新一季 `flags.prev`（`ending` / `team` / `target` /
   `morale` / `relics` / 起止日期），不另开历史表——玩家要的只是“上一季”。
2. **清空** `group_run_member` / `group_run_event` / `group_run_trial`。
   这三张表的主键是 (组, 人, 幕)，不清就会把上季的补给、行程、试炼带进来，
   试炼还会因为“已报过”直接判死。
3. 新的一季从当周周一开始，士气回 5。

上一季那句话留在远征页页脚（`上一季 · 抵达 52 格`）：上周太忙没打开，
不该等于“那一季没有过”。

**分享图**（`garmin_cn/runcard.py`）

结算页上的「保存这张图」出 1080×1920 的竖图，走和活动图同一套出图链路
（Python 出 1080 宽 HTML → App 离屏 WebView `draw(Canvas)`），画幅与
`exportspec` 的 9:16 契约一致，分享面板不会二次裁切。

- **卡片本身不用图像生成**。图上要写结局名、总里程、人数、四段走够没有，
  模型写中文和数字几乎必错，错一个数这张图就发不出去。版式与文案全部由代码
  渲染，数据来自 `/run/outcome`；只有最上面那条雪地插画是预先做好的图。
- **数字也跟着结算页走**：三个大数字是「走到的里程 / 走过的人 / 四段路走够
  N/M」，士气不再占位——它是局内数值，写在图上不解释没人看得懂。旧日志只在
  真的拿到过时才占第四格。

**结局插画**（2026-11-18 定案）

`garmin_cn/content/ending_<key>.*`，五个结局各一张，1920×680（2.82:1）。
脚印、石头、书本都画在图里，代码只负责摆位置。

- 曾经试过「一张底图 + 矢量脚印」：好处是加结局不用重出图、缩小后脚印仍是
  矢量；但矢量印在雪地上像贴纸，画风和插画差得太远，弃用。那条路留在代码里
  当备选（`ending_scene_lit/dark.*`，优先级低于每结局的图）。
- 五张必须像同一次拍摄：同一屋型、同一大小、同一雪线（70%）、3–5 粒星。
  生成时先定一张，其余**在那张上编辑**，不要重新生成——重新生成必然换房子。
- **只放“一队人这一季走到了哪里”**：没有 GPS、没有昵称、没有别人的名字，
  所以不需要像活动图那样先问一次脱敏档位。
- **不写每个人的名字和里程**（2026-11-18 定案）。组里本来就有榜单，
  每人的数据在小组页看得到，分享图不必复述；而且“同意给组里看”不等于同意
  出现在一张会被转发到群外的图上。结算页那面名单才是看人的地方。
- **没结束的赛季拒绝出图**：那时候没有结论，出出来是张空壳。
- 高度锁死 1920，余量交给「结局」与「四段路」两个弹性块——不锁的话出图
  会在上下留一大块底色。

### 11.3 训练护栏（硬性）

1. 远征贡献 = 当日计划里程全额；当天无计划按实际里程 50% 计入。
2. 每日贡献上限 = 当日计划里程（无计划 10 km），超出不计。
3. **试炼不增加距离，只提高精度**：距离固定为常规训练量（5/6/8/10 km），
   判定看配速分布、步频稳定性、心率漂移，不看跑得更远。
4. 试炼判定统一用“本周内”，不做“必须今天完成”。
5. 失败只损失团队补给，不扣个人榜单、不扣赛季积分。
6. `recovering` 状态不进事件池、不承担试炼。
7. 救援只消耗游戏内资源，不要求任何额外跑步。
8. 远征不修改、不生成任何训练计划；周目标只能下调，不能上调；暂停者不计入团队分母。

### 11.4 局外：团队营地

**休整点**（每人每周上限 4，直接汇入团队池；须本周至少 2 天训练）

| 行为 | 点数 |
|---|---|
| 按计划休息 1 天且当天无训练 | +1 |
| 睡眠 ≥7 小时达 4 天 | +1 |
| 恢复度连续 3 天回升 | +1 |
| 主动标记“今天休息”且无训练 | +1（每周最多 2 次） |

`recovering` 周休整点 ×1.5；`dormant` 不产点，回归补 1 点“归队”。

**营地树**（花点升级，等级只增不减，增益下季生效）

| 等级 | 名称 | 效果 | 人均成本 |
|---|---|---|---|
| Lv1 | 宿营 | 初始补给 +1 | 1 |
| Lv2 | 侦察 | 开局揭示前 2 格 | 3 |
| Lv3 | 医师 | 恢复期成员不占缺勤 | 5 |
| Lv4 | 驮马 | 每日贡献上限 +1 km | 7 |
| Lv5 | 传令 | 事件从 3 选 1 变 4 选 1 | 10 |

**按人数缩放，避免大组升级过快**

- 升级成本 = 人均成本 × 当前有效成员数
- 团队池上限 = 40 × 当前有效成员数
- 池满后不再累积，提示“已满，去升级营地”
- 效果全部是信息、容错、选项，**没有进度百分比加成**

**等级显示**

- 组列表 / 组详情 / 邀请卡显示 `秦岭跑团 · Lv3 营地`
- 后缀由客户端按 `camp_level` 拼接，**不写进 `groups.name`**
- 组徽章按等级换色，Lv5 加“传令”角标；排行榜不显示等级
- **解散后营地等级不恢复**：解散确认框必须明写“营地 LvN 与休整点将清零，无法找回”，
  并要求输入组名二次确认

### 11.5 多榜

| 衫 | 名称 | 口径 | 防刷 |
|---|---|---|---|
| 黄衫 | 里程王 | 周跑步类里程 | 只算跑步/越野/跑步机/徒步 |
| 绿衫 | 出勤王 | 周有运动的天数 | 一天多练只算 1 天 |
| 圆点衫 | 爬升王 | 周累计爬升 | 单次 ≤3000 m，爬升/距离 ≤200 m/km |
| 白衫 | 进步王 | **最近 7 天 vs 前 7 天**里程增幅（滚动，不按日历周） | 前 7 天 ≥10 km 才参评 |
| 红衫 | 计划完成王 | 按计划完成的天数 / 有计划的天数 | 休息日不算失败（`plan_done` 三态） |
| 蓝衫 | 连续王 | 最长连续训练或按计划休息 | 休息日算连续 |

> **红衫为什么换了**：原设计是「守护王 · 主动恢复天数」，要睡眠 / HRV。
> 服务端没有这些数据，也不该有——组页承诺的是「里程合计 + 脱敏剪影」。
> 而 `plan_done` 本来就在传，且是三态（完成 / 有课没跑 / 没计划），
> 休息日不会被算成失败。就衡量「是不是在一起练」这件事，计划完成率比
> 恢复分更直接，也不用动隐私口径。
>
> **爬升只算跑步类**（和黄衫同口径）。不这样限，骑车一趟 1000 m 爬升会把这件
> 衫变成自行车榜。上报入口按「爬升 / 里程 ≤ 200 m/km」截断，截了会在响应里
> 回 `clamped_elev`，不静默改数。

**探索徽章**（不占衫）：本地 500 m 网格计算本周新增格子数，只上传计数、不上传格子 ID；
单次 ≥3 km 的活动才计入，单日新增上限 50 格。后续“优质路线分享”是独立功能，
必须用户主动导出轨迹并授权，与探索徽章分开。

### 11.6 赛季积分

隐藏分 = 里程 30% + 出勤 20% + 爬升 15% + 连续 10% + 进步 15% + 让分与预言 10%。

**实现口径（与上式的差别，写清楚免得后面有人当成 bug）**：

- 每个维度按「组内最高」归一后再乘权重，不是绝对阈值。绝对阈值会让 5 人小队
  永远比 30 人大组难看，而赛季分只用来排组内名次。
- 让分与预言那 10 分**还没做**，所以当前满分是 **90**。它们将来是往上加的
  加分项（+2 / +3），不是权重。页面显示「62 分」，不要写成 `62/100`。
- 第一周没有上周数据，「进步」算不出来 → 那一周谁都不给这 15 分（满分 75）。
  不能凭空给分，也不该让这项变成「谁都没份」的 0 分并列。
- **进步为什么改成滚动 7 天**（2026-11-19）：原来是「本周至今 vs 上周整周」，
  分母恒为 7 天，周四只过了 4 天，全组必然负增长（线上实测 -62%），白衫
  基本发不出去、15 分也恒为 0。现在两个窗口等长（最近 7 天 / 再往前 7 天），
  任何一天都可比；代价是白衫不再严格属于「本周」，页面上要写明这一点。
  实测同一人：日历周口径 -62%，滚动口径 -3%。
恢复守护不进权重，只影响红衫与营地。

称号：前 10% 远征队长、前 30% 先锋、完成 3 周 行者、全员 同行者。
判定有优先级（同行者 > 远征队长 > 先锋 > 行者），只取最高的一个，不叠加。

**页面必须能自证**：组页核心卡底部有「这个分数和称号是怎么来的」，点开列出
五项得分 / 权重、每项的「我 vs 组里最高」、加分，以及四个称号的门槛和
「你现在是哪个、为什么是这个」。权重和称号文案由服务端下发（`weights` /
`titles` / `people[].parts`），页面不写死——改权重那天页面不能还在讲旧话。
分数是**组内相对分**，页面要写明这一点：换一批队友，同样的跑量算出来也不同。
组内不做降级；跨组联赛留到 P3 之后。

**让分赛（结对版）**：大神目标 = 自报 + 小白目标 × 50%，小白目标 = 自报；
两人都完成得双人徽章，小白完成而大神未完成得“逆袭”徽章。大组可选群组版：
大神目标 = 自报 + 小白总目标 × 0.25，上限自报 × 1.6。

**预言投票**：周一报目标时预测“本周谁完不成”；预测对 +2，被预测但完成 +3，不能预测自己。
结算周期固定为北京时间周一 00:00 – 周日 24:00（按客户端带来的本地日期算周）。

- 只能猜**报了 ≥5 km 目标**的人：没目标的人没有「完不成」这回事。
- `POST /v1/group/{id}/goal` 的 `km` 可以空着（= 只改预言），`predict` 传空串
  = 撤掉这周的预言。两条拆开之前，用户必须先报目标才能猜，于是「我只想猜别人」
  这件事根本做不了。
- `week` 返回的 `targets` 带每个人的 `km`，下拉里要显示「阿狗 · 40 km」——
  只有名字的话，猜谁全凭感觉。

**排名**：同分同名次，后续名次顺延（95、95、70 → 1、1、3）；衫按名次发，同名次都发，下一名空缺。

### 11.8 事件配置

`server/expedition_events.json`，服务端下发，客户端渲染。每条事件必须有 `summary`，
`text` 可被用户跳过，跳过时只显示 `summary` + 对应结果的 `result_brief`。

剧情事件（叙事）：

```json
{
  "id": "old_muleteer",
  "type": "story",
  "act": 1,
  "summary": "老背夫说山腰有条近路，但他三年没走过了。",
  "text": "他把烟袋在鞋底磕了磕：“那条路我年轻时候走过，能省半天。”说完又补了一句，“就是这几年雨大，不知道塌没塌。”",
  "options": [
    {"label": "跟他走近路", "brief": "快，但路可能塌了", "effect": {"advance": 2}, "tag": "guided"},
    {"label": "按地图走", "brief": "稳，慢半天", "effect": {"advance": 1}}
  ],
  "result_brief": {
    "guided": "你们跟着他钻过塌方口，提前半天到了营地。",
    "map": "地图上的路更好走，只是多绕了一段。"
  }
}
```

质量试炼（不增加距离）：

```json
{
  "id": "even_6k",
  "type": "trial",
  "act": 2,
  "summary": "把 6 公里跑匀：每公里与均值差不超过 5 秒。",
  "quality": {"metric": "even_pace", "distance_km": 6, "tolerance_s": 5},
  "success": {"advance": 3, "morale": 1},
  "fail": {"supply": -1}
}
```

`quality.metric` 枚举：`negative_split` / `even_pace` / `cadence_stable` / `hr_drift` /
`climb_steady`。选项的 `tag` 会写入赛季 `flags`，用于筛后续事件池与判定结局。

**团队 flag 的判定**（2026-11-17 补）：岔路是「全组同一段描述、各自选」，
所以 tag 要按**占比**折算成团队意志——某个 tag 有一半以上的人选了才算团队 flag。
不能谁选了就整个团队都算，那样 1 个人带路、50 人共享地图，不合理。

已接入的联动（2026-11-18 补：`picks` 原来只写不读，这三条全是空的）：

| flag | 效果 | 落在哪 |
|---|---|---|
| `guided`（过半请老周带路） | 第三、四幕每人每幕额外 +1 格 | `_settle` 的团队总量 |
| `rescue_hiker`（过半救人） | 终局全组士气 +1 | 第四幕结算的士气 |
| `leave_hiker`（过半抛下） | 终局全组士气 −1 | 第四幕结算的士气 |

“过半”按 `picks[tag] × 2 > 成员数` 算，不是“有人选了就算”。

`guided` 是刻意设计成「静态价值持平、长期分岔」：一幕选带路，当下付两包盐、
价值和看地图几乎一样，回报要等到后面两幕才体现。这样的选择才有回味，
而不是开局就能算出唯一解。

#### 增益规范

四条来源，统一结构：

| 来源 | 例子 | 触发方式 |
|---|---|---|
| 补给事件 | 顺风：本周每天行程上限 +2 km | 事件直接给 |
| 事件选项 | 篝火：本幕休整点 +1 | 选“拿盐和柴” |
| 试炼成功 | 节奏：本周结算额外 +1 格 | 负分割 5 km 达标 |
| 救援回报 | +1 士气 | 即时结算，不占增益槽 |

```json
{"id": "tailwind", "name": "顺风", "icon": "advance",
 "effect": "weekly_cap_add", "value": 2, "unit": "km",
 "weeks": 1, "desc": "本周每天多算 2 km 行程上限"}
```

- 最多同时 3 个，下周一清空；同类效果不叠加，取最高值。
- `icon` 取自图标系统：`advance` / `supply` / `morale` / `buff` / `camp` / `relic` /
  `strand` / `vigor`。
- 界面一律显示“图标 + 数值 + 一句话”，不暴露 `effect` 这种内部字段。

**已接入的消费**（2026-11-18 补：此前 `buff` 只写在内容里，代码读都没读）

| effect | 结算时怎么算 | 状态 |
|---|---|---|
| `weekly_cap_add` | 周上限 += 值 × **本周实际跑过的天数**（≤7） | 已接入 |
| `weekly_advance_add` | 该成员本幕贡献 += 值 | 已接入 |
| `weekly_morale_add` | 全组士气 += 组内**最高一份**（不按人数累加） | 已接入 |
| `weekly_supply_add` | 本幕成员行补给 += 值，下一幕 `draw` 抄过去 | 已接入 |
| `act_vigor_add` | 营地还没做，界面灰着显示 | 未接入 |

`weekly_cap_add` 按“实际跑过的天数”而不是 7 天：按 7 天算等于白送一周，
按 1 天算又对不起坚持了五天的人。

来源三条：试炼成功（`success.buff`）、事件选项（`option.buff`）、
**没有选项的补给事件**（抽到即生效——它没有按钮可点，不在抽签时兑现就是
一张永远不会发生的卡）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/group/{id}/run/state` | 当前幕全部状态：岔路、我的支线、进度、受困名单 |
| POST | `/v1/group/{id}/run/target` | 报本周目标 km（**只能下调**） |
| POST | `/v1/group/{id}/run/fork` | 选岔路 |
| POST | `/v1/group/{id}/run/event` | 选支线选项 |
| POST | `/v1/group/{id}/run/trial` | 报试炼结果（成功/失败都要报），带 `evidence` 由服务端复算 |
| POST | `/v1/group/{id}/run/rescue` | 救援受困者 |
| GET | `/v1/group/{id}/run/outcome` | 赛季结局（未结束只回进度，不剧透）；`people[]` 是每人的里程与那一点，`km` 是全队真实里程 |

所有接口都接受 `today`（用户本地日期）。服务器不知道用户在哪个时区，
「周」必须按用户本地日期算，否则 UTC+8 的人周一早上会看到上周的榜。

           "options": [{"id": "...", "label": "...", "brief": "...", "time": 0}]},
  "events": [{"id": "...", "type": "trial", "quality": {...}, "chosen": "", "options": []}],
  "stranded": [{"user_id": 12, "since": 1794919344, "rescue_by": null}],

#### 受困的时序（很重要）

**受困必须在「报试炼失败」的那一刻判定，不能等结算。**

原来的写法是在幕末结算时标 `stranded`，而结算跑完 `settled_act` 就 +1、
当前幕变成下一幕了；`/run/rescue` 查的是当前幕的行，于是永远查不到那个
`stranded`，永远回「这个人没有受困」——**24 小时救援窗口形同虚设**。

现在：`/run/trial` 报失败后立刻判（`maybe_strand`），返回 `me_stranded`。
结算里保留同一次判定做兜底，补的是「先报试炼、后选岔路」的顺序。

三个条件同时成立才受困：补给 < 2、本幕有失败的试炼、走的是**正的** `advance`
分支。`advance: -1`（抬人下山，慢一天）是稳妥选项，不算冒险。

#### state 里的两个易错字段

| 字段 | 说明 |
|---|---|
| `me.week_target_km` | 用户**报的值**，0 表示没报过 |
| `me.week_target_effective` | 实际参与计算的量，没报按 25 km 兜底 |

前端要显示后一个。只显示前一个会变成「本周目标 0 km」，而进度条按 25 算。

`api.trial` 返回的布尔叫 `me_stranded`，不叫 `stranded`——`state` 里的
`stranded` 是全组受困名单**数组**，同名会让客户端统一建模时撞类型。

**选项不下发 `effect`**。客户端只看到「快，但路可能塌了」这类定性文案，
看不到「+2 格 vs +3 格」。效果由服务端在选中时结算。
理由很直接：一旦把数值发下去，玩家就会开始算哪边更划算，选择退化成算术题；
而前面几轮平衡做的工作，恰恰是要让「差 0.1 分」这种差距只体现在情境里。

#### 三条硬约束

1. **抽签必须确定性**。随机源是 `seed:幕:用户:槽位`，同一组同一幕刷新多少次
   都是同一条事件。落库只记「选了什么」，不是「抽到了什么」。
2. **行程只在服务端算**。客户端只说「我跑了 20 km」，格数由服务端按
   `min(里程, 周目标) ÷ 5` 折算。改客户端能改自己的数字，改不了换算规则。
3. **试炼只记不验**。配速分布只有手机算得出来（要 `activity_detail` 的分圈），
   服务端收到「完成了」就加格。防不住伪造，所以产品上接受，不做反作弊的
   假动作——那只会让正常人被误伤。

#### 结算：cron 预热 + 懒触发兜底

两条路并存，**不是备选关系**：

| | 谁在用 | 做什么 |
|---|---|---|
| cron（`server/tick.py`） | 凌晨低峰 | 把跨周的组先结算掉，用户打开就是最新状态 |
| 懒触发（`ensure`） | 每次请求 | cron 没跑到时补上，代价由这个用户承担 17 ms |

crontab（服务器是 UTC，脚本内部按 `TICK_TZ_OFFSET=8` 算北京时间）：

```bash
5 0 * * *    cd /srv/runnercoach/server && python3 tick.py >> /var/log/rc-tick.log 2>&1
*/10 * * * * cd /srv/runnercoach/server && python3 tick.py --quiet
```

第一条每天结一次；第二条每 10 分钟兜一次，让「周一凌晨就打开 App 的人」
也不用等懒触发。`--quiet` 在没有要结算的组时不输出，避免日志刷屏。

**先说清楚：2C2G 完全跑得动 cron。** 实测 50 人组补算 4 幕 **17 ms**，
已结算后每次 3 ms；三个组一轮扫描 31 ms。不用它才是取舍问题，不是能力问题。

#### 跨进程安全：锁在数据库层

这是 cron 和 web 并存的**前提**。原来的进程内锁跨不了进程——cron 进程和
web 进程会各算一遍，士气扣两次、`flags` 互相覆盖。

现在改成：

```
BEGIN IMMEDIATE                     -- 进门就拿写锁，后到的排队等
UPDATE ... SET settled_act=N
 WHERE group_id=? AND settled_act=N-1   -- 条件更新，谁抢到谁算
```

- `rowcount == 1` 才结算，`0` 说明别人已经推进了，直接读最新值返回。
- **先抢锁再算**，不是先算再抢：算错的代价是白算 17 ms，而先算后抢在抢不到
  时白算一次，且两次结果若不同会让状态来回跳。
- 默认的 deferred 事务在这里会死锁：两个进程都先 SELECT（读锁）、再想写，
  互相等对方的读锁。`BEGIN IMMEDIATE` 一开始就拿写锁，排队而不是死锁。

**逐组短事务**：不要一个事务扫全表。结算一组几十毫秒，扫一百组会让写锁被占
几秒，期间所有上报都排队。

#### 热路径只读

`ensure` 分两段：

- **热路径**（绝大多数请求）：读两次判断「已经结算到位」，不拿写锁。
- **冷路径**（跨周那一刻）：才进写事务。

`state` 接口顺带修了 N+1：原来是人循环里各查一次周里程（50 人 = 51 条 SQL），
改成一条 `GROUP BY`。这个接口是进组页就调的，之前一直没人注意。

#### 设计时踩过的两个坑

1. 赛季结束分支漏了 `draw()`，第 4 幕没有成员行，结算时全是 `None`，总量恒为
   0——跑完四周的队伍最后一幕白走。压测时 50 人组从 0.0 修到 262.5。
2. 结算前必须先 `draw()` 把成员拉进那一幕。用户第三周才打开 App 时，第二幕
   没有任何人「进入」过，会被算成 0 行程、白扣一周。

#### 数值（服务端常量）

| 项 | 值 | 说明 |
|---|---|---|
| 每人每幕支线 | 2 条 | 类型按 40% 试炼 / 35% 补给 / 25% 叙事抽 |
| 遗迹出现率 | 45%/幕 | 随机落到一个成员头上，谁先走到谁碰上 |
| 段目标 | Σ周目标 ÷ 5 × 0.8 | 累计，按仍在参与的成员算 |
| 没报目标的人 | 按 25 km | 分母不能是 0，否则「谁都不填」就变成「怎么走都达标」 |
| 试炼格 | +3 | 失败 −1 补给 |
| 受困条件 | 补给 <2 + 试炼失败 + 走冒险分支 | 本幕行程冻结 |
| 救援窗口 | 24 小时 | −1 补给、−1 格，全组 +1 士气 |
| 士气上限 | 10 | 每 3 点 +5% 团队行程，最多 +15% |

  试炼引导都还没画——目前只能用接口调。

### 11.10 界面：一套骨架，两套气质

远征页和日常页**共用同一套视觉 token**（深空底色、玻璃卡片、16px 圆角、蓝青辉光），
但换掉了三样东西，让人一眼看出「这里在讲故事」而不是看数据：

| | 日常页 | 远征页 |
|---|---|---|
| 信息 | 数字（配速、负荷、完成率） | 处境（走到哪、还剩多少、要不要冒险） |
| 正文字体 | 无衬线 | **衬线**（宋体） |
| 进度 | 进度条 | **一条带折角的路 + 路名** |
| 暖色 | 无 | **赭石**（当前所在、火、补给） |

**赭石（`#C98B4B`）是全 App 唯一的暖色**，只在远征页出现，只用在三个地方：
路线上的「现在」、士气火苗、补给见底。整页只有它，所以它出现时就有分量——
冷环境里的一点火，这本身就是叙事。

#### 三个关键的界面判断

1. **进度条换成路线**。进度条回答「我完成了多少」，路线回答「我走到哪了」。
   前者是考核，后者是旅程。所以那条线是带折角的路径，已走实线、未走虚线，
   当前点立一面赭石小旗。**小旗按当前幕内进度定位，不按整季累计**——
   队伍超额时整季进度会超过 100%，用它会顶到终点，看起来像这一季已经走完。
2. **叙事卡是「纸条」，不是「面板」**。圆角从 16 收到 10、边框更暗、左侧一道
   类型色的竖线（岔路赭石、试炼青、补给蓝）。这是**不依赖字体**的区分手段，
   即使衬线没加载出来，「故事」和「数据」也不会混。
3. **选项不显示数值**。服务端刻意不下发 `effect`，界面只给 label + brief。
   一旦前端自己算「哪个更划算」，前面四轮平衡做的「差 0.1 分只体现在情境里」
   就白做了。`selftest` 里有一条硬断言：页面 HTML 不许出现 `effect` / `advance`。

#### 美术元素全用 SVG，不用图像生成

山脊、小旗、火苗、水壶、脚印，全部是内联 SVG path（加起来不到 3 KB）。
不用 AI 生图是三个具体理由，不是省钱：

* **深色底上的锐度**。现有卡片是 1px 边 + 顶部高光的精确质感，AI 图片的柔边
  雪雾贴在旁边会显得脏。
* **像素密度**。手机有 2x/3x 屏，420 宽的位图放大就糊；SVG 在任何密度下都锐利。
* **包体**。每张氛围图 200–400 KB，而三层山脊的 path 不到 2 KB。

山脊的不透明度总和不超 11%——它是「环境」不是「插画」，超过这个强度就会和
标题抢注意力，卡片压在山上也看不清字。

**唯一值得用图像生成的地方是结局分享图**（发到群里的那种卡片），那是要「出图」
而不是「渲染界面」。页面内一律 SVG。

#### 衬线字体必须内嵌（1.5 MB）

Android 的 WebView 里 `font-family: serif` 对中文**没有可用字体**，会静默
fallback 到无衬线——那么「衬线 vs 无衬线」这个最重要的区分就完全失效了，
而页面看起来仍然「正常」，极难发现。

`tools/build_font.py` 的做法：

1. 源字体用系统里的**思源宋体**（`NotoSerifSC-VF.ttf`，SIL OFL 协议，可商用、
   可嵌入、可再分发）。**绝不能**用系统自带的 SimSun/STSong——那是商业字体，
   打进 APK 是侵权。
2. 可变字体先实例化到 `wght=400`，只留正文字重。
3. 字符集 = **GB2312 一级（3755 字）+ 标点 + ASCII + 剧情实际用字**。
4. 子集化 + woff2，产物 1581 KB。

**为什么不用「只按当前剧情子集化」**（那样只要 300 KB）：字体在客户端、内容在
服务端。只按现有 40 条文案子集化，下次加一条用了生僻字的事件，客户端就会显示
方框——而且只有走到那一条的玩家才会看到这个 bug。

代价是 1.5 MB。它按需加载（`font-display:swap`，只在远征页解析），不拖慢日常页；
换来的是「加内容永不缺字」。

**加剧情之后要重跑 `python tools/build_font.py`**。`--check` 只做覆盖检查，
`selftest` 里已经调了 `check_coverage`，忘了重建会直接报出缺哪些字。

#### 结算页：先说人，再说这一季

**这一页的主角是「谁走了多少」**，不是士气补给这些局内数值。一份团队月报
的第一屏永远是人和他做的事，不会是系统的状态变量；结算页同理。

从上到下：

1. 结局（插画 + 标题 + 一句 + 正文）——情绪落点；
2. **这一季，谁走了多少**：每人一行，左边名字、右边里程（全身最大的数字），
   下面一行是他这一段最亮的一点 + 出勤天数与次数；
3. 四段路走够了没有（表头写明单位是「格 / 目标」）；
4. 页脚一行小字：`士气 7 · 旧日志 1/3 · 走过 3 人`。

人数、里程这些「人的数据」是主，士气/旧日志/补给是辅。旧日志**只在拿到过
的时候才提**——它是藏起来的东西，结算页写「旧日志 0/3」等于替玩家宣布他
错过了什么，把探索变成了补作业清单。

**每个人的那一句话怎么来**（`_people_stats` / `_badge_of`）

不排成排行榜。一条队五个人的差别往往在「强在哪」而不是「谁多」，按总量排名
会把后面四个人全抹平，而「都被看见」才是这类小组要的。

- 口径只看**开着共享**的人。关掉共享的人数据本来就没上报，凭空列一行
  「0 km」等于替他说他没跑；他们只计入 `hidden`，页面写「另有 N 人关掉了共享」。
- **受困的人照样列**：他跑了多少是既成事实，不能因为最后没走出来就从统计里
  消失（那才叫没被看见）。名字后面标「最后没走出来」。
- 一人只给**一条**——一条优先于三条并列。顺序是「这件事有多难忘」：
  试炼全对得上 > 走得最远 > 一天没断 > 单次最长 > 出勤最多 > 每周最稳 >
  后程发力 > 路上推进最远。
- 「最 X」只在**独一无二**时才说。两个人并列却只夸一个，比不夸更伤人；
  并列就退到下一条。
- 没有可夸的就不给，不硬凑「参与奖」。0 km 的人写「没有记录」，不写「0.0 km」——
  数字一样，前者不是判决。

#### 插画：同一片雪地，五种到达方式

五个结局共用一套版式，插图是同一处地方——雪地、小屋、脚印。
变的是脚印的去向和屋里的灯：

| 结局 | 画面 |
|---|---|
| 抵达 | 一串脚印走到门口，窗亮着 |
| 走到了但人散了 | 三条脚印散开，只有一条到门口，窗亮着 |
| 没走完 | 脚印走到一半断了，石头后面停下，窗是暗的 |
| 少一个人 | 一串到门口，另一串半路偏出、越走越淡被雪盖住，窗亮着 |
| 三本日志（隐藏） | 脚印到门口，窗亮着，路边压着三本旧日志 |

不用四张不同的插画，是因为「同一处地方、不同的到达方式」才是这个玩法的意思——
玩家换一季再来，看见的还是这片雪地，变的是自己走成了什么样。

结局文案（`endings`）和事件正文一样**只在服务端**：客户端平时只知道 `ending`
这个键，到赛季结束才拿到具体文字。抓包也只能拿到「自己走到的那个结局」。

四段记录显示「走够 / 没够」，不打分。**没结算过的幕显示「没走到」**，
不能显示成「0/0 没够」——那是两件事。

#### 遗迹（旧日志）的视觉标识

二、三、四幕各藏一处旧日志，集齐解锁隐藏结局。这类事件在界面上**必须能被认出来**，
否则玩家会直接划过去，隐藏结局就成了运气。

做法很克制：标签从「遭遇」改成「**旧物**」，卡片换暖色边和稍亮的底。
**不写有什么用，不标记进度**（页面上只有结算时才显示「旧日志 2/3」）。
标得太明显就变成任务清单，那就不叫探索了。

## 十二、内容下发与保护（红线）

> 起因：已经出现过第三方平台抓包本 App 做引流。赛季剧情是本项目最值钱的
> 原创内容，也是**最容易整包抄走**的部分——APK 就是 zip，解压即得全部
> Python 与 JSON。所以这条不是"优化项"，是**发布红线**。

### 12.1 一条原则

**客户端只有"怎么演"，没有"演什么"。**

| 层 | 放在哪 | 内容 |
|---|---|---|
| 引擎 | 客户端（APK 内） | 事件结构解析、资源结算、界面渲染、动画 |
| 内容 | 服务器（`server/content/`） | 事件池、标题与正文、选项文案、结果结论、结局判定参数、遗迹文本 |

客户端拿不到事件池，只知道"给我第 2 幕的事件"，服务器给什么演什么。

### 12.2 五条硬规则

1. **不进包**。事件池、剧情正文、结局参数一律不放进 `garmin_cn/`、
   `assets/`、`src/main/python/`。这一条由 `garmin_cn/contentguard.py` +
   `tools/guard_content.py` 在 `build.bat` 里拦截，发现即构建失败。
2. **不做离线剧本兜底**。这是最容易在"网络不好"的抱怨里被加回来的东西：
   一旦为了"断网也能玩"内置一份事件池，前面所有努力归零。断网就只显示
   已拉到的当幕内容 + 一句"下次联网再推进"。
3. **按幕下发，不发全季**。客户端一次只拿当前幕 + 下一幕的骨架。抓包最多
   拿走一幕（4–6 格），拿不到整季的 16–18 条。这是**降低单次泄漏损失**，
   不是防住抓包——运行时抓包永远看得到已下发的内容。
4. **判定在服务端**。行程结算、资源变化、结局判定全部由服务器算，客户端只
   负责显示。否则改包的人可以本地改补给和行程，绕过所有约束。
5. **缓存有边界**。本地只落当前幕的运行时缓存（`data/content_cache/`），
   换季清理、可一键清除，不跨季留存。

### 12.3 文本指纹（建议在 P1 做）

同一段剧情发给不同账号时，在正文里嵌入**不可见差异**——零宽字符序列编码
用户 ID 的哈希、或同义词/标点位置的确定性随机。正文读起来完全一样，但泄漏
出来的文本能反查到是哪个账号、哪次下发。

成本很低（下发时拼一次字符串），价值在于：**泄漏可归因**，而不只是"知道被抄了"。
真要维权时，"这段文字来自账号 X 的第 3 次下发"比"这是我们写的"有力得多。

前提是这条写进隐私说明：文本里含标识信息，用于追溯未授权传播。

### 12.4 防不住的部分（诚实说明）

| 手段 | 能不能防 |
|---|---|
| APK 解压看代码 | 内容不在包里，看得到引擎，看不到剧本 |
| 运行时抓包 | **防不住**已下发的内容，只能靠按幕下发把单次损失压小 |
| 改包分发 | 已有启动签名校验（`f97a1593`），改包版会提示非官方 |
| 抄玩法机制 | 防不住。机制本来就要给用户讲清楚，护城河是内容与运营，不是规则 |

所以策略是：**机制公开讲，内容只在服务器**。宣传稿可以讲"三类事件、两个资源",
但一句具体的事件文案都不给。

### 12.5 工程守卫

```bash
python tools/guard_content.py     # 扫会进包的目录，非零退出即停构建
```

判定只认"一定是剧情内容"的特征，避免误报卡住日常开发：

- 文件名带 `expedition` / `act1`~`act9` / `story_events`；
- JSON 里出现 `result_brief`（剧情事件独有字段）；
- JSON 同时有 `options` 与 `advance`；
- 代码里硬编码 ≥3 条 `advance` + `brief`。

`server/`、`docs/`、`preview/` 不在扫描范围（那是内容源与设计稿）。
`selftest.py` 与 `contentguard.py` 自身排除——前者不进包，后者写着特征词。

`android/build.bat` 在 `[2/2]` 之前调用它：**守卫失败就不打包**，不靠人记。
