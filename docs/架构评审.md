# 架构评审（2026-11-24）

评审范围：`garmin_cn/`（64k 行）、`server/`（16k 行）、`tools/`（13k 行）、
`android/` 的 Kotlin 壳（9.9k 行）、`deploy/`、交付链路（APK + 代码包）。

结论先说
========

1. **技术选型没有问题，不要换栈。** 纯 stdlib Python + WebView + 服务端渲染，
   零第三方依赖，离线可用，22 MB 一个包能跑下 10 万行逻辑。换成 FastAPI /
   Compose / Flutter 都能做，但都是把已经验证过的东西重写一遍，收益是"现代"，
   成本是三个月。
2. **真正的架构债不是"旧"，是"同一套功能写了两遍"**：App 用 Python 出 HTML，
   网页又用 Python 再出一遍 HTML；请求处理也分成了四套，各自拼响应头和错误页。
   这一周连着出的三个问题（底部 5 个 tab 要改两处、赛事单位换算、休整点与横屏）
   都是它直接导致的。
3. 建议以 **收敛（方案 A）** 为主线做三个月；**前端 SPA 化（方案 C）** 列为观察项，
   用"页面改动频率"当触发条件；**换服务端框架（方案 B）明确不做**。

七个问题（按投入产出排序）
==========================

P1　双 UI 栈：App 与网页各写一遍
--------------------------------
- 现象：`garmin_cn/ui.py`+`groupui.py`+`eventui.py`+`aiui.py`（约 9k 行）给
  WebView 出页面；`server/webapp.py`+`webgroup.py`（约 3.2k 行）给浏览器再出
  一遍同样的页面。小组页尤其明显：`webgroup.py` 的 800 行基本是 `groupui.py`
  的简化重写。
- 代价：这一周踩到的三次都是它——底部导航从 4 个 tab 改 5 个要动两处；赛事
  `current/target` 是米、要按 kind 换单位，`groupui._chal_pair` 写了一份、
  `webgroup._chal_pair` 又写一份；休整点与横屏问题各不相同，但都要在两套里
  分别验证。
- 注意：网页版**已经**有一条正确的路——`web_render.py` 用子进程带
  `GARMIN_HOME` 复用 `garmin_cn` 的渲染函数，再套网页壳。今日/历史/计划/运动
  设置都走这条，只有小组页、教练页、底图页是另写的。
- 做法：把这几页也改走 `web_render` 那条路，把"两侧差异"收敛成一处适配
  （底部导航、链接改写、只读标记），删掉 `webgroup.py` 里的渲染实现。

P2　四套 HTTP 处理器
--------------------
- 现象：`garmin_cn/serve.py`（设备本地 2,476 行）、`server/app.py`（网关 2,032
  行）、`server/webapp.py`（网页 2,371 行）、`server/manage.py`（组长后台）。
  四套各自做路由分发、响应头、错误页、JSON 序列化。
  证据：`send_header("Content-Type"` 在 `serve.py` 出现 12 次、`app.py` 11 次、
  `webapp.py` 7 次。
- 代价：缓存策略、错误页样式、鉴权失败时的行为在三处各写一次，改一处漏两处；
  新加一个页面要先想清楚该往哪个 handler 里塞。
- 做法：抽一个 200 行左右的 `httpkit`（路由表 + 统一响应 + 错误页 + JSON/HTML
  两种出口），四个 handler 都退回成"注册路由"的薄层。不引框架也能做到。

P3　上帝模块
------------
- `MainActivity.kt` 5,736 行：WebView 宿主 + 每个原生对话框 + JS 桥 + 通知 +
  文件选择 + 编码器入口全在一起。改动风险高，且没有编译期边界。
- `appapi.py` 4,419 行：`_API` 白名单 + `call()` 分发 + 各域实现。
- `selftest.py` 8,656 行：2,034 条断言在一个文件里，任何两人同时改都要冲突。
- 做法（都不改行为）：`appapi` 拆 `domains/`（sync / plan / group / body / ai /
  media），`appapi.call()` 只留 dispatch；`MainActivity` 拆 `WebHost` /
  `Dialogs` / `Bridge`；`selftest` 按域拆 8~10 个文件，保留一个入口跑全部。

P4　代码包的基版本耦合
----------------------
- 现象：`latest.json` 只有一个包 + 一个 `base_version`。今天实测：包升到
  `2.0.3-x` 之后，还在 `2.0.2` 的客户端**一个包都拿不到**（`_fits()` 直接
  拒绝），而且界面上看不出原因。
- 另一层风险：代码包本质上允许服务端下发任意 Python 并在客户端执行，没有签名
  校验。这是自建分发省掉重装 APK 的代价，属于"知道自己在做什么"的选择，但要
  有边界。
- 做法：服务端保留最近 2~3 个 base 的包，按客户端版本返回对应的一份；包里带
  签名（哪怕只是 sha256 + 内置公钥）；诊断日志里明确写"为什么没挂上"。

P5　配置碎片
------------
- 现象：用户级状态散在 11 个 JSON（`plan.json`、`manual.json`、`meals.json`、
  `ai_chat.json`、`amap.json`、`mi_auth.json`、`session.json`、`coros_mcp.json`、
  `week_overrides.json`、`races_sources.json`…）+ 3 个 SQLite。每个都有自己的
  读/写/迁移代码，字段缺省各写一遍。
- 代价：备份只覆盖 SQLite（`deploy/backup.py`），JSON 那部分换机器就没了；
  新加一个配置要么新建文件、要么塞进别人的文件。
- 做法：短期先补"用户目录整体备份"；中期收成 `settings.json` + 每域一个命名
  空间，读取走统一的 `settings.get(domain, key, default)`。

P6　可观测性
------------
- 539 处宽泛兜底，好处是 App 不崩，坏处是"功能坏了但没人知道"。休整点那个
  bug（一次都没上报过）就是靠用户发现，而不是靠日志。
- 做法：不改异常结构，只在关键路径上加**结构化事件**（一行 JSON：动作、结果、
  耗时、原因），落 diag 的一个环形缓冲；关键业务（上报、登录、续期、代码包
  挂载）必须有"这次做了什么、结果如何"的记录，而不是只在失败时写。

P7　测试与 CI
-------------
- 没有 CI（`.github` 为空）。所有门禁靠人手动跑：`cli.py selftest`、
  `tools/test_bgsync.py`、`server/test_web.py`、`server/test_groups.py`、
  `tools/text_audit.py`、`tools/audit_ui.py`。
- 做法：加一个 `tools/gate.py` 把六道门禁串起来（已有一半），GitHub Actions /
  Gitee Go 上跑；PR 必过。成本不到一天。

三个方向与取舍
==============

| 方向 | 内容 | 收益 | 成本 | 判断 |
|---|---|---|---|---|
| **A 收敛（推荐）** | 不换栈；抽 httpkit、抽 render 复用、拆上帝模块、补 CI 与观测 | 直接消掉 P1/P2/P3 的重复与冲突；改一个功能只改一处 | 3 个月，逐步可发 | **做** |
| B 服务端换框架 | FastAPI + uvicorn | 路由/校验/OpenAPI 更省事 | 重写 4 个 handler，1.6G 机器装 FastAPI 也不轻 | 现在不做 |
| C 前端 SPA 化 | App 与网页共用一套前端，Python 只出 JSON | 架构最干净，双 UI 问题根治 | 重写约 1 万行渲染代码，失去"服务端渲染、弱网可用"的优势 | **观察**，见触发条件 |

C 的触发条件（满足两条再启动）：小组/教练这类页面每月仍在改；且 iOS/Android
两端视觉差异持续需要人工对账。否则 A 足够。

- 网页小组页改走 `web_render`，删 `webgroup.py` 的渲染实现；教练页、底图页
  同样处理，只留"网页专属"的壳。
- `_km`/`_pace`/`esc`/`_chal_pair`/日期格式化收进 `garmin_cn/fmt.py`，两侧共用。
- 验收：`server/test_web.py` 全绿 + `audit_ui` 三档达标 + 组页逐块截图对比。

P2（2~4 周，拆上帝）

现在就该修的缺陷（和重构无关）
==============================

1. **代码包多 base 并存**——否则升一次 APK，老设备静默断更（今天已实测）。
2. **备份覆盖用户目录**——现在只备 SQLite，`plan.json`/`ai_chat.json`/`meals.json`
   这些丢了就没了。
3. **设备 API 限流**——目前只有短信和组接口有限流，`/v1/*` 其他接口裸奔；
   自建服务器上被人拿到 token 可以刷。
4. **静默失败的可见性**——至少让"上报 0 行""续期失败""代码包未挂载"能在诊断
   日志里各占一行。

哪些看起来重、但其实合理
==========================

评审也要防止过度重构，这几处**不建议动**：

| 模块 | 行数 | 为什么看着重 | 判断 |
|---|---|---|---|
| `motion.py` + `MotionEncoder/Audio` | 2,350 + 700 | 端上出视频、抽帧、混音，还要兼容竖拍/横拍 | 核心卖点，保留 |
| `server/expedition.py` + 内容池 | 1,661 | 一套带结算、补给、结局的多人玩法 | 产品选择，保留；但内容池要独立于代码发布 |
| 代码包（`codepack.py`） | 400 | 服务端下发 Python 并执行，很不"常规" | 保留但收边界（见 P4）；否则每次改文案都要重装 22 MB |
| `actcard.py` | 2,183 | 单张图 1000+ 行 CSS/SVG | 是产品辨识度所在，保留 |

换句话说：**重不重不看行数，看它是否只有一份、边界是否清楚**。上面的模块都是
"只有一份"，所以重也值；P1/P2 那些是"同一件事有两到四份"，这才是要削的。

明确不做
========

- 不换 Compose / Flutter / React Native：丢掉 10 万行已验证逻辑，只换来"现代"。
- 不引 ORM、消息队列、微服务：单机几十用户，纯增负担。
- 不为异步而 async：`ThreadingHTTPServer` + SQLite 在这个量级足够，改 async 只是
  把复杂度挪个地方。
- 不动 `garmin_cn` 的领域计算（间歇识别、彩蛋、赛事、远征）：那是这个产品的
  价值所在，重构优先级最低。
