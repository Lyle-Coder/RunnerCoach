# 赛事数据源与自动更新

> 目标：延伸阅读里的「近期赛事」只出现**还在报名窗口内**的比赛；数据能自动检查更新，不靠手改 JSON。

## 一、结论：用「最酷」的报名中列表

「只展示报名窗口内的赛事」落到数据上就两个字段：`reg_open` / `reg_close`。
公开接口里没有一家同时给「窗口 + 合法可抓」，但我把候选源逐个摸了一遍之后，
**最酷 zuicool.com 满足全部三条硬指标**：

| 源 | 服务端渲染 | 每场带报名截止 | robots 允许 | 可用性 |
|---|---|---|---|---|
| **最酷 zuicool.com** | ✅ HTML 直出 | ✅ 「报名截止：11-18 12:00」 | ✅ 只禁 `/news/wp-content/` | **主源** |
| 中国马拉松 runchina（田协） | ❌ SPA | ❌ 只有赛事日期 | 有反爬 | 不用 |
| ITRA itra.run | ❌ 需登录/JS | ❌ 无报名时间 | ToS 限制 | 不用 |
| Ahotu（World's Sports Group） | ❌ | ⚠️ 有价格/状态，非窗口起止 | 商业授权 | 不用 |
| 赛事官网 / 公众号 | — | ✅ | — | 只作纠错兜底 |

它首页那三块「报名预告 / 报名中 / 大家都在报」本身就是按报名状态分好的名单，
`/events/reg` 更是纯粹的「报名中」列表（`?page=N&per-page=100`，每页 100 场）。
换句话说：**不需要猜谁在报名，平台已经替你筛好了。**

实测（2026-11-13）：抓 2 页 → 200 条卡片 → **165 场在报名窗口内**，
2 场「即将报名」（还没开）被正确跳过，7 条是页面残留的过期条目。

## 二、它给什么、不给什么

拿到的字段（每张卡片 + 名称正则补充）：

```
名称 / 赛事日期（2026.12.06）/ 地点（省 市）/ 报名截止（11-18 12:00）
距离 ← 从名称认（10KM / 50公里 / 半程 / 马拉松），认不出就留空
链接 ← https://zuicool.com/event/{id}
```

**拿不到 `reg_open`（报名开始日）**：列表页只写截止。

处理方式是**不编**：既然一场赛事此刻出现在「报名中」名单里，就说明开放日不晚于今天，
所以用量时的「今天」当下界，并在记录里写 `reg_open_source: "inferred"` 标出来是推的。
`reg_close` 是抓到的原文，不是推的——展示时的「报名剩 N 天」只用它。

跨年要当心：`2027.01.01` 的比赛，截止写「12-10」，年份得回到 2026。
规则是「报名截止一定不晚于比赛日」，推不出就丢弃。

## 三、展示规则：窗口外的一律不出现

| 状态 | 判定 | 展示 |
|---|---|---|
| 报名中 | `reg_open <= 今天 <= reg_close` | ✅ |
| 即将报名 | 今天 < `reg_open` | ❌ |
| 已截止 | 今天 > `reg_close` | ❌ |
| 窗口不明 | 缺日期 / 解析失败 | ❌ |

「窗口不明不展示」是刻意的：宁可比实际少一场，也不要让人按错误截止日准备。

抓来的赛事有一百多场，全部丢进首页轮播会把术语彻底淹没，所以有两道闸门
（`reading.RACE_SOON` / `RACE_PER_SLIDE`）：

- 只有**截止最近 12 场**参与抽取（其余仍在文件里，留给将来的赛事页）；
- 每次轮播最多露出 **2 条**赛事，剩下的位置给术语。

## 四、更新链路

```
garmin_cn/races_fetch.py          解析 + 抓取（App 与 tools 共用同一份）
        │
        ├─ App 启动 → start_background() → 6 秒后后台线程 → maybe_update()
        │     每天最多一轮；今天已更新就跳过；失败静默、保留旧数据
        │
        └─ python tools/races_sync.py [--check|--dry-run]
             读 data/races_sources.json，支持 zuicool / manual / page 三种源
                        │
              GARMIN_HOME/data/content/races.json（原子写入）
                        │
              reading.py 读取 → 按窗口过滤 → 首页轮播 / 一图流注脚
```

几条硬约束：

- **失败不写盘**：抓不到就保留上一次的可用数据，绝不「因为没抓到所以清空」；
- **原子写入**：写 `.tmp` 再 `replace`，中途断电不会留下半个 JSON；
- **路径跟 `GARMIN_HOME`**：写包目录的话，APK 一更新 Chaquopy 重建解压目录，数据就没了
  （饮食记录踩过这个坑）；
- **每日一次**：`updated` 是今天就跳过；线程用「每小时最多起一个」防刷新风暴。

## 五、清理：过期的要真删掉，不是只藏起来

展示层（`reading.races()`）本来就按窗口过滤，所以过期条目不会出现在界面上。
但**文件本身也要清**——否则一次抓取失败留下的旧条目会一直躺着，文件越攒越大，
而没人知道里面有一半已经没用了。

规则（`races_fetch.keep()`）：

| 情况 | 处理 |
|---|---|
| `reg_close` 早于今天 | 删（展示层也不会显示它了） |
| `reg_close` 就是今天 | **留**——当天还能报 |
| 自动抓来的、却没有 `reg_close` | 删（脏数据） |
| 人工维护的、缺 `reg_close` | **留**（可能正在补数据，删了等于让人白填） |

三个时机都会清：

1. **`maybe_update()` 一进来就清**，在所有「今天已更新 / 刚试过」的跳过判断**之前**。
   清理不联网，所以哪怕连续几天抓取失败、一次也没抓成，文件里的旧比赛也会被清掉；
2. **`sync()` 覆盖写时**再按同一规则过滤一遍（抓取本身只写窗口内的，这是保险）；
3. **手动**：`python tools/races_sync.py --prune`，不联网，只清理。

没有条目被删时**不写盘**——避免每次启动都把文件 mtime 刷一遍。

顺带解决另一个坑：`sync()` 原先整体覆盖文件，App 每天跑一次会把 `via: manual`
的手工条目**抹掉**。现在覆盖时保留「不是这个源抓来的」条目（且同样要过窗口校验）。

`--check` 也不再逐条刷屏，只报统计 + 需要看的几条：

```
· 报名中 165 场 · 已过期 0 · 窗口不明 0 · 超 7 天未核对 0
```

## 六、抓取纪律（别把自己变成爬虫）

- 每天 1 轮，每轮最多 2 页（≈200 场），上限 5 页；
- 同域名串行，页间 `sleep 1.5s`，不并发；
- 带自家 UA（含项目地址），方便对方联系；
- 只抓列表页，**不逐场抓详情**——距离从名称正则推，推不出就留空；
- 遵守 robots：`/news/wp-content/` 不碰，其余只做低频列表访问。

## 七、兜底与风险

- **页面改版**：`parse_list` 用 `<div class="event">` + `class="event-a"` 定位，
  改版后大概率整体解析不出 → 抓取返回 0 条 → **保留旧数据并记一条诊断日志**
  （`diag: races 赛事抓取失败`），不会把界面搞空也不会崩；
- **延期/取消**：平台偶尔用宣传语字段写「延期提示：从 11 月 22 日延至 12 月 20 日」，
  我们只信 `<div class="info">` 里的日期，宣传语不参与判断；
- **重复条目**：运营会把同一场挂两次（例如「暨小勇士障碍挑战赛」单独一条），
  按 `id` 去重，轮播侧再按名称去重一次；
- **不做**：不做全网赛事库、不做「报名代抢」相关任何接口。

## 八、后续可以加的（现在不做）

- 「即将报名」入口：现在直接丢弃，其实「3 天后开报」对备赛也有用；
- 按城市/距离/爬升过滤，而不是全量；
- 赛事详情页补充爬升与报名费（会多 100+ 次请求，暂不做）。
