# 赛事数据源与自动更新

> 目标：延伸阅读里的「近期赛事」只出现**还在报名窗口内**的比赛；数据能自动检查更新，不靠手改 JSON。

## 一、先说结论：没有「又稳定、又合法、又带报名窗口」的公开 API

我把三类源都查了一遍，各自缺一块：

| 源 | 覆盖 | 有报名窗口吗 | 稳定/合规 |
|---|---|---|---|
| **中国马拉松** runchina.org.cn（田协官方） | 国内路跑认证赛事 | ❌ 只有日期与赛事信息 | 权威，但页面是 SPA、有明显反爬；无公开 API，批量抓取有风险 |
| **ITRA** itra.run | 全球越野 | ❌ 日期/距离/爬升/时限，无报名时间 | 结构化但无公开 API；ToS 限制商业性抓取 |
| **Ahotu** ahotu.com（World's Sports Group） | 6 万场、194 国，含报名信息 | ⚠️ 有价格/报名状态，但非"窗口起止" | 商业平台，需合作/授权，不开放 API |
| **赛事官网 / 官方公告** | 单场 | ✅ 唯一可靠来源 | 每家一套，结构不统一 |

**报名窗口只存在于两处**：赛事官网/公众号的公告、以及报名平台（最酷、马拉马拉、大麦等）的商品页。这两处都没有开放接口，也没有统一格式。

所以「全网自动抓报名窗口」这件事**现在做不成，硬做出来也不稳**：页面一改版就静默失效，而赛事信息错了比没有更糟。

## 二、采用的分层方案

### 1. 数据源分两层

```
权威日历（有日期，没报名窗口）        定向抓取（有报名窗口，每场一处）
  runchina / ITRA            →      赛事官网 · 报名页
        └──────────┬──────────────────────┘
                   ▼
           races.json（人工复核后才进）
```

- **日历层**用来「发现赛事」和校对日期、距离、爬升；
- **报名层**只对**我们自己关心的赛事**（10~30 场：目标赛 + 备选）做定向检查，每场配一条官方 URL；
- 两层对不上时，**以官方公告为准**，并在 JSON 里留 `source_url` 与 `checked_at` 便于追。

### 2. 只展示报名窗口内，且「查不到就不展示」

`reg_status` 四态：

| 状态 | 判定 | 是否展示 |
|---|---|---|
| `open` | `reg_open <= 今天 <= reg_close` | ✅ |
| `upcoming` | 今天 < `reg_open` | ❌（可以另给「将要开放」入口，默认不做） |
| `closed` | 今天 > `reg_close` | ❌ |
| `unknown` | 缺窗口或抓取失败 | ❌ |

`unknown` 不展示是刻意的：宁可比实际少一场，也不要让人按错误截止日准备。

### 3. 更新链路

```
data/races_sources.json   （人工维护：id/名称/官方页/报名页，可选手填窗口）
        │
        ├─ python tools/races_sync.py --check     # 只看哪些条目过期/缺字段
        ├─ python tools/races_sync.py --dry-run   # 打印将发生的变化，不落盘
        └─ python tools/races_sync.py             # 抓取 → 归一化 → 校验 → 原子写入
                                                        │
                                    data/content/races.json（覆盖包内基线）
                                                        │
                                              App 启动即读，按窗口过滤
```

- 每天跑一次（cron / WorkBuddy 定时任务都行），失败**不写盘**，保留上一次的可用数据；
- 写入前做完整性校验（日期可解析、`reg_close >= reg_open`、`date >= reg_close`、URL 只认 http/https）；
- 每条带 `checked_at`；超过 7 天没检查过的，界面上标注「数据 X 天未核对」，不给「报名中」的强承诺。

### 4. 抓取器怎么写才不容易烂

- 每场一个 `adapter`，只有两种：
  1. **`manual`**：窗口由人填（最可靠，默认）；
  2. **`page`**：抓官方页，按关键词（报名/截止/截至）+ 日期正则找窗口；找到**开始和截止两个日期**才采信，只有一个就退回 `unknown`。
- 抓取失败、页面改版、关键词没命中 → 一律 `unknown`，不猜。
- 请求带 UA、超时 10s、失败重试 1 次；同一域名串行 1s 间隔，不并发打人家服务器。

## 三、现在能落地的第一步（本次实现）

1. `races.json` 结构 + 报名窗口字段 + `checked_at`；
2. App 侧过滤：只有 `open` 的赛事进「延伸阅读」（首页轮播），其余一律不显示；
3. `tools/races_sync.py`：读 `data/races_sources.json`，支持 `manual` 与 `page` 两种 adapter，`--check` / `--dry-run` / 正式写入；
4. selftest 覆盖：窗口过滤、过期不展示、缺字段降级、抓取值不合法时退回 unknown。

## 四、后续可以加的（现在不做）

- Ahotu / ITRA 的正式数据合作（一次授权解决"日历层"的稳定性和合规）；
- 报名平台的商品页 API（若开放）；
- 用户自定义订阅：只关心城市/距离/爬升区间。

## 五、风险

- **合规**：批量抓 runchina/ITRA 有 ToS 与反爬风险，只做「定向、低频、少量」访问；
- **时效**：赛事延期/取消极常见，`checked_at` 必须显示；
- **误报**：任何自动抓到的窗口都要能被人工一键改回 `unknown`；
- **不做**：不做全网赛事库、不做"报名代抢"相关的任何接口。
