# 协作流程

面向多人协作的分支约定。**main 只接受合并，不接受直接提交。** 所有人都先在自己
的长期分支撑上开发，合并时机由负责人拍板。

## 一、分支模型

| 分支 | 用途 | 谁能推 |
|---|---|---|
| `main` | 唯一可发布分支，永远对应线上最新 Release | 只在合并时由负责人推 |
| `dev/<gitee账号>` | 每个人自己的长期分支撑，日常提交都在这里 | 本人 |

- 分支名统一用 **Gitee 账号**（`git config user.name` 不算数，以远端登录名为准），
  例如 `dev/liyufei-lyle`。同一个人不要开多个长期分支，避免自己跟自己冲突。
- `main` 建议在 Gitee 仓库「管理 → 分支管理」里设为**保护分支**，禁止直接 push，
  只允许合并请求通过。这样能挡住误推——本仓库就发生过一次直接推 main 的情况。
- `origin` 是 GitHub 镜像，只做备份，**不承载发布**；发布一律走 `gitee`。

## 二、日常开发

每次开工先跟 main 对齐，再动手：

```bash
git fetch gitee
git switch dev/<你的账号>          # 首次：git switch -c dev/<你的账号> gitee/main
git merge gitee/main                # 把自己的分支更新到最新主干
```

开发、自检、提交：

```bash
python cli.py selftest              # 离线全链路自检，提交前必须过
git add -A
git commit -m "fix: 简短说明改了什么、为什么"
git push gitee dev/<你的账号>
```

约定：

- 一次提交只做一件事，提交信息写「改了什么、为什么」；不要写真实活动 ID、
  日期、GPS 坐标或健康数值（发版时这些会原样出现在公开 Release 里）。
- 已经推到远端的提交不要 `rebase`，用 `merge` 追主干，避免把别人的历史改写。
- 分支上的中间状态可以粗糙，但推之前至少保证 `python cli.py selftest` 能过。
- 不要提交 `config.json`、`data/`、`*.db`、`server/.env`、`dist/`、`*.apk`；
  push 前用 `git status` 扫一眼，`.gitignore` 已经兜底，但别依赖它。

## 三、合并到 main（等负责人指示）

**不要在没得到指示时自行合并。** 收到指示后按下面四步走，先评估、再动手。

### 1. 预演合并，只读不动

```bash
git fetch gitee
git switch -c tmp/merge-<账号> gitee/main
git merge --no-commit --no-ff dev/<账号>
```

- 冲突文件：`git diff --name-only --diff-filter=U`
- 改动面：`git diff --stat gitee/main...dev/<账号>`
- 决定是继续还是放弃：`git merge --abort`（放弃）或解决冲突后继续

### 2. 评估要报告什么

给负责人一份简短结论，至少包含：

1. **冲突清单**：哪些文件冲突、冲突是逻辑冲突还是纯行号错位；
2. **影响面**：动了哪些模块、有没有改公共接口 / 数据库 schema / 版本号 /
   `android/app/src/main/python` 副本；
3. **与 main 上已有改动的重叠**：同一函数、同一段 HTML/CSS 是否被别人改过；
4. **验证情况**：`python cli.py selftest` 是否通过，需不需要额外冒烟；
5. **建议**：直接合并 / 拆分合并 / 退回分支修改。

### 3. 合并并推送

```bash
git switch main
git merge --no-ff dev/<账号> -m "merge: <账号> 的 xxx"
python cli.py selftest
git push gitee main
```

用 `--no-ff` 保留分支拓扑，出问题时能整段回滚（`git revert -m 1 <merge>`）。

### 4. 清理

```bash
git branch -d tmp/merge-<账号>
```

`dev/<账号>` 是长期分支，保留不动；只有本人确认阶段性工作结束后才删。

## 四、什么走本地合并，什么走 Pull Request

| 情况 | 方式 |
|---|---|
| ≤ 3 个文件、单模块、不动公共接口 / schema / 版本号 | 本地评估后合并 |
| 跨模块改动、改公共接口或协议、改数据库 schema | Gitee Pull Request |
| 涉及发版的改动（版本号、Release 脚本、Android 打包） | Gitee Pull Request |
| > 5 个文件或 > 300 行 | Gitee Pull Request |
| 两个人同时改了同一批文件 | Gitee Pull Request |

走 PR 的流程：推 `dev/<账号>` → Gitee 网页「Pull Requests → 新建」→
源分支选自己的、目标选 `main` → 写清楚改了什么、怎么验证 → 负责人审阅合并。
PR 里同样要附上 `cli.py selftest` 的结果。

## 五、发版

发版仍然只在 `main` 上做，流程见 [`发布流程.md`](发布流程.md)：

- `tools/release.py` 会强制校验「当前在 main 且与上游同步」，`dev/*` 分支发不了版；
- 版本号（`garmin_cn/__init__.py`、`android/app/build.gradle.kts`）建议单独一个
  提交，合并进 main 后再打 tag；
- 一个 tag 只发一次，发错用新的补丁版本，不要强推覆盖 tag。

## 六、冲突高发区

这些文件多人同时改最容易冲突，动手前先在群里说一声：

- `garmin_cn/actcard.py`、`garmin_cn/card.py`：活动图 / 看板 HTML 与 CSS 集中在这里；
- `garmin_cn/interval.py`：间歇版式只认佳明 `hasIntensityIntervals`，改门槛只影响切分质量；
- `cli.py`：命令入口与 `selftest`，几乎每个功能都会碰；
- `garmin_cn/appapi.py`：App 侧接口，改返回结构要同步 Android；
- `android/app/build.gradle.kts`：版本号，发版时必改。
