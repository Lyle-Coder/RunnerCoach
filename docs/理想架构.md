# 理想架构（不考虑重构成本）

问题不是"怎么把现有代码修得更好"，而是"如果今天从零设计，要什么形状才能
支撑未来三年的体验"。这份文档只回答后者；怎么从现状迁过去放在最后一节。

第一原则：**体验的天花板由架构决定，不由功能多少决定。**

现在这套架构能做的体验已经做到了：服务端渲染 HTML、点一下整页换一次、
两套 UI 各写一遍、改个文案要发 22 MB 的包。它撑不住的是下面这几类事：

| 想要但做不到 | 卡在哪 |
|---|---|
| 点开就出内容、翻页像原生 | 每次导航都是整页 HTTP，没有客户端状态 |
| 断网还能改计划、看历史、写笔记 | 数据在 Python 进程里，页面是渲染出来的字符串 |
| 手机上看到一半，平板接着看 | 状态跟着设备走，不跟着账号走 |
| 群里有人跑了，立刻出现 | 只有轮询，没有长连接；服务端不是权威源 |
| 教练一个字一个字往外说 | 同步请求、整段返回 |
| 同一张活动图在 iPhone 上长一样 | 卡片是 HTML，iPhone 没有可跑的渲染器 |
| 一次只改 1% 用户看效果 | 没有特性开关，只能发版 |

# 一、目标形态：三层 + 两条总线

```
┌──────────────────────────────────────────────────────────────┐
│  一个前端（TypeScript SPA）                                  │
│  Android / iOS / 浏览器 / PWA 同一份代码与设计系统            │
└───────────────┬──────────────────────────────┬───────────────┘
                │ 命令 / 查询（JSON + SSE）     │ 本地读写（离线优先）
┌───────────────▼───────────────┐  ┌───────────▼───────────────┐
│  同步总线 sync                │  │  本地库 local store        │
│  变更日志 · 游标 · 冲突合并    │  │  SQLite / IndexedDB       │
└───────────────┬───────────────┘  └───────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│  服务端（一个进程，三类职责）                                 │
│  ① 账号与权限   ② 共享状态（小组/远征/排行榜）   ③ 代理外部源  │
│  ④ AI 教练服务  ⑤ 媒体与分享    ⑥ 事件与实验                  │
└───────────────┬──────────────────────────────────────────────┘
                │ 纯函数调用（同一份代码，本地/服务端都跑）
┌───────────────▼──────────────────────────────────────────────┐
│  领域内核 kernel（无 I/O，可确定性重放）                      │
│  训练负荷 · 间歇识别 · 计划 · 卡片几何 · 排名 · 远征规则      │
└──────────────────────────────────────────────────────────────┘
```

两条总线：
- **数据总线**：客户端事件 → 服务端事件表 → 物化视图（榜单、简报、图表）。
  所有"页面"都是视图，不是现场计算。
- **实时总线**：SSE 长连接推共享状态变化与 AI token，客户端按需订阅。

# 二、六条设计原则

1. **前端拥有交互，服务端拥有真相**。
   动画、手势、乐观更新、骨架屏全在客户端；服务端只回答"这条数据是什么、
   你能不能改"。现在的"服务端拼 HTML"把交互权也拿走了，所以翻页一定卡。
2. **本地优先**（local-first）。任何读写先落本地库、立即出结果，后台再同步。
   断网不是异常状态，是常态之一（跑步时经常没信号）。
3. **一个内核，多处执行**。训练负荷、间歇判定这类计算必须是纯函数，能在
   手机、服务端、测试里跑出**同一个数**。今天这些逻辑和 I/O 混在 `api/gui`
   里，导致"网页和 App 数字不一样"这类问题没法根除。
4. **一件事实只有一个源头**。小组排名只由服务端的物化视图算，客户端不算；
   卡片只由内核生成一次，App/网页/服务端共用。
5. **可观测、可实验**。每个关键动作是一条事件，每个新功能一个开关。
   没有这两样，优化体验就是凭感觉。
6. **跨端一致优先于单端极致**。iOS 现在是二等公民（只有阉割网页版），
   这是当前最大的体验缺口，架构必须让它变成一等公民。

# 三、逐层设计

## 3.1 前端：一个 SPA，四端同一份

- **栈**：TypeScript + React（或 Solid）+ Vite；TanStack Router/Query；
  设计令牌（颜色/字阶/间距/动效）集中一份，暗色主题由令牌切换而非复制 CSS。
- **壳**：Capacitor（Android/iOS）。它就是我们已经在用的 WebView，但把原生
  能力做成标准插件：后台同步、通知、文件、分享、BLE（体脂秤直接连）、
  安全存储（Keystore）。
- **能力**：
  - 路由级代码分割，冷启动先渲染壳与缓存数据（TTI < 1s）
  - 手势与转场（返回、下拉刷新、tab 切换）用原生级动画
  - 乐观更新：点赞/评论/记一笔立刻生效，失败再回滚
  - 虚拟列表（历史几百条不卡）
  - 图表用 Canvas/WebGL 绘制，滚动时 60fps
  - 离线队列：所有写操作进 outbox，恢复网络自动重放
- **为什么不是原生双端**：领域逻辑在 Python，重写成 Kotlin+Swift 两份等于
  把 6 万行算两遍；SPA + Capacitor 能让 Android/iOS/网页共用一套 UI 与交互，
  原生只承担"壳"的职责。**为什么不是 Flutter**：图表与分享生态弱于 Web，
  且要和 Python 内核打通需要 FFI，成本高于收益。

## 3.2 本地库与同步

- **本地库**：SQLite（移动端 op-sqlite）+ IndexedDB（纯浏览器）两个适配器，
  同一套 schema 与查询层（TypeScript 接口）。
- **记录形态**：
  - 活动/体重/睡眠：**append-only**（事实不可改，只追加）
  - 计划/目标/笔记：**可变实体**，带 `version` 与字段级时间戳
  - 小组成员：**集合语义**（增删幂等，天然可合并）
- **同步协议**（自建，不引 CRDT 框架）：
  - 客户端上行：`POST /sync/push`，一批带 `ulid + hlc` 的变更；
  - 服务端下行：`GET /sync/pull?since=cursor`，返回变更 + 新游标；
  - 合并：事实类只追加；可变实体按字段 LWW（HLC 排序，同毫秒比设备 id）；
    集合类取并集 + 墓碑。
  - 冲突可见：服务端返回 `conflicts[]`，客户端在设置里能看"这条被另一台设备
    覆盖过"，而不是静默丢数据。
- **为什么不引 CRDT 库**：我们只有三种语义，自建 300 行比引入框架更可控，
  也更容易在 Python 服务端复用同一套合并函数。

## 3.3 服务端：一个进程，六类职责

保留 Python（内核是 Python，重写不划算），但换成 **FastAPI + uvicorn**：
路由声明、请求校验（Pydantic）、SSE、依赖注入、OpenAPI 文档全都是现成的。
一个进程六块职责，内部按模块分，不拆微服务（几十到几千用户，拆了只是多几个
故障点）。

| 职责 | 内容 | 关键设计 |
|---|---|---|
| 账号与权限 | 邮箱验证码 / passkey / 设备令牌 | **一个会话模型**：短期 access + 长期 refresh，静默续期；外部账号（佳明/高驰/小米）作为"连接"，不参与登录 |
| 共享状态 | 小组、远征、排行榜、赛事 | **服务端唯一权威**；写入串行化（单写者队列），读走物化视图 |
| 外部源代理 | 佳明/高驰/小米/华为/Keep 的登录与拉取 | 每个源一个 `connector` 适配器，统一 `pull(since)->facts` 接口；登录态加密存、静默续期 |
| AI 教练 | 上下文装配、流式回答、工具调用 | 见 3.5 |
| 媒体与分享 | 活动图/视频/分享页 | 见 3.6 |
| 事件与实验 | 埋点、特性开关、灰度 | 见 3.7 |

- **存储**：SQLite（WAL）起步，单写连接 + 读连接池；到并发瓶颈再换 Postgres
  （schema 与查询层早就按 SQL 标准写，迁移是配置级）。**不引 Redis**：
  实时在线状态用内存 + 心跳表足够。
- **实时**：SSE（`GET /events/subscribe?topics=...`），Caddy 直接反代；
  客户端断线自动重连带 `Last-Event-ID`，不丢事件。

## 3.4 领域内核：唯一的一份计算

- **形态**：`kernel/` 目录，纯函数，输入输出都是 dataclass/JSON，不 import
  数据库、不读文件、不联网。**可确定性重放**：同样输入永远同样输出。
- **执行位置**：
  - 服务端：直接 import（榜单、简报、卡片生成）
  - Android：Chaquopy（已有能力，保留）
  - iOS / 浏览器：**不跑内核**，改为"服务端预计算 + 本地缓存"；只有少数
    必须离线算的（今日摘要）用 golden-file 对拍过的 TS 子集实现。
- **契约**：`kernel/contract/*.json` 定义每个函数的输入输出，CI 里跑
  "Python 结果 == TS 子集结果" 的对拍，对不上直接红灯。
- **收益**：`interval.py` 的判定阈值、`easteregg` 的彩蛋条件、组内排名口径
  从此只有一处；"App 显示 5 组、网页显示 10 组"这类问题从设计上消失。

## 3.5 AI 教练子系统

现在的教练是"页面里拼一段 context 调一次模型"。理想形态是**一个服务**：

- **上下文装配**（server-side）：从事件表生成结构化 athlete context
  （最近 7/28 天负荷、睡眠、体重、计划完成、比赛倒计时、伤病史、偏好），
  带版本号，可缓存、可解释（用户能点开"教练看到了什么"）。
- **工具调用**：教练可以调用内核的只读函数（`predict_race_time`、
  `plan_week`）拿精确数字，而不是让模型心算。
- **流式**：SSE 逐 token 下推，首字 < 1.5s；同时给"思考中"的结构化状态。
- **记忆**：对话原文全存 + 定期结构化摘要（不是向量检索，健康领域要可解释）；
  用户可查看、可删除。
- **评测**：`evals/` 里存 50 条金标准问答（含"数据里没有这一项"这类反例），
  每次改 prompt/模型跑一遍打分，回归才允许上线。
- **成本与降级**：按账号配额 + 缓存（同日同问题复用）；模型不可用时退化成
  "规则建议"（现有 `brief` 能力），不要给用户一个转圈。

## 3.6 媒体与分享

- **活动图**：从"HTML 卡片"改成**内核生成 SVG**。同样的数据 → 同一个 SVG，
  三端渲染完全一致；服务端转 PNG（resvg，无浏览器依赖），分享页直接出图。
  这一步同时解决"iPhone 上没有卡片渲染器"和"html2canvas 不支持文字渐变"。
- **视频**：端上编码（现有 ffmpeg 能力）为主，服务端兜底转码；产物进对象
  存储，分享走签名 URL（不暴露用户目录）。
- **分享页**：`/s/<id>` 是 SSR 的静态页（社交平台抓取需要），但内容来自
  同一份内核输出。

## 3.7 交付、实验、可观测

- **交付**：JS 包签名后放 CDN，版本清单 + 灰度（按用户哈希分批）；APK 只在
  壳/原生能力变化时才发。**替代现在的"代码包"**：现在的代码包是"下发任意
  Python 并执行"，理想形态是"下发签名前端资源"，风险面小一个数量级。
- **特性开关**：`flags.json` 服务端下发，支持按用户/设备/百分比；开关与代码
  同版本，可一键回滚。
- **埋点**：客户端批量上报事件（`ui.view`、`action.*`、`perf.*`），服务端
  append-only 落库；自建看板（不做第三方 SDK，健康数据不出服务器）。
- **质量**：错误边界 + 崩溃上报；性能预算（TTI、帧率、接口 p95）进 CI 门禁；
  端上 e2e 用真机农场跑主路径 20 条。

# 四、关键流程走查（验证这套架构真的更好）

**① 打开 App**：壳先渲染缓存 → 首页 100ms 内出骨架 → 本地库读昨日数据 →
后台拉增量 → 屏幕上的数字就地更新（无闪烁）。现在：等本地 Python 服务起、
等整页 HTML、等字体。

**② 跑完回到手机**：系统通知（本地任务或 FCM/Web Push）→ 点开直接进详情，
数据已在通知时预取。现在：轮询 + 手动同步。

**③ 群里有人刚跑完**：SSE 推一条 `activity.created` → 榜单就地插入并高亮。
现在：刷新页面才看到。

**④ 问教练**：输入框发送 → 本地先回显 → 服务端流式返回 → 首字 1.5s 内。
现在：整页 POST，等十几秒白屏。

**⑤ 地铁里没信号**：看历史、改明天的计划、写训练笔记全部可用，出站自动同步。
现在：页面打不开或一直转圈。

**⑥ 换 iPhone**：装同一个 App（Capacitor 壳），登录后所有数据、对话、小组
都在。现在：只有阉割网页版。

**⑦ 分享活动图**：点分享 → 出 SVG/PNG（三端一致）→ 系统分享面板。
现在：网页里点"存成图片"，靠 html2canvas 兜。

# 五、这套架构要付的代价（诚实清单）

| 代价 | 说明 | 缓解 |
|---|---|---|
| 构建链变重 | 前端要 node/vite/构建产物，不再是"改 py 就生效" | 前端产物走 CDN + 灰度，Android 不再依赖重装 |
| 两套语言 | TS 前端 + Python 服务端/内核 | 内核契约 + 对拍测试把它钉死；服务端不写业务 UI |
| 离线冲突要设计 | 多设备同时改同一个计划 | 三种语义（追加/字段 LWW/集合）已覆盖 95% 场景，冲突可见 |
| 首屏要自己做 | 骨架屏、缓存策略、错误态 | 用成熟路由/查询库，别自己造 |
| 团队需要前端能力 | 现在全是 Python | 这是唯一硬门槛；SPA 技术栈也是最好招人的 |

# 六、迁移路径（Strangler Fig，边跑边换）

不追求"一次性重写"，但要保证每一步都能上线、能回滚、用户无感。

- **M1（2 周）地基**：拆出 `kernel/`（先搬 `interval`、`ranking`、`body` 三类
  纯计算 + 契约测试）；同一份内核同时被现有 App 与新服务端调用。
- **M2（3 周）新前端 1 页**：SPA 只做"今日"，读 `/api/v2/*`；APK 里用开关
  让 5% 用户进 SPA 路由，其余人还是旧 HTML。指标对比后放量。
- **M3（3 周）同步层**：本地库 + push/pull 游标；先只同步"活动与日汇总"，
  再扩到计划与笔记。旧接口保留双写。
- **M4（3 周）小组与实时**：SSE + 服务端物化视图；小组页迁到 SPA；旧
  `/w` 页面改为 302 到 SPA 路由。
- **M5（2 周）iOS 与分享**：Capacitor iOS 壳；活动图改 SVG + 服务端出 PNG；
  分享页上线。
- **M6（收尾）**：退役 `serve.py` 的 HTML 渲染与"代码包"，保留 Python 内核
  与 connector；监控指标确认无回退后删旧代码。

每一步的验收不是"代码写完"，而是三个数字：**TTI、主路径 p95、崩溃率**，
以及一条用户可感知的改进（比如"群里立刻看到"）。

# 七、常见误区（明确不这么做）

- **不拆微服务**：用户规模撑不起，运维复杂度是纯负担。
- **不引 GraphQL**：客户端就几个固定页面，REST + 少量聚合接口更省。
- **不把内核移植到 Rust/Go**：性能不是瓶颈，迁移只是把风险换个地方。
- **不做"原生 + 网页"两套 UI**：那正是现在痛苦来源的另一版本。
- **不为实时而上 WebSocket**：SSE 足够、穿透性更好、实现更简单。
- **不把健康数据交给第三方分析 SDK**：隐私是这类产品的底线。

# 八、判断这套架构是否成功的指标

| 指标 | 现状（估） | 目标 |
|---|---|---|
| 冷启动到可交互 | 2~4 s | < 1 s |
| 页面切换 | 200~800 ms（整页） | < 100 ms（路由） |
| 教练首字延迟 | 8~20 s | < 1.5 s |
| 群动态可见延迟 | 取决于刷新 | < 2 s |
| 离线可用页面 | 0 | 全部只读 + 部分写入 |
| 支持平台 | Android + 阉割网页 | Android / iOS / 网页 / PWA |
| 一次小改动的发布 | 22 MB 或代码包 | JS 灰度，秒级回滚 |
