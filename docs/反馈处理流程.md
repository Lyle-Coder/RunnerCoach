# 反馈处理流程

内测期间，用户反馈从微信群进来。这份文档规定「一条反馈进来之后怎么办」，
包括分几类、每类谁动手、什么情况下**不许**自动发。

消息来源：**由项目拥有者转发／粘贴／截图给助手**。
微信个人号没有对外接口，也不要为了读群消息去搞 Hook 或非官方协议——
封号风险远大于省下的时间。

---

## 一、先分三类

判断只看一件事：**这次改动会碰到什么**。

| 类别 | 判据 | 动作 |
|---|---|---|
| **A 代码包级** | 只动 `garmin_cn/*.py` 里的文案、样式、纯函数、常量；不动 `android/`；不动 DB schema；不抬版本号 | 改 → 跑门禁 → 直接发代码包 |
| **B 原生级** | 动 `android/`（Kotlin / res / manifest / gradle）、改 DB schema、改协议契约、需要新权限、需要抬版本号 | 挂 Gitee issue，不自己动手 |
| **C 仅服务端** | 只动 `server/*.py` | 改 → 跑测试 → **单独部署**，不发代码包也不抬版 |

第三类容易被忘：改了服务端却没部署，表现是「代码改了、线上没变」，
比 A、B 两类都难查。所以 C 类做完必须显式说一句「已部署」。

不属于以上三类的情况：**先复现，再分类**。复现不出来的，走 issue 挂
「待复现」，不要猜着改。

---

## 二、A 类：直接发，但有硬门槛

项目拥有者已授权 A 类免确认直发。授权不等于无条件，下面四条**必须全绿**
才允许 `publish_code.py`：

1. `python cli.py selftest` 通过
2. `python tools/test_bgsync.py` 通过（动了后台/通知相关时必跑）
3. `python tools/text_audit.py` 没有新增命中
4. 能在代码里指出**具体哪一行**导致这个现象

第 4 条是防「猜着改」：如果只能凭反馈描述推断、指不到具体位置，说明
这条还没定位清楚，它不属于 A 类，应该挂 issue 或先复现。

### 仍然不许直发的情况

即使被判定为 A 类，出现下面任一条也要停下来问：

- 改动涉及**数据写入路径**（上报、上报队列、服务端请求）
- 改动涉及**日期/时区/周边界**的计算
- 改动涉及**发版/更新/挂载**逻辑（`codepack.py`、`apk_fetch`、`selftest` 守卫）
- 同一症状**改过一次没解决**（说明判断错了，别在同一个假设上加补丁）
- 需要改文案来「解释」一个行为，而不是改行为本身

这五条的共同点：错了不会立刻被发现，但会污染数据或让所有人卡在坏版本上。

## 三、B 类：挂 issue，不自己动手

命令：

```bat
python tools/gitee_issue.py --title "组页地图在 4G 下不显示" ^
    --body @/tmp/body.md --type bug
```

注意这个仓库的 issue 是**项目型**：必须走扁平路径 `/repos/{owner}/issues`
带 `repo=` 和 `issue_type=`，标准 REST 路径一律 404。编号是字母数字
（`IKWVF6`），不是自增数字。这些坑已经固化在 `tools/gitee_issue.py` 里。

标题格式：`<现象> · <在哪`>`，不要写「优化一下」「有 bug」这种。例：

- 好的：`组页地图在 4G 下不显示 · 足迹页`
- 差的：`地图有问题`

正文模板（四段，缺一段就别提）：

```
原话：用户怎么说的，照抄，不改写
复现：什么设备、什么操作、什么时候
判断：我这边的初步定位（能指到代码就指，指不到就写「未定位」）
为什么不能走代码包：动了 android/ 的什么，或者为什么要抬版
```

`--type` 只有三个：`bug` / `需求` / `任务`。标签不要自己造，
用仓库里已有的（默认不传）。

## 四、每次处理完给什么回执

三条信息，不要更多：

1. **归类**：A / B / C，一句话理由
2. **做了什么**：改了哪几个文件、版本号（A、C 类）或 issue 编号（B 类）
3. **没做什么**：判断为「不是代码问题」的，说清是什么问题（网络、权限、数据）

如果一条反馈最后判断成「不改」，也要回执说清原因，否则用户会以为漏了。

---

## 五、已知的「看起来像 bug，其实不是」

内测群最容易出现的误报，先按这张表排一遍再动代码：

| 现象 | 常见真实原因 |
|---|---|
| 通知收不到 | Android 13+ 没给通知权限；或省电模式冻结了 App |
| 后台没补传 | 「强行停止」会取消所有 job；或系统省电白名单没开 |
| 组页数据不更新 | 20 分钟节流；回前台 30 秒后才跑 |
| 榜单少人 | 对方关了共享（`share_level=off`），或还没上报 |
| 地图空白 | 没配高德 Key，或当天没跑过；不是渲染 bug |
| 更新下载失败 | 走的是 8443 + 自签证书，网络环境拦截；不是 APK 坏了 |
| 数据「少了一天」 | 跨周边界：周榜只算本周，上周数据在月榜 |

## 附：为什么不做自动监听群消息

2026-11-20 评估过一次，结论是**不做**。记在这里，免得以后重复讨论。

### 实测条件（项目拥有者的 PC）

- 微信 4.1.15.56（`Weixin.exe`），数据在 `Documents\xwechat_files\<wxid>\db_storage\`
- `message_0.db` 的文件头不是 `SQLite format 3`，说明库是加密的
- 系统 OCR 支持中文（`zh-Hans-CN`），但 PowerShell 的 `Add-Type` 被安全策略拦，
  调不到 WinRT 的异步接口
- pip 装不了包：索引页 curl 返回正常（1.1 MB），但 pip 报 `from versions: none`，
  Pillow / winsdk 都装不上
- 机器上没有第三方导出工具

### 四条路径的结论

| 路径 | 结论 |
|---|---|
| 手动复制／粘贴 | **采用** |
| 截图 + OCR | 环境不具备；且窗口遮挡、滚动会漏、深色小字识别差 |
| 第三方工具离线导出 | 违反腾讯协议；工具来源不可验证；微信小版本升级即失效 |
| 实时读取进程内存 | 风险最高，**明确不做** |

### 决定

只走手动。用户的原话是「数据安全要紧」——为了省每天几十秒去读别的进程的内存、
赌工具不失效，代价与收益不匹配。

如果将来消息量大到手动不可行，重开这个议题的前提是：**先攒到真实消息量数据**，
而不是先建工具。
