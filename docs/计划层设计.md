# 计划层设计（赛季玩法的前置）

> 状态：设计，未实现。2026-11-17。
> 目的：保证"每名跑者有一份可读、可改、可执行的本周计划"，
> 赛季的周目标与远征才有着落。

---

## 一、为什么先做这一层

赛季目标 = 本周计划里程。没有计划，目标就是空的。而现有计划能力散在四条链路上，
结构不统一、也不都能落盘，所以先收口成一个"计划层"。

**边界**：计划层只负责"读、写、改、推"。它不生成训练建议的文案，不参与赛季计分。

---

## 二、现有能力盘点

| 能力 | 位置 | 状态 |
|---|---|---|
| 读佳明日历 → 归一化为 `plan.json` | `plan.fetch_calendar` / `from_calendar` | ✅ 可用 |
| 本地兜底生成整周结构 | `plan.from_coach` | ✅ 可用，但不落盘 |
| 高驰课表导入 | `coros_workout_*` | ✅ 可用 |
| 建训练课 + 排日历 | `workout.build_all` / `create` / `schedule` | ✅ 可用 |
| 清理已推送课程 | `workout.list_mine` / `delete_old` | ✅ 可用 |
| 完成/未完成判定 | `plan.annotate` | ✅ 可用 |
| **用户自建周计划** | 无 | ❌ 缺 |
| **计划落盘 + 来源标记** | 无 | ❌ 缺 |

结论：**缺的是"统一模型 + 自建写入 + 来源优先级"**，不是从零做。

---

## 三、数据模型

沿用现有 `plan.json` 的 `week[]` 结构，只补三个字段。

```json
{
  "source": "manual",
  "week_no": 2,
  "start": "2026-11-17",
  "week_km": 30,
  "focus": "有氧基础",
  "days": [
    {
      "date": "2026-11-17",
      "dow": "周一",
      "rest": false,
      "source": "manual",
      "items": [
        {
          "kind": "easy",
          "km": 6,
          "minutes": 36,
          "vert": 0,
          "note": "轻松跑，能说话",
          "steps": []
        }
      ]
    }
  ]
}
```

`item` 字段与 `workout.build` 的输入对齐，推手表时补 `week` / `dow` / `abbr` 即可。

| 字段 | 说明 |
|---|---|
| `kind` | `easy` / `tempo` / `interval` / `long` / `race` / `strength` / `rest`，**不填默认 `easy`** |
| `km` / `minutes` | 量与时长，至少填一个 |
| `vert` | 目标爬升（越野用） |
| `steps[]` | 结构化步骤，可选；不填则按 `kind` 套模板 |
| `note` | 一句话说明 |

---

## 四、四个来源与优先级

```
manual（用户自建/改过） > calendar（佳明日历） > coros（高驰导入） > generated（自动生成）
```

- 优先级按**天**判定，不按周：用户只改了周三，周三变 manual，其余六天仍跟日历。
- `plan.json` 顶层记整周来源，每个 day 记自己的来源，冲突时取优先级高的那个。

---

## 五、编辑与确认流程

### 5.1 读

1. 有 `plan.json` 且未过期 → 直接用
2. 否则按来源顺序尝试：日历 → 高驰 → 生成草稿
3. **合并 `plan_overrides`**：用户改过的日期以本地为准，覆盖来源数据
4. 都没有 → 返回 `empty`，页面提示"先设置本周计划"

### 5.2 改

- 单日编辑：改 km / kind / note / steps，保存后写入 `plan_overrides`（按日期键）
- 整周编辑：一次提交 7 天
- **不直接改佳明日历**：本地改的是"我的计划"，佳明那边保持原样，除非用户明确点"同步到佳明"

### 5.3 确认

| 来源 | 是否需要确认 |
|---|---|
| 用户自建 | 保存即生效 |
| 自动生成 | **先出草稿**，用户点"采用"才写入 `plan.json` |
| 日历 / 高驰 | 自动生效，无需确认 |

草稿存 `data/plan_draft.json`，与正式 `plan.json` 分开，避免半成品影响赛季结算。

保存或确认后**提示一次**“是否同步到今天的手表”，可一键推送；同一天不重复弹。

### 5.4 自动续

- 生成型计划：确认过一次后，记住"沿用此规则"，每周一 00:00 自动生成下一周并生效，
  页面提示"已为本周生成计划，可修改"。
- 自建计划：每周一提示"本周还没有计划，复制上周 / 新建"。
- 日历型：跟随佳明，不主动生成。

## 六、详细度：两级，不强迫

| 级别 | 填什么 | 推手表时 |
|---|---|---|
| 简单 | `km` + `kind` | 按课型套模板（热身 / 主课 / 冷身） |
| 详细 | `steps[]`（时长/距离 + 配速或心率区间 + 重复组） | 直接转 Garmin DTO |

界面上默认简单模式，展开"高级"才出现步骤编辑。大部分跑者不会填 steps，
但会填"周三 7 公里节奏跑"——这已经能推出可执行的课。

## 七、反推手表

### 7.1 链路

```
PlanItem → info（补 week/dow/abbr）→ workout.build_all → POST /workout-service/workout
        → POST /workout-service/schedule/{id} → 手表同步
```

### 7.2 同步策略

| 场景 | 做法 |
|---|---|
| 首次推送 | 建课 + 排期 |
| 计划改了 | 先 `delete_old` 清旧课，再重新推（`replace=True`） |
| 只改了一天 | 只重推那一天，其余不动 |
| 推送失败 | 本地计划保留，标记"未同步"，可手动重试 |
| 休息日 | 不建课、不排期 |

### 7.3 去重与命名

沿用现有约定：课名以 `W<周数>` 开头（如 `W2 周三 节奏跑`），`list_mine` 靠这个前缀
识别"自己推的课"，不会误删用户在佳明里手建的课程。

### 7.4 边界

- 只推**跑步 / 越野 / 力量 / 骑行**四类；其他运动不建课。
- 推手表是**可选动作**，不点就不推——不能因为用户没连佳明，就让计划层不可用。
- 时区用日期字符串，不做 UTC 转换。

---

## 八、与赛季的契约

赛季只读一个值：

```
week_target_km = Σ（本周非休息日、跑步类 kind 的 km）
```

- 目标在周一快照，周中改计划**不影响**本周目标（只降不升由赛季层兜底）。
- 计划层不关心组、不关心赛季，只保证"本周有一份计划、能算出里程"。

## 九、实施顺序

| 步骤 | 内容 | 依赖 |
|---|---|---|
| ① | 统一模型 + `source`/`day.source` 字段，读入口兼容旧 `plan.json` | 无 |
| ② | `plan_save`：单日/整周写入 + `plan_overrides` 合并 | ① |
| ③ | `plan_generate`：按历史跑量出草稿 + 采用/放弃 | ① |
| ④ | `plan_push`：计划 → 训练课 → 日历，含替换与失败重试 | ① |
| ⑤ | 每日完成判定对接（复用 `annotate`） | ① |
| ⑥ | 赛季读取 `week_target_km` | ①–⑤ |

②③④ 可以并行，但都要等 ① 的模型定稿。

---

## 十、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 旧 `plan.json` 没有 `source` | 读旧快照会崩 | 读时补默认值 `calendar`，写时再升级 |
| 用户改计划后手表没更新 | 执行错课 | 编辑后提示"是否同步到今天的手表"，给一键推 |
| 重复推送产生大量旧课 | 手表课程列表污染 | 只删 `plan_push.json` 里记过的 workoutId，不调 `delete_old()`（按名字前缀批量删会误伤官方计划） |
| 生成规则不适合个人 | 计划不可用 | 一律先出草稿、可改；不直接覆盖 |
| 时区/跨日 | 排到前一天 | 只传 `YYYY-MM-DD`，不做时间换算 |
| 没有佳明账号 | 功能不可用 | 计划层本地可用，推送单独降级 |

## 十一、落地记录（2026-11-17 已实现）

### 11.1 模块划分

| 文件 | 职责 | 写盘 |
|---|---|---|
| `garmin_cn/plan.py` | 只读归一化（日历 / 教练 / 本地兜底 → 同一结构）+ 合并改动 + `week_target()` | 只念，不写 |
| `garmin_cn/planedit.py` | 单日/整周保存、撤销、校验、编辑视图 | `plan_overrides.json` |
| `garmin_cn/plangen.py` | 画像、草稿生成、确认、每周一自动续 | `plan_draft.json` / `plan_rules.json` |
| `garmin_cn/planpush.py` | 计划 → 训练课 → 日历 | `plan_push.json` |
| `garmin_cn/contentguard.py` | 构建前拦截剧情内容进包 | 不写 |
| `tools/guard_content.py` | 上面那个的命令行入口，`build.bat` 会调 | 不写 |

`plan.py` 保持**只读**：任何读取方都不会因为调了它而改到磁盘。写入集中在
`planedit.py` 一个地方，校验也只有一份。

### 11.2 落盘文件

```
data/plan.json            来源快照（日历 / 教练 / 高驰），只由同步写，永远是原样
data/plan_overrides.json  用户改动，按日期存，唯一可编辑的计划文件
data/plan_draft.json      生成但还没确认的草稿
data/plan_rules.json      自动续状态（auto / week_index / last_week）
data/plan_push.json       自己推到佳明的 workoutId（重推与清除只认这份记录）
```

**快照落盘的是原样数据，不改写**。合并发生在读取时（`plan.load` / `plan.fetch`
返回前），所以重新拉日历不会把用户的修改固化成"来源数据"，也不会冲掉它。

### 11.3 接口

| 接口 | 作用 |
|---|---|
| `plan(date?, refresh?, source?)` | 读本周课表（已合并改动、已重算完成度） |
| `plan_week(date?)` | 编辑视图：每天当前课 + 来源 + 是否改过 + 是否为过去 |
| `plan_save(date, items, rest, note)` | 保存某天（`items` 是 JSON 字符串） |
| `plan_save_week(days)` | 整周保存，一天不合法整体不落盘 |
| `plan_clear(date?)` | 撤销某天 / 全部改动 |
| `plan_overrides()` | 列出所有改动 |
| `plan_generate(run_days, week_km)` | 生成草稿（不落正式计划） |
| `plan_draft()` | 读现有草稿 |
| `plan_confirm()` | 确认草稿 → 写改动 + 开启自动续 |
| `plan_renew()` | App 启动时调一次，周一自动续 |
| `plan_push(dry, phase)` | 推成佳明训练课并排日历；`dry=true` 只返回 payload |
| `plan_push_info()` / `plan_push_clear()` | 查看 / 删除自己推的课 |
| `plan_target(date?)` | 本周跑步里程合计，赛季直接读这个 |

### 11.4 生成规则（实际参数）

周量 = 近 4 周周均 × 系数，系数取「赛事系数」与「减量周系数」中较小的一个：

| 条件 | 系数 |
|---|---|
| 离下一场比赛 ≤ 7 天 | 0.5 |
| ≤ 21 天 | 0.7 |
| ≤ 84 天 | 1.1 |
| > 84 天或无赛事 | 1.05 / 1.0 |
| 每第 4 周（`week_index % 4 == 0`） | 0.7 |

上浮有硬上限：不超过近 4 周均值的 **1.15 倍**。长距离单次不超过 **32 km**，
且不超过周量的 45%。

| 每周跑几天 | 长距离占比 | 强度课占比 |
|---|---|---|
| 1 | 100%（当唯一一次） | — |
| 2 | 55% | — |
| 3 | 40% | 25% |
| 4 | 34% | 24% |
| 5 | 30% | 22% |
| 6 | 28% | 20% |

排课顺序：周三（强度）→ 周六（长距离）→ 周一 → 周五 → 周四 → 周二 → 周日。
一周只跑两天时**不排强度课**——两天的人把一天练成节奏跑，效果不如两次有氧。

配速按历史中位数推：轻松 ×1.08、节奏 ×0.97、长距离 ×1.10；没有任何配速数据时
按 6'00"/km 兜底。时长 = 里程 × 配速，取整到 5 分钟。

**生成器不排间歇课**。没人给强度目标时自己加间歇是越界。

### 11.5 三个关键取舍

1. **快照不合并落盘**。合并只发生在读取时。代价是每次读多解析一个小文件，
   收益是「改完计划」和「重新同步」永远不互相破坏。
2. **确认草稿不盖手改**。改动记录带 `origin`（`manual` / `generated`），
   `plan_confirm` 跳过所有 `manual` 的天，并在返回里报 `skipped_manual`。
   自动续是给"没管这周"的人用的，不是给"安排好了又被系统改掉"的人用的。
3. **推送只删自己建的课**。不用 `workout.delete_old()`（它按 `W<周数>` 前缀批量
   删，会误伤官方教练计划的课），改成记录自己的 workoutId。代价是要维护一份
   记录，收益是永远不会删错。

### 11.6 已知限制

- **App 界面还没接**。这一轮只做了 Python 侧与接口；`MainActivity` / WebView 的
  编辑页、草稿预览页、推送按钮都还没做，目前只能用 MCP / 调试入口调。
- **推送没在真机验证过**。本机没有 adb，也没有可用的佳明登录态。`dry=true` 的
  payload 结构已核对（`W47 周二 轻松跑` 这类课名、`schedule` 的日期格式），
  但「推上去手表能不能收到」需要真机跑一次。
- **赛事系数会明显压低周量**。当前本机有 12 天后的秦岭 43K，生成出来是
  48.3 × 0.7 ≈ 34 km。这是设计意图（赛前减量），但如果用户不想让 App 自己的
  计划干预备赛，需要给「不按赛事减量」的开关——现在没有。
